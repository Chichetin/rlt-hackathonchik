**F-01. Дата `as_of` из запроса строит индекс BM25 и блокирует поиск всех пользователей.**
`Query.as_of` — ручка backtest (eval вызывает `search()` напрямую), но `/api/search` и `/api/export`
принимали её от клиента. На каждую новую дату `get_index()` строит индекс под глобальным `index._lock`,
затем `supplier_rows()` падает (`suppliers_<as_of>.parquet` нет) — 503. Доступ атакующего: любой, кто
может отправить POST в API (аутентификации нет); ввод — одно поле JSON. Замер на полных данных
(parquet, без сети): запрос с `as_of=2025-03-01` — **46.3 с и 110 МБ** нового индекса на диске; обычный
поиск, запущенный через 3 с после такого запроса, — **40.2 с вместо ~0.5 с**; в docker-compose каталог
индексов смонтирован только для чтения — там это 500. Исправление: `_accepted()` отвечает 422 до
поиска. Тест: `tests/unit/test_api.py::test_search_rejects_client_as_of_without_building_an_index` (до
правки — 503 и собранный индекс, после — 422, каталог индексов пуст). Риск правки: интегратор, который
по OpenAPI передаст `as_of`, получит 422 с объяснением; UI, e2e, `make latency` его не передают.

**F-02. Неограниченная длина текста запроса.** Замер `/api/search` по длине текста: 2 000 символов —
0.4 с, 20 000 — 1.0 с, 200 000 — 3.7 с, **1 000 000 — 17.9 с** на запрос (поток пула занят всё это время).
Самый длинный текст в `eval/cases/dev.jsonl` — 4 553 символа (p99 — 1 160). Исправление: 422 при тексте
длиннее 20 000 символов (`MAX_TEXT_CHARS`), а не молчаливая обрезка. Контракт `Query` не менялся
(заморожен). Тест: `test_search_rejects_oversized_text`. Гипотеза ревьюера «повтор одного частого токена
дороже» внутри лимита опровергнута замером: 20 000 символов «услуги » (2 857 одинаковых токенов) — 1.06 с,
«поставка » — 0.69 с.

**F-03. `make eval-final` на полном holdout не укладывается во время до code freeze и сжигает
конфигурацию при прерывании.** Holdout — 88 848 кейсов; `evaluate()` тратит 0.25 с (E-002: 498.7 с на
2 000) — 0.30 с (H-15f: 609.7 с) на кейс → **6–7.5 ч одним запуском**, а по `docs/timeline.md` он стоит в окне
15:00–16:30 02.10. Маркер «конфигурация уже оценивалась» пишется **до** чтения holdout: прерванный
прогон оставляет конфигурацию сожжённой и без результата. Результат в прежнем формате (`indent=2`) на
88 848 кейсах — ≈ 14.7 МиБ, выше стража коммита 5 МБ. Длительность нигде не оценивалась. Исправление:
`holdout_sample: 3000` и `holdout_seed` в `configs/split.yaml` (входят в sha256 конфигурации — выборка
задана до запуска и не зависит от результата), `final.holdout_sample()` — n кейсов с наименьшим
sha256(seed:query_id); результат построчно (`dump_record`) с полем `sample`; ≈ 15–25 мин (0.30–0.47 с на кейс), 95% CI recall@10 ≈
±0.016. Тесты: `tests/unit/test_eval_seal.py::test_holdout_sample_is_fixed_by_seed_not_by_order`,
`::test_final_main_evaluates_the_configured_sample`. Ограничение протокола, которое правка не снимает:
`eval-final` меряет только конфигурацию продукта — baseline на holdout не считается, сравнение с
baseline остаётся на dev.

закупки» на прошлом лоте — круговой: ответ лежит в индексе. Что сделать (решение команды, не исправлено):
показывать новые лоты из тестовой выгрузки организаторов (`TEST_DATA_DIR`, #121), или для лотов dev искать

явно отмечать в карточке участников открытой закупки.

## 5. Эксперименты

R-fresh-<id> [--config-of H-15f | --baseline B-bm25]`, разница — `uv run python -m src.eval.compare`.

## 7. Остаточные риски и следующие шаги

Риски, которые этот проход не закрыл:
- F-07: живое демо без воркера и без прогретого кеша — блок «С опытом» без названий (решение человека:
  внешние запросы к ФНС).
- F-13: показ прошлого лота по номеру находит его собственных участников — формулировки на защите и выбор
  демо-лота.
- F-04/Э-1/Э-2: дефолт v1 слабее B-bm25 и H-15f на всех проверенных выборках; переход — подтверждение №3.
- F-05: внутри блока «Новые» порядок — ИНН; качество блока не измерено.
- API без аутентификации и лимитов (F-10); для встраивания в АИС ГЗ — шлюз с аутентификацией.

Три следующих действия с наибольшей пользой:
1. До защиты: запустить воркер рядом с API (`make demo`), прогреть кеш (`uv run python -m
   src.worker.prefetch --top 200`, затем поиск по демо-лотам) и выбрать демо-лот, который не находит сам
   себя (тестовая выгрузка `TEST_DATA_DIR` или поиск на дату cutoff).
2. Подтверждение №3: перенести H-15f в `configs/search.yaml` (Э-1: +0.102 к v1, +0.033 к B-bm25 на кейсах
   вне подбора), затем `make eval-final` на выборке 3 000 (≈ 15–25 мин) до code freeze.
3. Достроить Э-2 (`R-free-H-15f`) и разметить блок «Новые» (#21) — это две незакрытые цифры качества для К2
   и К3.

## 8. Вердикт прохода

Для целевого сценария — живое демо подбора на реальных данных и защита — проект **в основном готов**:
поиск, обогащение через кеш, объяснения и источники фактов работают, утечек во времени в backtest не
найдено, `make check` зелёный на исходной ревизии. **Не готовы** три вещи, влияющие на баллы: состояние
живого демо (F-07), круговой показ прошлого лота (F-13) и дефолт скоринга, который измеримо слабее
доступной альтернативы (F-04). Полная безопасность и оптимальность методов этим проходом не
утверждаются: Postgres-путь, сеть источников и UI-стили не проверялись (раздел 2).

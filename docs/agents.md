# Система агентов

Источник: разделы 2, 13, 14 `docs/source/hackathon-research-workflow.md`; форма — образцы
команды (Почта, FloodValue). Определения — `.claude/agents/*.md`, протокол сессии участника —
`.claude/skills/orchestrate/SKILL.md` (`/orchestrate`). Правила проекта агенты получают из
`CLAUDE.md` автоматически; в промпте роли — только то, что её отличает.

Общего оркестратора нет: у каждого из четырёх участников своя сессия, которая берёт **свои** задачи
из GitHub Issues и гоняет конвейер ролей. Стыковка — через контракты и `main`.

## Роли

| Роль | Модель | Когда | Видит и может | Возвращает |
|---|---|---|---|---|
| сессия участника | модель человека | всё окно | основная копия на `main` — только чтение; берёт задачи, заводит worktree, пишет брифы, запускает роли | итог окна: что влито, что в работе, что ждёт человека |
| `builder` | sonnet; сложность «высокая» → `model: opus` | одна issue | свой worktree: тест → код → `make check` → PR → `reviewer` → merge по вердикту | PR, команды и числа, решения D-… |
| `reviewer` | opus | каждый PR и каждое спорное решение | только diff против `origin/main` + условия + контракты; ничего не правит | `merge` / `доработать` / `отклонить` с `файл:строка` |
| `evaluator` | sonnet | после изменения поиска, скоринга, данных | `make eval EXP=<id>`; `eval-final` — только по заморозке | строка в `EXPERIMENTS.md`, числа с интервалами |
| `operator` | sonnet | после UI-изменений, перед чек-поинтами | UI в роли пользователя (контрактный управляющий `[ОБНОВИТЬ 01.10]`) | где сценарий не укладывается в 60–90 с, топ-3 правки |
| `jury` | opus | перед каждым чек-поинтом и сдачей; арбитр | только артефакты репозитория | оценка по 10 пунктам; 15 каверзных вопросов; вердикт арбитра |
| `scribe` | sonnet | README, методология, словарь, факты | свой worktree по задаче; цифры только из `eval/results/*.json` | документы, где каждое утверждение с командой |
| `pitch` | sonnet | после чек-поинта 2 | `pitch/`, числа — только из `pitch/facts.md` | две версии питча, `QA.md`, сценарий видео |

`haiku` не используется нигде: дешёвая модель чаще выдумывает числа в отчётах (D-013).

## Конвейер задачи

```text
сессия: take #N → worktree → бриф
  → builder: тест → код → make check (+ make e2e) → merge origin/main → PR (Closes #N)
  → reviewer: diff → вердикт
  → (доработать → тот же builder через SendMessage → reviewer; 2 отклонения → jury)
  → evaluator, если менялись поиск/скоринг/данные
  → merge по одному: git merge origin/main → make check → gh pr merge --merge --delete-branch
  → issues.sh note → уборка worktree
веха: operator → jury → submission-checklist (перед сдачей)
```

## Решения без человека

Решение по реализации, трактовке, методу, контракту — `reviewer` в режиме «решение» (или
скептик с контекстом только из diff и условий) → «принять» → строка в `research/DECISIONS.md`.
Человеку — только пять подтверждений из `CLAUDE.md` («Автономия»). Блоки «ЗАДАЧА / СДЕЛАНО»
печатаются человеку и не блокируют работу.

## Что знать, запуская вручную

- Субагент стартует в рабочем каталоге сессии (основная копия), поэтому worktree заводит сессия, а
  абсолютный путь идёт в бриф. `isolation: worktree` у Agent не использовать: он даёт свои имена
  веток, а хуки и уборка опираются на `worktree-<N>-<тема>`.
- В брифе любой пишущей роли — номер задачи #N; без него хук `check-issue.sh` не даст править.
- Параллельно — не больше трёх `builder`, с непересекающимися каталогами (`docs/project-structure.md`).
- `SubagentStop`-хук `check-worktrees.sh` ищет секреты во всех worktree после каждого субагента.
- Из worktree e2e — со своим портом: `E2E_PORT=8766 make e2e`.
- Находки `operator`, `jury` — новые задачи (`issues.sh create`), а не строки в документах.

# RLT.Hack — сервис подбора поставщиков для АИС ГЗ и Электронного магазина СПб

## Operating manual для четырёх параллельных сессий Claude Code

> **Для людей** (агент этот блок тоже читает, но адресован он команде)
>
> 1. Положите файл в корень репозитория и добавьте в `CLAUDE.md` строку `@hackathon-research-workflow.md` (или переименуйте файл в `CLAUDE.md`). Тогда каждая сессия Claude Code подхватит его автоматически.
> 2. До 1 октября выполните раздел 16 «Подготовка». Часть пунктов (вопросы организаторам, ключи API) требует времени на ответ.
> 3. На постановке задачи (1 октября, 10:00–10:15) один человек записывает, остальные слушают. Сразу после — 20 минут на заполнение раздела 1.
> 4. Каждый открывает свою сессию фразой: `Моя роль: DATA | MATCH | SOURCES | APP. Прочитай CLAUDE.md и status/*.md, затем выполни «Первые действия» своей роли.`
> 5. **[ПРОВЕРИТЬ]** — предположения, которых нет в условиях хакатона. Агент не строит на них необратимых решений.

## 0. Кейс и что считается победой

**Из условий.** RLT.Hack от Росэлторг, 1–2 октября 2026, Санкт-Петербург, очно. Цель — сервис подбора наиболее релевантных исполнителей контрактов: поставщиков, производителей и дистрибьюторов для АИС ГЗ и Электронного магазина Санкт-Петербурга. Призы: 250 / 175 / 100 тыс. ₽.

**Контекст.** АИС ГЗ — региональная система госзаказа Петербурга: Портал 44, Портал 223 и Электронный магазин — подсистема закупок малого объёма (п. 4, 5 ч. 1 ст. 93 44-ФЗ). Сведения о закупках малого объёма, поданных офертах и заключённых контрактах в Электронном магазине публичны (estore.gz-spb.ru). Техподдержку АИС ГЗ ведёт СПб ГБУ «Информационно-методический центр»; его директор и заместитель председателя Комитета по госзаказу СПб входят в жюри. Значит, среди судей — будущие пользователи и владелец системы, в которую решение должно встраиваться.

**Что требуют условия.** Это и есть чек-лист оценки. Каждый пункт должен быть закрыт видимым артефактом:

| # | Пункт условий | Что показываем на защите | Владелец |
|---|---|---|---|
| 1 | Проанализировать данные организаторов | профиль данных и 2–3 инсайта с цифрами | DATA |
| 2 | Определить бизнес-смысл полей | `research/DATA_DICTIONARY.md` → слайд | DATA |
| 3 | Создать методологию подбора контрагентов | `research/METHODOLOGY.md` → слайд с формулой и компонентами | MATCH |
| 4 | Поиск поставщиков в открытых источниках | живой поиск компаний, которых нет в данных организаторов | SOURCES |
| 5 | Обогащение данных по контрагентам | карточка контрагента, где у каждого факта указан источник | SOURCES |
| 6 | Удобный веб-интерфейс | сценарий заказчика за 60–90 секунд | APP |
| 7 | Тест на реальных кейсах | 5–10 реальных закупок СПб: прогон, метрики, разбор | DATA |
| 8 | Возможность масштабирования | схема архитектуры и то, что из неё реально работает | APP |
| 9 | Демонстрация работоспособности | live-демо и запасное видео | APP |
| 10 | Презентация | две версии: основная защита и защита Топ-5 | APP (+ все) |

Пропущенный пункт — прямая потеря баллов. Пункт, закрытый «на словах», почти то же самое.

Победа — это когда жюри видит, что сервис **работает на реальных данных**, **находит больше и лучше, чем заказчик нашёл бы сам**, **объясняет каждую рекомендацию и происхождение каждого факта** и **понятно, как встраивается в АИС ГЗ**.

Главная установка:

**Сначала работающий end-to-end, потом измеримое качество, потом полировка. Прозрачность важнее изощрённости: жюри из госзаказа должно понимать, почему поставщик оказался в списке.**

## 2. Команда и координация

Четыре человека, у каждого своя сессия Claude Code. Главные риски параллельной работы: конфликты правок, разные представления о схеме данных и четыре агента, которые молча делают одно и то же.

### Роли и владение

| Роль | Владеет | Отвечает за |
|---|---|---|
| DATA | `src/ingest/`, `data/processed/`, `eval/`, `research/DATA_DICTIONARY.md` | данные организаторов, смысл полей, единая схема, реальные кейсы, backtest и метрики |
| MATCH | `src/match/`, `indexes/`, `research/METHODOLOGY.md` | понимание запроса, кандидаты из истории, скоринг, объяснения |
| SOURCES | `src/sources/`, `src/enrich/`, `cache/` | поиск компаний в открытых источниках, сопоставление с ИНН, обогащение, проверки надёжности |
| APP | `src/api/`, `src/ui/`, `deploy/`, `pitch/` | API, интерфейс, docker-compose, сценарий демо, чек-поинты, презентация |

**Пиши только в свои директории.** Нужна правка чужого модуля или контракта — запиши запрос в раздел `REQUESTS` своего `status/<роль>.md` и скажи своему человеку.

APP одновременно ведёт интерфейс и питч, и во второй день это самая нагруженная роль. После feature freeze (2 окт, 14:00) цифры и слайды по методологии готовят DATA и MATCH, APP собирает презентацию.

### Контракты

`src/contracts.py` фиксируется до 11:30 первого дня; дальше меняется только по согласию всех четверых. Ниже стартовая версия; DATA правит поля после профилирования данных.

```python
class Query:                       # потребность заказчика
    query_id: str
    text: str                      # наименование, описание или фрагмент ТЗ
    okpd2: str | None
    ktru: str | None
    region: str = "Санкт-Петербург"
    budget: float | None
    filters: dict                  # только СМП, только производители, регион и т. п.

class Evidence:                    # один факт и его происхождение
    source: str                    # "data:contracts", "ЕГРЮЛ", "сайт компании", ...
    url: str | None
    fetched_at: datetime
    fact: str

class Counterparty:
    inn: str | None                # ключ; None — ИНН ещё не подтверждён
    name: str
    kind: str | None               # manufacturer / distributor / dealer / unknown
    region: str | None
    status: str | None             # действующее / в процессе ликвидации / ...
    is_msp: bool | None
    in_rnp: bool | None
    okved: list[str]
    contacts: dict[str, str]       # только корпоративные контакты из источников
    stats: dict                    # контракты по категориям, суммы, последняя активность
    evidence: list[Evidence]

class ScoreComponent:
    name: str                      # product_fit / experience / reliability / activity / geography / price
    value: float                   # 0..1
    weight: float
    explanation: str               # одна строка для пользователя

class CounterpartyMatch:
    counterparty: Counterparty
    score: float
    components: list[ScoreComponent]
    origin: str                    # "history" — есть в данных организаторов; "discovered" — найден в открытых источниках

def search(query: Query, k: int = 20, weights: dict | None = None) -> list[CounterpartyMatch]: ...
def enrich(inn: str) -> Counterparty: ...
```

Пока реального `search` нет, MATCH отдаёт stub: валидные по схеме данные, код помечен `# STUB`, при вызове в лог пишется предупреждение. APP строит интерфейс против stub. Перед демо `grep -rn "STUB" src/` должен возвращать пустой результат.

### Общая память

Не полагайся на контекст текущей сессии: он кончится или будет сжат. Внешняя память проекта:

```text
research/
    PROBLEM.md          # задача, пользователь, сценарии, open questions
    DATA_DICTIONARY.md  # поле → тип → пример → заполненность → бизнес-смысл → уверенность → как проверили
    METHODOLOGY.md      # как считается релевантность; это же слайд
    SOURCES.md          # внешние источники: что дают, доступ, лимиты, риски
    DECISIONS.md        # append-only: решение, почему, альтернативы, фидбек с чек-поинтов
    EXPERIMENTS.md
    ERROR_ANALYSIS.md
status/
    data.md  match.md  sources.md  app.md
```

Формат status-файла:

```text
UPDATED: <время>
DONE:
DOING:
NEXT:
BLOCKED BY:
REQUESTS: (к другим ролям)
```

Обновляй свой status после каждой завершённой задачи и перед `/compact`, `/clear` или концом сессии. Перед новой задачей читай чужие status — это дешевле, чем дублировать работу.

### Git и секреты

Trunk-based, маленькие коммиты, `git pull --rebase` перед push, `main` всегда запускается. Ломающее изменение сначала делается в ветке. Ключи API хранятся только в `.env`; `.env` — в `.gitignore`.

### Лимиты

Лимиты Claude Max конечны. Массовые LLM-вызовы через сессию (разметка сотен пар, извлечение данных с сотен сайтов) — только после согласования с человеком: если у одного из четверых лимит закончится посреди дня, команда потеряет четверть мощности. Рантайм продукта не зависит от подписки Claude: если продукту нужна LLM, используется API, разрешённый правилами, с fallback без LLM.

## 4. Предметная область

Стартовое понимание. Всё, кроме условий хакатона и фактов об АИС ГЗ из раздела 0, — **[ПРОВЕРИТЬ]**.

- Заказчики — госучреждения Петербурга. В Электронном магазине они размещают закупки малого объёма, поставщики подают оферты. Мало оферт — мало конкуренции и выше цена, поэтому найти и пригласить релевантных поставщиков — очевидная ценность.
- Для обоснования НМЦК заказчики собирают коммерческие предложения. Найти, у кого их запросить, — вторая возможная задача сервиса.
- Сигналы релевантности: коды ОКПД2 (иерархия вида `XX.XX.XX.XXX`) и КТРУ, наименования позиций в истории контрактов и оферт, ОКВЭД компании, регион, опыт работы с госзаказчиками.
- Сигналы надёжности: статус юрлица (действующее, ликвидация, банкротство), возраст компании, наличие в реестре недобросовестных поставщиков (РНП), расторгнутые контракты, финансовая отчётность.
- Правовые фильтры, которые могут быть важны заказчику: закупки только у СМП/СОНКО (ст. 30 44-ФЗ), национальный режим и реестры российской продукции. Мы не юристы, поэтому оформляем это как фильтры, которые пользователь включает сам, и уточняем у экспертов.
- Производитель, дистрибьютор и дилер — разные сущности с разной ценностью: производитель часто дешевле, дистрибьютор надёжнее по срокам и ассортименту. Тип определяется по ОКВЭД, реестрам промышленной продукции и сайту компании.
- Сервис рекомендует, а не назначает: закупка остаётся открытой для всех. Этот тезис готовим к вопросам о конкуренции и равном доступе.
- Официальные руководства пользователя АИС ГЗ опубликованы на manuals.gz-spb.ru. Это первый источник для пункта «бизнес-смысл полей».

## 5. Методология подбора

Пишется в `research/METHODOLOGY.md` и становится слайдом. Это прозрачная взвешенная модель, а не чёрный ящик: жюри из госзаказа должно понимать каждую компоненту.

**Шаг 1. Понимание запроса.** Нормализация текста (регистр, ё→е, единицы, числа, лемматизация). Если ОКПД2/КТРУ не указаны, код предсказывается по ближайшим позициям из истории (голосование по префиксу). Разбор ТЗ на позиции и характеристики с помощью LLM — только если хватит времени и API разрешён.

**Шаг 2. Кандидаты из двух источников.**

- *Из данных организаторов* — контрагенты, которые поставляли или предлагали похожие позиции. Лестница: BM25 по наименованиям → совпадение ОКПД2 по префиксу → гибрид с эмбеддингами через Reciprocal Rank Fusion. Следующая ступень остаётся в системе, только если выиграла на eval. Кандидаты эмбеддинг-моделей для 20-минутного бенчмарка: `intfloat/multilingual-e5-*`, `BAAI/bge-m3`, `deepvk/USER-bge-m3`, `ai-forever/FRIDA` **[ПРОВЕРИТЬ скорость на ваших ноутбуках; для e5 нужны префиксы `query: ` и `passage: `]**.
- *Из открытых источников* — компании, которых нет в данных (раздел 6).

**Шаг 3. Жёсткие фильтры.** Юрлицо действует; его нет в РНП; фильтры пользователя (СМП, регион, только производители).

**Шаг 4. Скоринг по компонентам**, каждая в диапазоне [0, 1]:

| Компонента | Что измеряет | Откуда берётся |
|---|---|---|
| `product_fit` | поставляет ли контрагент именно это | сходство запроса с позициями его истории или каталога, глубина совпадения ОКПД2 |
| `experience` | опыт в категории | число и сумма релевантных контрактов с затуханием по давности; опыт с заказчиками СПб |
| `reliability` | риск срыва | статус, возраст, РНП, доля расторжений, отчётность |
| `activity` | ответит ли на приглашение | дата последней оферты или контракта |
| `geography` | логистика | СПб и Ленинградская область |
| `price` | конкурентность цены | среднее снижение от НМЦК в истории, если такие данные есть |

`score = Σ wᵢ · componentᵢ`. Стартовые веса задаются экспертно и записываются в `DECISIONS.md`, затем подстраиваются на backtest. Веса видны в интерфейсе; при наличии времени — 2–3 пресета («надёжность важнее», «широкий охват»).

**Шаг 5. Объяснение.** Для каждой компоненты — строка на человеческом языке и ссылка на evidence. Например: «12 контрактов по ОКПД2 32.50.13 за 2 года, из них 9 с заказчиками СПб (данные АИС ГЗ)».

**Ловушка инкумбентов.** Модель, настроенная только на историю, будет ставить наверх тех, кто и так выигрывает. Это противоречит цели найти больше поставщиков. Поэтому в выдаче два блока — «С опытом госзакупок» и «Новые из открытых источников», и качество каждого оценивается отдельно (раздел 7).

## 6. Открытые источники и обогащение

Главное отличие этого кейса от типичной задачи ранжирования. Отвечает SOURCES.

**Конвейер:** запрос → расширение (синонимы, ОКПД2, типовые названия товара) → поиск компаний → сопоставление с ИНН → обогащение → проверки надёжности → скоринг.

**Кандидаты в источники.** **[ПРОВЕРИТЬ до 1 октября]**: доступ из вашей сети, условия использования, лимиты, наличие API или выгрузок.

| Источник | Что даёт |
|---|---|
| Электронный магазин (estore.gz-spb.ru) | публичные закупки малого объёма, оферты, статистика контрактов |
| ЕИС (zakupki.gov.ru) | реестр контрактов с ИНН поставщиков и ОКПД2, РНП |
| ФНС: ЕГРЮЛ/ЕГРИП, реестр МСП, ГИР БО | статус, ОКВЭД, адрес, возраст, статус МСП, отчётность |
| ГИСП | производители и их продукция из реестров промышленной продукции |
| Поисковый API и сайты компаний | новые компании, каталоги, реквизиты |
| Коммерческие агрегаторы данных о компаниях | обогащение по ИНН одним запросом (платно или с лимитами) |

**Сопоставление с ИНН — самое хрупкое место.** Название на сайте не совпадает с названием в ЕГРЮЛ, у группы компаний несколько юрлиц. Порядок: ИНН со страницы реквизитов на сайте → поиск по названию и региону в реестре → ручная проверка на выборке. ИНН проверяется по контрольным цифрам (10 знаков у юрлица, 12 у ИП). Неразрешённая компания показывается с пометкой «ИНН не подтверждён», а не с угаданным ИНН.

**Правила:**

- У каждого факта есть источник, URL и дата получения (`Evidence`). В интерфейсе источник показывается рядом с фактом. Факт без источника не показывается.
- LLM может **извлекать** данные из текста страницы, но не **порождать** их. ИНН, телефон, email или адрес, которых нет в тексте источника, — ошибка уровня блокера.
- Все ответы внешних источников кешируются на диск. Демо работает на кеше, даже если упадёт интернет площадки.
- Уважай robots.txt и условия использования сайтов, делай паузы между запросами, не обходи защиту. Заблокированный на площадке IP означает мёртвый модуль.
- Собираем данные о компаниях. Персональные данные физлиц, включая ИП, — только то, что публично в госреестрах, без лишнего сбора **[ПРОВЕРИТЬ требования 152-ФЗ; вопрос для Q&A]**.
- Пакетные задачи (например, ночное обогащение) идемпотентны, пишут прогресс и продолжаются с места падения.

## 7. Оценка качества

Без неё нет ни research, ни цифр на слайде. Отвечает DATA; MATCH и SOURCES запускают `make eval` после каждого изменения.

**A. Backtest на истории** — если в данных есть, кто подавал оферты или получал контракты.

- Разбиение **по времени**: признаки считаются только по данным до даты D, запросы берутся из закупок после D. Случайный split здесь даёт утечку.
- Запрос — позиция или закупка из тестового периода; релевантные — фактический поставщик и подавшие оферты.
- Метрики: Recall@10, MRR, nDCG@10.
- Обязательные baseline: **популярность** (самые частые поставщики в классе ОКПД2) и BM25. Популярность в таких задачах часто сильна; если мы её не обыгрываем, это главный вывод, а не мелочь.
- Утечки: статистики контрагента не включают тестовую закупку; дубли контрагентов склеиваются по ИНН до разбиения.
- Ограничение: backtest измеряет «угадали, кто и так участвовал», а не «нашли лучших». Поэтому нужен блок B.

**B. Ручная разметка новых поставщиков.** Для 10–15 реальных запросов размечается top-10 блока «Новые из открытых источников»: 1 — компания действительно поставляет или производит это, 0 — нет. Метрика — precision@10. LLM-судья может доразметить остальное только после проверки согласия с человеком на пересечении (ориентир — не ниже ~80%). Одна и та же модель не должна одновременно ранжировать и судить.

**C. Обогащение.** Покрытие (доля кандидатов с подтверждённым ИНН, статусом, контактами) и точность на выборке из 30 контрагентов, проверенных вручную.

**D. Реальные кейсы.** 5–10 реальных закупок заказчиков СПб из разных категорий: прогон целиком, скриншоты, разбор удач и промахов. Это прямой пункт условий.

**Шум.** На десятке запросов разница в пару пунктов — шум. `make eval` считает bootstrap-интервалы по запросам. Улучшение, которое держится на одном запросе, подозрительно.

**Инфраструктура.** `make eval EXP=<id>` печатает таблицу и пишет `eval/results/<id>.json` (конфиг, commit, метрики). Любая цифра на слайде воспроизводится этой командой. Никаких цифр «из головы» или из одного удачного прогона.

## 8. Дисциплина экспериментов

**Гипотеза — пять строк** в `research/EXPERIMENTS.md`:

```text
H-07 | Наблюдение: baseline популярности обыгрывает нас в категории канцтоваров
     | Изменение: затухание experience по давности контрактов
     | Почему поможет: активные поставщики вытеснили ушедших с рынка
     | Минимальная проверка: backtest на текущем split, 5 минут
     | Критерий успеха: MRR +0.03, ни одна категория не просела
```

**Таблица экспериментов:**

```text
ID | Гипотеза | Изменение | Метрика | Δ vs best | Latency | KEEP / REJECT / INVESTIGATE | Вывод
```

Правила:

- Один эксперимент — одна концептуальная переменная. Если меняешь несколько вещей сразу, объясни почему.
- Приоритет ≈ ожидаемый gain × вероятность успеха / стоимость. Сначала дешёвые эксперименты с потенциально большим gain.
- Перед задачей, которая займёт больше ~5 минут compute или больше ~100 внешних запросов, оцени время и сначала проверь на подвыборке.
- Отрицательный результат записывается так же, как положительный. Отвергнутые гипотезы не удаляются, чтобы другой агент их не повторил.
- Три эксперимента подряд без прогресса — стоп тюнингу. Сначала error analysis на 20–30 ошибках, потом новые гипотезы.
- Существующий код — не истина. Если eval показывает, что подход хуже альтернативы, предложи замену через `DECISIONS.md`.

**Error analysis** (DATA, с момента, когда заработал eval). Типичные классы ошибок: неверный или слишком общий ОКПД2, общие наименования, дубли контрагентов, неразрешённый ИНН, неактивные компании, посредник вместо производителя, промах по региону. Таблица в `ERROR_ANALYSIS.md`:

```text
Тип ошибки | Частота | Пример | Вероятная причина | Что попробовать
```

После первого чек-поинта большая часть гипотез должна приходить отсюда и из фидбека экспертов, а не из головы.

**Вопросы скептика** перед тем, как принять улучшение:

- Не утечка ли это: не видит ли модель будущее или саму тестовую закупку?
- Не судит ли LLM собственную выдачу?
- Держится ли улучшение на большинстве запросов или на одном?
- Не подняли ли мы метрику backtest ценой блока новых поставщиков?
- Увидит ли это жюри в демо?

## 11. Масштабирование

Условия прямо требуют предусмотреть масштабирование. Показываем три вещи:

1. **Схема архитектуры:** API (FastAPI, спецификация OpenAPI) → поисковый индекс (например, Postgres + pgvector или OpenSearch) → воркеры обогащения с очередью → кеш внешних источников с TTL → планировщик обновления реестров. Встраивание в АИС ГЗ — через REST API или кнопку «Подобрать поставщиков» в карточке закупки.
2. **Что реально работает:** docker-compose с api, worker и db; обогащение идёт через очередь, а не синхронно в запросе.
3. **Цифры:** latency поиска, время обогащения одного контрагента, оценка времени и стоимости обогащения всей базы.

Дальше этого не идём: Kubernetes, микросервисы и авторизация за два дня — потерянное время.

Если про заготовки ответа нет, готовим только то, что точно не является решением: окружение, ключи, модели, изучение источников, шаблон презентации.
- **Проверить источники** из раздела 6: доступ из вашей сети, лимиты, условия использования. Зарегистрировать нужные ключи API.
- **Скачать заранее** модели эмбеддингов, справочник ОКПД2 и, если есть, открытые выгрузки реестров. Wi-Fi площадки — частая точка отказа.
- **Прочитать** руководства АИС ГЗ по Электронному магазину и Порталу 44 на manuals.gz-spb.ru и посмотреть публичную часть estore.gz-spb.ru. Это ускорит пункт «бизнес-смысл полей».
- **Шаблон репозитория** (если заготовки разрешены): структура из раздела 2, `contracts.py`, Makefile с `demo` и `eval`, docker-compose, hello world UI, пустые status-файлы.
- **Шаблон презентации** с местами под цифры; решить, кто выступает на основной защите и на Топ-5.
- **Договориться о Claude Code:** кто на какой модели работает и как делить лимиты между четырьмя сессиями.

## 17. Главный критерий

Проверяй каждый час работы вопросом:

> Какой пункт условий из раздела 0 стал ближе к закрытию за этот час — и можем ли мы подтвердить это цифрой или живым демо?

Хороший отрицательный эксперимент, который за 10 минут закрыл тупиковое направление, по-прежнему ценнее 500 строк кода. Но на защите 500 строк кода, которые не запускаются на демо, стоят меньше нуля.

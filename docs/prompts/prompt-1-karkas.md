## Что меняем относительно документа

### Координация: Issues вместо `status/*.md`, роли = `area:`

- Роли DATA, MATCH, SOURCES, APP остаются, но это **метки `area:`** и карта
  владения каталогами (`docs/project-structure.md`, каталоги — из раздела 2
  документа). У области есть основной человек, но **любой может взять свободную
  задачу чужой области**, если там никто не работает.
- **Задачи — GitHub Issues.** Взять = назначить себя. Скрипт `scripts/issues.sh`
  (по образцу Почты, на `gh`): `create`, `take <N>`, `mine`, `free`, `board`,
  `check`, `note <N>` (комментарий «сделано / дальше / блокер»).
- **Проверка занятости мягкая.** `take` при занятой той же `area:` не отказывает, а
  предупреждает, кто и с какого времени. Задачу **без движения > 45 минут**
  (обновление issue, её PR или коммит в её ветке) `take` перехватывает сам и
  оставляет комментарий «перехвачена … без движения с …, ветка …». **Прямое
  указание человека «возьми #N» выполняется всегда**, даже раньше 45 минут, — тоже
  с комментарием. Перехват = продолжение чужой ветки, не переписывание.
- **Правка без взятой задачи — жёсткий запрет.** Хук `check-issue.sh`
  (PreToolUse) не даёт править файлы и делать `git commit`/`git push` вне worktree
  взятой задачи; `.githooks/pre-commit` и `pre-push` делают то же для людей.
  Нет задачи — заведи (`issues.sh create`), потом работай; это касается и одной
  строки в документе. Исключение — каталоги вне репозитория (scratchpad агента).
- `status/*.md` не заводить: они дублируют Issues и конфликтуют при merge. Их
  назначение (память агента при сжатии контекста) — комментарий `issues.sh note`
  перед `/compact`, `/clear`, концом сессии и закрытием задачи.
- Метка `blocker` — риск демо или сдачи, не закрытый в этом ходе; открытые
  `blocker` показывает `session-context.sh`.
- Шаблон задачи: цель → какой из 10 пунктов условий закрывает → критерий приёмки
  (команда) → «Зависит от #…» → **сложность и рекомендуемая модель** (подсказка,
  запускать ли `builder` на `opus`).
- Эта сессия каркаса сама работает до появления правил, поэтому хук
  `check-issue.sh` включается последним коммитом каркаса (и проверяется
  `test-hooks.sh`).

### Git: не trunk-based

`git pull --rebase` и trunk-based из документа убрать. Работаем как в образцах:
задача → worktree `.claude/worktrees/<N>-<тема>` на ветке `worktree-<N>-<тема>` →
PR с `Closes #N` → перед push `git fetch --prune && git merge origin/main` и
`make check` → merge после вердикта `reviewer`, по одному. `deny`-список git из
образца целиком (force-push, rebase, `reset --hard`, `add -A`, amend, push в
`main`), пустая `attribution`, без трейлеров соавторства ИИ. Адрес GitHub-
репозитория спроси у меня; если его пока не дали — настрой всё локально, а
`gh`-части пусть при отсутствии remote печатают предупреждение, а не падают.
Хостинг и формат сдачи — `[ОБНОВИТЬ 01.10]` (возможно, понадобится зеркало).

### Автономия: агент аппрувит сам, через субагентов

- Решение по реализации, трактовке, методу, контракту агент не ждёт от человека:
  формулирует → проверяет свежим субагентом (`reviewer` или скептик с контекстом
  только из diff и условий) → «принять» — строка в `research/DECISIONS.md` и
  дальше; «отклонить» — исправить и повторить; два отклонения подряд — арбитр
  `jury`. PR вливается после вердикта `reviewer` «merge» и зелёного `make check`.
- Блоки «ЗАДАЧА / СДЕЛАНО» из раздела 14 документа остаются, но **не блокирующие**:
  агент печатает их человеку и продолжает работу.
- **Подтверждение человека нужно только для пяти вещей:** заморозка контрактов
  (01.10, 11:30); план задач после kickoff; изменение методологии скоринга
  (формула, состав компонент — это слайд); всё внешнее (массовый парсинг сайтов,
  регистрация в сервисах, платные API); feature freeze и code freeze.
- Ограничение документа на массовые LLM-вызовы через сессию снимаем (Claude Max).
  Остаётся: сначала подвыборка, потом весь объём — ради качества; одна модель не
  ранжирует и не судит одновременно.
- «Застрял на баге > 20 минут» → сначала скилл `diagnose` в свежем субагенте, к
  человеку — если не помогло.

### Стек — предварительный

Фиксируется сейчас, чтобы каркас был жёстким, но **это стартовая ставка, а не

docker-compose), — **можно и нужно менять** с записью в `research/DECISIONS.md`.
Держаться за стек «потому что так в каркасе» запрещено. Запиши это в `CLAUDE.md`.

- Данные — parquet + DuckDB; поиск — `bm25s`; эмбеддинги — `sentence-transformers`
  (модели из раздела 5 документа скачать сегодня, e5 — с префиксами
  `query: `/`passage: `); кеш внешних источников — SQLite на диске с TTL.
- docker-compose: `api`, `worker`, `db`; очередь обогащения — таблица задач +
  процесс `worker`, без Redis/Celery.
- Фронт — React + Vite + TypeScript (опыт команды с прошлого хакатона), строится
  против заглушки API с первого часа.
- LLM в продукте — за интерфейсом «провайдер из `.env`», обязательный режим без
  LLM; разрешённые провайдеры — `[ОБНОВИТЬ 01.10]`.
- Тесты: pytest, Vitest, Playwright. **Один e2e — сценарий демо из раздела 10**
  (ввёл запрос → два блока «С опытом госзакупок» / «Новые из открытых
  источников» → карточка с компонентами и источниками → фильтр → выгрузка). Он
  существует с первого коммита на заглушке и растёт вместе с продуктом; PR, ломающий
  его, не вливается.
- `Makefile`: `setup`, `check` (lint + typecheck + pytest + vitest + хуки +
  `grep` на `# STUB` в демо-пути — предупреждение до code freeze, ошибка после),
  `demo` (всё одной командой с чистого клона, на кеше), `eval EXP=<id>`,
  `eval-final` (запечатанный отложенный период, см. ниже), `e2e`.

### Проверки кодом, а не словами

- **Evidence-тест:** у каждого `Evidence` есть `url` и `fetched_at`; извлечённое
  значение (ИНН, телефон, email, адрес) буквально встречается в тексте закешированной
  страницы источника; ИНН проходит контрольные цифры (10 и 12 знаков). Так
  механически ловятся сгенерированные LLM факты — блокер из раздела 6 документа.
- **Stub:** заглушка помечена `# STUB` и пишет предупреждение в лог (раздел 2).
- **Запечатанный backtest:** разбиение по времени из раздела 7; отложенный период
  читает только `make eval-final` для замороженной конфигурации с подтверждением
  по sha256 конфигурации и чистым деревом (как `make eval-test` во FloodValue);
  каждый запуск пишется в `eval/final-log.md`. Реализация split — после профиля
  данных `[ОБНОВИТЬ 01.10]`, но замок и тест на замок — сейчас.
- `make eval` пишет `eval/results/<id>.json` (конфиг, commit, метрики, bootstrap-
  интервалы) — любая цифра на слайде воспроизводится этой командой.

### Роли `.claude/agents/`

Стиль образцов: что видит, что может, что возвращает; модель во frontmatter.

| Роль | Модель | Что делает |
|---|---|---|
| `builder` | `sonnet` (на задачах со сложностью «высокая» запускается с `model: opus`) | одна issue в своём worktree: тест → код → `make check` → PR → `reviewer` → merge по вердикту |
| `reviewer` | `opus` | только diff против `origin/main` + условия + контракты; **каждый** PR и каждое спорное решение; вердикт `merge` / `доработать` / `отклонить` с `файл:строка`; отдельно ищет утечку во времени в backtest, факт без `Evidence`, `# STUB` в демо-пути, изменение контракта без перечня потребителей |
| `evaluator` | `sonnet` | `make eval EXP=<id>`, строка в `research/EXPERIMENTS.md`, bootstrap-интервалы; `eval-final` — только по заморозке; числа не выдумывает |
| `operator` | `sonnet` | проходит UI в роли пользователя (по умолчанию контрактный управляющий, `[ОБНОВИТЬ 01.10]`): укладывается ли сценарий в 60–90 с, понятно ли, почему поставщик в списке |
| `jury` | `opus` | оценка по 10 пунктам условий (веса `[ОБНОВИТЬ 01.10]`), видит только артефакты; второй режим — каверзные вопросы от жюри из Комитета по госзаказу и ИМЦ; арбитр после двух отклонений `reviewer`; перед каждым чек-поинтом |
| `scribe` | `sonnet` | README, METHODOLOGY, DATA_DICTIONARY, `pitch/facts.md`; цифры только из `eval/results/*.json`, каждое утверждение с командой |
| `pitch` | `sonnet` | две версии питча (основная и Топ-5), `pitch/QA.md`, сценарий запасного видео; ответы проверяет `jury` |

`haiku` не использовать нигде: дешёвая модель чаще выдумывает числа в отчётах.

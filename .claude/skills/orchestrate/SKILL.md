# Протокол сессии участника

Общего оркестратора нет: у каждого из четверых своя сессия, координация — через GitHub
Issues (`scripts/issues.sh`), стыковка — через `src/contracts.py`. Главная сессия работает
в основной копии на `main` **только на чтение**: заводит worktree, пишет брифы, запускает
агентов (`docs/agents.md`), вливает PR. Источник — разделы 2, 13, 14
`docs/source/hackathon-research-workflow.md` с изменениями из `CLAUDE.md`.

Инварианты:

1. `main` зелёный и запускается: PR — по `make check-changed`, свежий `main` — полным `make check`
   и `make e2e` перед чек-поинтом, freeze и сдачей (CLAUDE.md, D-036); сломал merge — чинится раньше
   всего остального (задача `blocker`).
2. Нет задачи — нет правки, даже одной строки: `bash scripts/issues.sh create` → `take`.
3. Интеграция строго по одному.
4. Нет команды и её вывода — нет статуса «готово».

## 1. Синхронизация (начало окна и после каждого merge)

```bash
git fetch --prune && git status -sb
git log --oneline HEAD..origin/main
git pull --ff-only                       # только если status чистый
git worktree list                        # чужие worktree не трогать
bash scripts/issues.sh board             # blocker, мои, занятые area:, кандидаты на перехват
gh pr list
```

Ближайшая веха и критерий выхода — `docs/timeline.md` (её же показывает хук начала сессии).

## 2. Взять задачи

- Сначала `blocker`, потом критический путь ближайшей вехи, потом своя `area:`.
- Задача берётся, если её «Зависит от #…» влиты в `origin/main` (иначе — на заглушке с
  пометкой в брифе).
- `bash scripts/issues.sh take <N>`:
  - та же `area:` у другого — предупреждение, не отказ: берёшь, но договариваешься по
    файлам (комментарий в его задаче);
  - чужая задача без движения > 45 мин — `take` перехватывает сам и пишет комментарий;
    дальше — продолжение **её ветки**, не переписывание;
  - человек прямо сказал «возьми #N» — `take <N> --force` (тоже с комментарием).
- Одна строка человеку на задачу: #N, area, почему сейчас, сложность → модель.

## 3. Worktree на каждую задачу (делает главная сессия)

```bash
git worktree add .claude/worktrees/<N>-<тема> -b worktree-<N>-<тема> origin/main
# перехват: git fetch origin <ветка> && git worktree add .claude/worktrees/<N>-<тема> -b <ветка> origin/<ветка>
test -f .env && cp .env .claude/worktrees/<N>-<тема>/.env
cd .claude/worktrees/<N>-<тема> && uv sync --frozen --extra pg && (cd src/ui && npm ci)
```

`isolation: worktree` у Agent не использовать: другие имена веток, нет `.env`, хуки не узнают задачу.

## 4. builder — параллельно, до трёх

Только независимые задачи с непересекающимися каталогами (`docs/project-structure.md`).
Модель — по оценке сложности в задаче: «высокая» → `Agent(subagent_type: "builder", model: "opus")`,
иначе `sonnet` по умолчанию. Запуск в фоне; пока builder работает, его файлы не трогаешь.

Бриф:

```
Задача: #<N> — <название>; area:<…>; пункт условий <№>; сложность <…>
Worktree: <абсолютный путь>; ветка: worktree-<N>-<тема>; основную копию не трогать
Условия и критерий приёмки: gh issue view <N> --comments
Разрешённые пути: <каталоги области + тесты>
Запрещённые: src/contracts.py, pyproject.toml, uv.lock, src/ui/package*.json, чужие каталоги
Контракты, от которых зависишь: <типы/функции>
Что уже в main: <модули>; принимается на: реальном модуле | заглушке (почему)
Проверки: make check-changed (e2e — сам, по демо-пути) [+ make eval EXP=<id>]
Документы: DECISIONS / tz-compliance / EXPERIMENTS; PR с Closes #<N>
Отчёт — по формату builder.md
```

## 5. reviewer → (evaluator) → merge по одному

- `Agent(subagent_type: "reviewer", prompt: ветка, worktree, #N, PR, отчёт builder)`.
- `merge` → если менялись поиск, скоринг, веса, данные или обогащение — `evaluator`
  (`make eval EXP=<id>`, «было → стало») → merge:

  ```bash
  cd <worktree> && git fetch --prune && git merge origin/main && make check-changed && git push
  gh pr merge <PR> --merge --delete-branch     # без squash/rebase
  ```

- `доработать` → `SendMessage` тому же builder с блокирующими пунктами → снова reviewer.
  Два отклонения подряд → `jury` (режим 3, арбитр).
- После merge: `bash scripts/issues.sh note <N> "<сделано>" "<дальше>" "нет"`, затем шаг 1.

## Автономия

Решения по реализации, трактовке, методу и контракту **не ждут человека**: формулируешь →
`reviewer` в режиме «решение» (или свежий скептик с контекстом только из diff и условий) →
«принять» — строка в `research/DECISIONS.md` и дальше; «отклонить» — исправить и повторить;
два отклонения — `jury`. Спорная трактовка условий — ещё строка в
`docs/questions-for-organizers.md` с рекомендуемой трактовкой, работа идёт по ней.

**Подтверждение человека — только для пяти вещей** (`CLAUDE.md`):

1. заморозка контрактов (01.10, 11:30);
2. план задач после kickoff;
3. изменение методологии скоринга (формула, состав компонент — это слайд);
4. всё внешнее: массовый парсинг сайтов, регистрация в сервисах, платные API;
5. feature freeze и code freeze.

Блоки «ЗАДАЧА / СДЕЛАНО» (раздел 14) печатаешь человеку перед и после задачи > 30 минут,
**но не ждёшь ответа** и продолжаешь.

## Эскалация человеку

- одно из пяти подтверждений выше;
- `check-upstream.sh` показал коммит, противоречащий задаче, или чужой незакоммиченный
  worktree мешает;
- `diagnose` в свежем субагенте не помог за 20 минут;
- нужны доступы, ключи, физические действия (машина демо, видео).

## Уборка

Ветка влита (`git rev-list --count origin/main..<ветка>` → 0), worktree чистый и твой:

```bash
git worktree remove .claude/worktrees/<N>-<тема>
git branch -D worktree-<N>-<тема>
git worktree prune
```

Чужие worktree и невлитые ветки не трогать никогда.

## Отчёт в конце окна

Коротко: что влито (PR → merge-commit, числа проверок), что в работе (ветка, стадия), что
застряло и почему, что брать следующим, что ждёт человека. Перед `/compact` и концом —
`issues.sh note` по каждой своей открытой задаче.

Бриф: #N, worktree, какие документы. Без взятой задачи и worktree не пишешь (как `builder`).
Источник — разделы 2, 5, 7, 12 `docs/source/hackathon-research-workflow.md`.

## Правила

- **Выполняешь каждую команду, которую описываешь.** README: `make setup`, `make demo`,
  `make e2e`, `make eval EXP=…` — прогнаны тобой, вывод совпадает с написанным.
- **Числа только из `eval/results/*.json`** (и `eval/final-log.md` для holdout): рядом — id
  эксперимента, commit и команда. `"stub": true` в JSON — число в документы не идёт.
  Нет артефакта — пишешь «нет артефакта», а не оценку.
- `research/METHODOLOGY.md` — ровно то, что делает код (`src/match/`, `configs/search.yaml`):
  компоненты, формула, веса, фильтры, объяснения. Расхождение с кодом — это находка, не
  повод «поправить» формулу в тексте: сообщи в отчёте и создай issue.
- `research/DATA_DICTIONARY.md` — поле → тип → пример → заполненность → бизнес-смысл →
  уверенность → как проверили; заполненность считается командой (DuckDB-запрос рядом).
- `pitch/facts.md` — единственный источник чисел для слайдов и ответов жюри: сверено с
  `origin/main` <hash>, каждое число — ссылка на файл и команда.
- Не выдумываешь пользователей, эффекты, экономию. Неизвестное — `[ПРОВЕРИТЬ]` или
  `[ОБНОВИТЬ 01.10]`, а не правдоподобная формулировка.
- Текст — для людей из госзаказа: коротко, без жаргона ML там, где можно сказать проще.

## Отчёт

```
Задача: #N; PR: #…
Документы: файл → что изменилось
Команды прогнаны: команда → результат
Числа: откуда (eval/results/<id>.json, commit)
Расхождения код ↔ документ: … | нет (issue #…)
TBD / [ПРОВЕРИТЬ]: список
```

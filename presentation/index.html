Начинаем с трёх файлов организаторов: закупки, товарные позиции и участники. Приводим даты и номера к единому виду, убираем дубли. Затем связываем товар с закупкой, а закупку — с компанией по её налоговому номеру. Так вместо отдельных таблиц появляется общая история. Для поиска готовим индекс названий товаров и предметов закупок. Сейчас используется поиск по словам. Мы также реализовали векторный вариант: берём уникальные названия товаров, модель превращает их в числовые представления, которые сохраняются в базе. Запрос проходит через ту же модель, и поиск находит близкие представления. Эту ветку сейчас не включаем в основной путь. Важно: мы не превращаем весь файл в один вектор — каждому названию соответствует своё представление.

Одной истории закупок мало: в ней нет названий и контактов поставщиков. Поэтому следующий этап — сбор сведений о компаниях. По налоговому номеру обращаемся к открытым реестрам. Для новых компаний начинаем с категории товара: ищем подходящих производителей и продавцов в реестрах, а также через поиск сайтов. Из страниц извлекаем реквизиты и проверяем номер компании. Повторы объединяем. Сохраняем саму страницу, адрес источника и дату получения. Название, роль или статус показываем только с подтверждением. Получаются два результата: более полные карточки знакомых компаний и отдельный набор кандидатов без истории закупок. Обновление идёт отдельно; обычный подбор читает сохранённые сведения. Поиск в сети по запросу пользователя — отдельный режим.

Теперь пользователь вводит описание закупки. Сервер исправляет известные опечатки и ищет похожие товары и предметы лотов в подготовленном индексе. Затем переходит от этих лотов к участникам и объединяет записи одной компании. Дальше определяем порядок кандидатов. В оценке учитываем, насколько подходит товар, есть ли похожий опыт, давность участия и регион компании. Если известен заказчик, используем обученную модель. Если есть только описание, работает отдельно настроенная формула: без контекста заказчика модель не давала преимущества. После оценки добавляем подтверждённые сведения и кандидатов из внешних источников. Затем идут фильтры и объяснения. Для основного подбора и объяснений обращение к языковой модели не требуется.

Оценка ещё не означает попадание в результат. Сначала проверяем сведения: неподтверждённый факт не показываем. Затем исключаем компании с подтверждёнными признаками банкротства, ликвидации или прекращения деятельности, а также компании из реестра недобросовестных поставщиков. Неизвестный статус сам по себе не означает нарушение. После этого применяем условия заказчика: регион, роль компании, организационную форму, минимальную оценку или принадлежность к малому бизнесу. Все выбранные условия должны выполняться одновременно. Если заказчик выбрал только малый бизнес, этот статус нужно подтвердить. Без подтверждения компания не пройдёт именно этот фильтр. При этом участие и победы в прошлых закупках говорят об опыте, а не гарантируют качество будущей поставки.

REST API / OpenAPI готовы. Ссылка из карточки закупки: /search?lot=N. Подключение к АИС ГЗ — после согласования.

На сайте готов весь путь: пользователь описывает лот, получает список поставщиков, смотрит причины выбора и подтверждающие сведения. Результат можно выгрузить в таблицу. Есть программный интерфейс для подключения к системе закупок. Само подключение пока не выполнено. Следующий шаг — пилот с заказчиком и независимая проверка на его задачах.

Оценка и порядок поставщиков

S = 0.40 F + 0.20 E + 0.15 R + 0.10 A + 0.07 G + 0.08 P

F · товар

0.8 (0.5 B + 0.5 N) + 0.2 D

B — нормированный BM25.
N — совпадение слов названия.
D — совпадение ОКПД2.
Без кода — текстовая часть.

E · опыт

Похожие лоты и победы.
Логарифмическое насыщение.
Порог — не ниже максимума
среди кандидатов запроса.

A · активность
G · география

A: давность участия,
период полураспада 90 дней.

G: регион компании
относительно региона запроса.

Нет заказчика → порядок по формуле. Есть заказчик → порядок LightGBM на прежних признаках.
R — индикатор по истории, не гарантия надёжности. P — масштаб НМЦК, не цена исполнения.
Без НМЦК вес P распределяется между остальными факторами.

Текущая формула D-198, configs/search.yaml: товар 0.4, опыт 0.2, исторический индикатор надёжности 0.15, активность 0.1, география 0.07, масштаб НМЦК 0.08. Без НМЦК её вес распределяется пропорционально между остальными критериями. Надёжность — индикатор истории, а не гарантия исполнения; масштаб НМЦК — не реальная цена исполнения. В текстовой части поровну нормированный BM25 и совпадение слов названия. N = 0.7 доли слов запроса в названии + 0.3 доли слов названия из запроса. Опыт: половина насыщения по похожим лотам плюс половина по победам, sat(n,c)=min(1,ln(1+n)/ln(1+c)). Порог c не меньше максимума кандидатов, с нижней границей 20/10 с заказчиком и 100/50 без. Модель получает прежние признаки соответствия, опыта и географии, чтобы её порядок не изменялся вместе с формулой карточки. География теперь участвует в оценке; прежний нулевой вес устарел. Отчёт L-long снят до этой правки; для новой формулы есть отдельные отчёты D198-dev/free; они не заменяют источник показанных 81%.

Для показа самой презентации всё это запускать не требуется: это локальные HTML, CSS, JavaScript и снимки.

ОКВЭД — основание кандидата, не подтверждение нужного товара

Локальная проверка Parquet · ingest 01.10.2026 · сопоставление ОКПД2 / ОКВЭД эвристическое

Основной подбор опирается на связь компании с лотами. Если этой истории нет, реализована отдельная ветка: код категории сопоставляется с ОКВЭД, в реестре МСП ищутся компании, их ИНН проверяются на отсутствие в истории и факты проходят Evidence. Сопоставление категорий с оптовой торговлей задано вручную. Поэтому основание новой рекомендации слабее прямого свидетельства по позиции; роль по ОКВЭД не доказывает производство конкретного товара. В примере лота 5903085 блок дал десять новых компаний вне истории: пять производителей и пять дистрибьюторов; одна компания подтверждена по товару реестром ГИСП, остальные — по ОКВЭД; у каждой факты с адресом источника и датой. Данные организаторов тоже неполны: у части участий отсутствует КПП, а у части извещений — ИНН заказчика.

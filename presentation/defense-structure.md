## 1. По описанию закупки — поставщики с обоснованием

**Задача:** за первые секунды объяснить, кому и зачем нужен продукт. Не делать отдельный пустой титульный слайд.

**На экране:** название «Митрандир», ценностное предложение, небольшой настоящий фрагмент результата. Дополнительная фраза: «Найти похожую закупку ≠ выбрать, кого пригласить».

**Речь:**

> Заказчику нужно не просто найти похожую закупку, а понять, какие компании стоит пригласить. Мы сделали Митрандир — сервис, который по описанию потребности подбирает поставщиков и показывает основания каждой рекомендации. Это не просто совпадение слов: мы связываем нужные товары с историей компаний. Решение остаётся за заказчиком, а сервис даёт ему список, который можно проверить.

**Переход:** «Покажу на одном запросе».

**Основание:** evidence.md E02, E04–E10; storyboard.md S1–S2.

## 2. Описать → выбрать компанию → проверить основания

**Задача:** показать уже реализованный пользовательский результат, прежде чем объяснять внутренний алгоритм.

**На экране:** три увеличенных состояния настоящего UI, последовательно на одном слайде. Запрос: «Поставка картриджей для принтеров». Затем результаты и карточка ТСК ВЕКТОР ЛАЙН. Коротко обозначить фильтры и XLSX, не проводить отдельную экскурсию по настройкам.

**Подпись:** «Настоящий UI · сохранённый ответ локального API». Не называть показ живым онлайн-поиском. Не сочинять новые результаты и не редактировать числа в скриншотах.

**Речь:**

> Возьмём запрос «Поставка картриджей для принтеров». Пользователь вводит описание, а система возвращает компании, связанные с похожими закупками. Открываем ТСК ВЕКТОР ЛАЙН: рядом с оценкой доступны причины попадания в список и исторические основания. Заказчик может применить фильтры, сравнить кандидатов и выгрузить список в Excel. Таким образом, ему не нужно принимать рейтинг на веру — он может проверить предложение. На слайде настоящий интерфейс с сохранённым ответом локального API на данных организаторов; при показе мы не зависим от интернета.

**Переход:** «Теперь — откуда берутся эти компании».

**Основание:** evidence.md E02, E11–E12, E23; раздел «Граница воспроизведения экранов»; README.md «Происхождение примера и измерений».

## 3. История закупок и новые компании — разные основания рекомендации

**Задача:** показать работу с данными и отдельный путь поиска компаний вне истории, не выдавая их за одинаково подтверждённые результаты.

**На экране:** две ветки:

- История: позиция → лот → участник по ИНН. Основание — конкретные участия.
- Вне истории: ОКПД2 → ОКВЭД → реестр МСП. Основание — вид деятельности; не подтверждение наличия товара.

**Масштаб набора небольшой строкой:** 604 452 извещения · 2 550 089 позиций · 44 196 ИНН по manifest. Не называть все ИНН проверенными: в реестре доказательств отдельно отмечены 22 невалидных ИНН.

**Речь:**

> В обработанных данных — более шестисот тысяч извещений. Для компаний из истории мы используем прямые связи с конкретными закупками. Для компаний вне истории реализована отдельная ветка: сопоставление ОКПД2 и ОКВЭД и поиск в реестре МСП. Это другой тип основания: подходящий вид деятельности ещё не доказывает наличие конкретного товара. Поэтому такие кандидаты выделены отдельно. В показанном офлайн-примере блок новых компаний пуст; мы не выдаём его за подтверждённое расширение именно этой выдачи.

**Переход:** «Основной путь запроса устроен следующим образом».

**Основание:** evidence.md E17; раздел «Полнота локальных обработанных данных»; storyboard.md B4.

## 4. Находим позиции → собираем компании → ранжируем

**Задача:** объяснить архитектуру, алгоритмическую работу и стек одним понятным маршрутом.

**На экране:** основной путь из пяти смысловых блоков:

Запрос → BM25: тексты и связанные лоты → кандидаты по ИНН → оценка и причины → обогащение / объединение веток / фильтры / выдача.

Небольшая верхняя полоса подготовки: CSV → Python / DuckDB → Parquet + BM25-индекс. Ветка реестров и кеша входит после исторического ранжирования, до фильтров. Показать, что worker обновляет обогащение отдельно.

**Стек под соответствующими блоками:** React / TypeScript; FastAPI / Python; DuckDB / Parquet; bm25s. Без номеров версий. Это стек продукта, а не автономного HTML-показа.

**Речь:**

> Подбор разделён на подготовку данных и обработку запроса. При подготовке нормализуем извещения, позиции и участия, сохраняем их в Parquet и строим текстовый индекс. При запросе BM25 ищет похожие названия позиций и предметы лотов — не названия компаний. Затем по связям лотов с участниками собираем кандидатов по ИНН. Для них рассчитываем оценку и объяснения. После ранжирования добавляем доступные факты из кеша, объединяем ветку новых компаний и применяем фильтры. Обогащение может обновляться отдельным воркером. Интерфейс написан на React и TypeScript, API — на FastAPI, обработка данных — на Python и DuckDB. Основной подбор и объяснения работают без LLM.

**Не читать со сцены:** prefix5, названия внутренних функций, лимиты 500/200, pgvector/RRF, версии библиотек, подробности пагинации. Оставить в техническом резерве.

**Переход:** «Но одного маршрута недостаточно — нужно объяснить конкретную рекомендацию».

**Основание:** evidence.md E03–E10, E15–E20. В сохранённом примере (срез 1086c2c) — BM25/H-15f; на текущем main порядок задаёт LightGBM LambdaMART (D-103). Векторная ветка выключена; наблюдённое локальное хранилище — Parquet, а не PostgreSQL.

## 5. От рекомендации — до конкретного лота

**Задача:** продемонстрировать проверяемость и смысл ранжирования, не превращая основной рассказ в чтение формул.

**На экране:**

- ТСК ВЕКТОР ЛАЙН → историческое свидетельство: лот 5424546 от 02.12.2024.
- Три активных фактора: соответствие товару; опыт в похожих закупках; активность относительно конца данных.
- Доказательство опыта: 126 похожих лотов, 36 побед в них.

Точные формулы, веса, насыщение опыта, score 0.9996 и правила равенства — на запасном B1. Если число score видно в настоящем UI, сохранять его без изменения; подпись: «Рейтинг соответствия, не вероятность успешной поставки».

**Речь:**

> У ТСК ВЕКТОР ЛАЙН можно проследить рекомендацию до конкретного исторического лота — поставки картриджей. Для оценки используем три фактора. Соответствие учитывает текст и код ОКПД2. Опыт — участия и победы именно в похожих закупках: в этом примере сто двадцать шесть лотов и тридцать шесть побед. Активность определяется относительно конца доступных данных, а не сегодняшнего дня. Причины формируются из этих же признаков. Поэтому заказчик видит не отдельный красивый текст поверх рейтинга, а его основания. Такой рейтинг объясняет релевантность, но не гарантирует качество будущей поставки.

**Переход:** «Проверили ли мы, что дополнительное ранжирование полезнее одного BM25?»

**Основание:** evidence.md E07–E12. Источники data:items являются идентификаторами записей, а не обязательно публичными URL. Реестр доказывает происхождение факта, не качество исполнения.

## 6. На dev-выборке скоринг улучшил полноту первых десяти результатов

**Задача:** показать количественный результат и корректно ограничить его смысл.

**На экране:** две полосы на общей шкале 0…1:

- BM25: Recall@10 = 0.449.
- BM25 + ранжировщик LightGBM (текущий дефолт D-103, `A361-base`): Recall@10 = 0.572 [0.553, 0.592]; прежний H-15f — 0.491 (запасной B2).

Сохранить 95% bootstrap-интервалы из исходного evidence.md. Подпись: «2 000 одинаковых dev-запросов · сохранённые отчёты исторических версий». Контекст: вход — предмет + позиции + ОКПД2; история до 01.07.2025, запросы — июль–сентябрь 2025. Вариант ранжировщика выбран на dev (обучение — лоты до 01.07.2025, dev не читался); независимый holdout не оценён.

**Речь:**

> В сохранённых экспериментах мы сравнили один BM25 с выбранным скорингом на двух тысячах одинаковых запросов. Recall@10 вырос с 0.449 до 0.491. Эта метрика показывает, какую долю известных релевантных поставщиков система возвращает в первой десятке, в среднем по запросам. Это не процент успешных поставок. Веса подбирались на этой же dev-выборке, поэтому результат пока не является независимой финальной проверкой. Кроме того, тест использовал предмет, позиции и коды закупки: переносить эти числа на любой короткий текст нельзя. Следующий шаг — независимый holdout и оценка полезности списка заказчиком.

**Что не утверждать:** статистическую значимость прироста без парного анализа; качество текущего HEAD; независимость dev от настройки; качество новых компаний; отсутствие всех временных утечек; ускорение или экономический эффект.

**Основание:** evidence.md «Метрики: только исторический список поставщиков». B-bm25 = 0.449234 [0.428892; 0.469074], commit 1086c2c (перезапуск #271). Парная разница E-003 к B-bm25 — +0.041 [+0.031; +0.052] (pitch/facts.md). E-003 = 0.490523 [0.471269; 0.510758], commit 497b959. Отчёты от 01.10.2026. Это сохранённое сравнение разных commits, не новый A/B текущего приложения.

## 7. Рабочий сценарий и следующий практический шаг

**Задача:** закончить конкретным результатом команды и предложением проверки, а не формулой или перечнем оговорок.

**На экране:** «Описание → поставщики → основания → XLSX». Ниже — «Подготовлен REST API / OpenAPI». Справа — «Предлагаем: пилот подключения + независимая экспертная проверка». Финальная фраза: «Митрандир — список поставщиков, который можно проверить».

**Речь:**

> Результат нашей работы — сервис с полным пользовательским сценарием: задать закупку, получить кандидатов, проверить основания, применить фильтры и выгрузить список. Для подключения подготовлен REST API с OpenAPI. Следующий предлагаемый этап — согласовать пилот и проверить рекомендации с заказчиком на независимой выборке. Мы не заменяем решение заказчика: Митрандир даёт ему список поставщиков, который можно проверить. Спасибо, готовы к вопросам.

**Граница:** API реализован; промышленная интеграция с АИС ГЗ не подтверждена. Пилот — предложение, не состоявшаяся договорённость. Измеренного экономического эффекта нет.

**Основание:** evidence.md E23, UNKNOWN и HYPOTHESIS / предлагаемые действия.

## Две минуты вопросов

Запасные слайды не входят в основной маршрут и не открываются автоматически. На вопрос — прямой ответ ориентировочно на 20–30 секунд и только релевантный резервный слайд. Не пытаться самостоятельно рассказать все пять за две минуты.

### B1 — формула и выбор алгоритма

S = 0.762F + 0.190E + 0.048A. F = 0.8B + 0.2D, без кода F = B. Опыт насыщается на default-пределах 20 лотов / 10 побед. Активность отсчитывается от конца данных. Равенство: score → BM25 → ИНН. Не называть эти веса обученной LTR-моделью. В выбранном примере первые четыре результата имеют одинаковый score 0.9996. Наличие векторной ветки не доказывает, что она лучше или хуже; она выключена в default.

Основание: evidence.md E07–E12, E19–E22; storyboard.md B1.

### B2 — методика проверки

Разобрать Recall@10 и определения релевантности: ЭМ — валидные ИНН оферт, АИС ГЗ — исполнители из выгрузки. Историческое отсечение до 01.07.2025, dev — июль–сентябрь. Настройка на dev, holdout не оценён. Нет полного point-in-time подтверждения времени появления оферт и побед: остаточная временная утечка возможна. Текущие реестровые факты и «Новые» в метрику не входят. Не выдавать отдельные bootstrap-интервалы за проверку значимости разницы.

Основание: evidence.md «Метрики»; storyboard.md B2.

### B3 — инфраструктура и интеграция

Наблюдённый режим: React → FastAPI → Parquet / DuckDB + bm25s, кеш и worker. PostgreSQL — реализованный вариант, не наблюдённая база этого показа. API и XLSX не равны внедрению в АИС ГЗ. Предлагается согласовать контракт интеграции и пилот. Не путать автономную HTML-презентацию без backend с самим продуктом.

Основание: evidence.md E15–E20, E23; storyboard.md B3.

### B4 — новые компании и внешние факты

«Новая» означает отсутствующую в нашей истории, а не недавно зарегистрированную. ОКПД2 → ОКВЭД → реестр МСП — эвристическая ветка. Подходящий ОКВЭД и роль производителя не доказывают производство конкретного товара. В зафиксированном примере новых компаний нет. Полное покрытие реестров, контактов и статусов не подтверждено. Локальные идентификаторы записей не следует выдавать за публичные страницы источников.

Основание: evidence.md E10, E17–E18, UNKNOWN; storyboard.md B4.

### B5 — границы и эффект для заказчика

Есть происхождение рекомендаций и измерение исторической полноты; нет оценки качества будущего исполнения и измеренной экономии. Цена исполнения и reliability не входят в default-score. Возможное сокращение ручной работы — гипотеза. Предложение для пилота: измерить время составления списка и экспертную оценку его полезности; это новые предлагаемые критерии пилота, не проведённые измерения.

Основание: evidence.md E14, UNKNOWN, HYPOTHESIS / предлагаемые действия; storyboard.md B5.

## A. Backtest на истории

Если в данных есть, кто подавал оферты или получал контракты (есть: таблица Поставщики — ИНН участников лота и `is_winner`, `research/PROBLEM.md`).

- Разбиение **по времени**: признаки — только по данным до даты D, запросы — из закупок после D.
  Случайный split даёт утечку.
- Запрос — позиция или закупка из тестового периода; релевантные — фактический поставщик и
  подавшие оферты (ЭМ: все оферты лота релевантны, победитель — grade 2; АИС ГЗ: в данных фактически только исполнитель — релевантен он; метрики считаем **раздельно по каналам**).
- Метрики: Recall@10, MRR, nDCG@10 (`src/eval/metrics.py`). Рядом — метрики по победителю лота, в которых отчитываются другие команды (#280): `winner@1/5/10/20` (победитель в топ-k) и `winner_mrr`; считаются по кейсам с победителем (`grades = 2`), число таких кейсов — `n` в `metrics` и срезах. В ЭМ релевантны все оферты, в АИС ГЗ — только исполнитель: recall@10 между каналами не сравнивается, `winner@10` — сравнивается. `winner_mrr` считается по сохранённому списку top-k (k = 20), то есть это MRR@20; у других команд MRR может считаться по полному списку. Сравнимость с чужими цифрами ограничена протоколом: у нас `as_of` = cutoff (история заморожена на начало периода), у других история обновляется по месяцам.
- Обязательные baseline: **популярность** (самые частые поставщики в классе ОКПД2) и **BM25**.
  Если мы их не обыгрываем — это главный вывод, а не мелочь. Baselines: популярность в классе ОКПД2, **история заказчика** (в 2025 г. 57.85% побед — у поставщика, уже побеждавшего у этого заказчика), BM25 — T-08 плана. Потолок recall на истории — доля холодного старта (dev 6.75%).
- Утечки: статистики контрагента не включают тестовую закупку; дубли склеиваются по ИНН до разбиения.
- Ограничение: backtest измеряет «угадали, кто и так участвовал», а не «нашли лучших». Поэтому нужен B.

### Baselines и срезы (T-08, D-038…D-040)

Baselines — записи `configs/baselines.yaml` (id эксперимента → метод), код — `src/eval/baselines.py`;
`configs/search.yaml` остаётся конфигурацией продукта. История для каждого — только лоты с
`publish_date < as_of` кейса (в eval `as_of = cutoff`), ИНН с неверной контрольной суммой не выдаются.

| ID | Что ранжирует | Запуск |
|---|---|---|
| B-pop | поставщики по числу лотов, в которых они **участвовали** (не только побеждали), в группе ОКПД2 запроса — 4 знака, «17.12»; у запроса несколько кодов — лоты любой из групп, лот считается один раз; при равенстве — по ИНН. Набралось меньше k — добор по классу (2 знака), затем по всем классам | `make eval EXP=B-pop` |
| B-inc | инкумбент: поставщики, участвовавшие **у этого заказчика** (`customer_inn`) в этой группе ОКПД2, по убыванию числа лотов; дальше добор списком B-pop. Нет заказчика или истории — это B-pop | `make eval EXP=B-inc` |
| B-bm25 | порядок ретривера `search()` без компонентного скоринга: BM25 по позициям лотов до `as_of` → поставщики по лучшему BM25 своих лотов, затем по числу совпавших лотов. От текущего метода (`search()` v1, E-002) отличается тем, что тот берёт тех же 200 кандидатов и пересортировывает их по сумме компонент (product_fit с ОКПД2, experience, activity, geography) | `make eval EXP=B-bm25` |

Другой id с тем же методом (например, прогон на реальных кейсах):
`uv run python -m src.eval.run --exp B-inc-real --baseline B-inc --part real`.

**Срезы** считаются для любого эксперимента (`slices` в `eval/results/<id>.json`, те же метрики и
bootstrap-интервалы, `n_queries` среза рядом):

- `channel=ЭМ`, `channel=АИС ГЗ` — канал кейса. Между собой каналы не сравниваются: в ЭМ релевантны
  все оферты, в АИС ГЗ — только исполнитель.
- `winner=new` — **победитель новый для заказчика**: ни один победитель лота (`grades = 2`) не
  участвовал ни в одном лоте этого заказчика до `as_of` (в любом классе, с любым исходом);
  `winner=known` — хотя бы один участвовал. Кейсы без победителя или без ИНН заказчика (в dev-выборке
  45 из 2 000) в эти два среза не входят. Метрики внутри среза — те же, по всем релевантным кейсам.
- пересечения `channel=…,winner=…`.

Срез «новый для заказчика» — ответ на ограничение backtest: B-inc по построению не может найти
поставщика, которого заказчик ещё не видел в этой группе, а сервис обещает именно это.

## B. Ручная разметка новых поставщиков

Для 10–15 реальных запросов размечается top-10 блока «Новые из открытых источников»: 1 — компания
действительно поставляет или производит это, 0 — нет. Метрика — precision@10. LLM-судья может
доразметить остальное только после проверки согласия с человеком на пересечении (ориентир — не
ниже ~80%). Одна и та же модель не ранжирует и не судит одновременно.

Файл разметки — `eval/labels/new_suppliers.csv`:

```text
query_id,inn,name,label,labeled_by,labeled_at
stub-dev-1,0000100051,,1,человек:<логин>,2026-10-01T15:10
stub-dev-1,,ООО «…» (ИНН не подтверждён),0,llm:<модель>,2026-10-01T15:20
```

`inn` или `name` (если ИНН не подтверждён); `label` — 0/1; `labeled_by` — `человек:<логин>` или
`llm:<модель>`.

### Как размечать (T-14, #21)

Таблица для разметки — `eval/labels/new_suppliers_todo.csv` (разделитель `;`, UTF-8 с BOM — открывается в
Excel; строится командой `uv run python -m src.eval.label_new prepare`, 12 запросов: 8 `real` + 4 класса ОКПД2
из dev, правило — `select_cases`). В ней top-10 блока «Новые» на момент сборки (ответы реестра МСП лежат в
кеше, список зафиксирован), контекст запроса (`query_text`, `okpd2`) и только факты из Evidence: название,
ИНН, ОКВЭД с расшифровкой, регион, статус МСП, ссылка на источник.

1. Заполните `label`: `1` — компания действительно поставляет или производит предмет запроса (по названию,
   ОКВЭД и, если сомневаетесь, по сайту компании); `0` — нет (не тот товар, не та отрасль, посредник без
   этого товара, ликвидирована). Сомнение → откройте источник; неопределимое — оставьте пустым (в расчёт не
   идёт). Только ОКВЭД «по классу» без совпадения с предметом — `0`, совпадение класса не равно «поставляет».
2. Заполните `labeled_by` (`человек:<логин>`) и `labeled_at` (`2026-10-01T15:10`). Остальные колонки не меняйте.
3. Сохраните как `eval/labels/new_suppliers.csv` (колонки `query_id,inn,name,label,labeled_by,labeled_at`
   обязательны, лишние score игнорирует; `;` или `,`). Если ИНН не подтверждён, ключ — `name`.
4. `uv run python -m src.eval.label_new score --exp N-new-p10` → `eval/results/N-new-p10.json`: precision@10
   по запросам (доля `1` среди размеченных строк запроса), среднее с bootstrap 95 % и согласие человека с LLM
   на пересечении (`agreement_human_llm`). Метки LLM исключаются из метрики, пока нет ≥ 20 общих пар с согласием ≥ 80 %.
   Блок строится по текущему реестру МСП и не режется по времени: это precision сегодняшнего сервиса, а не backtest. Метка человека сильнее метки LLM; LLM-строки допускаются только
   после согласия ≥ ~80 % на пересечении.

### LLM-судья (#82, D-070)

Судит субагент, не модель, ранжирующая блок. `uv run python -m src.eval.judge_new export` — слепые пакеты
`eval/judge/packets/<query_id>.json` (вне git; только запрос и факты кандидата, без меток, скора и позиции);
`... prompt` — инструкция судье (порядок: сначала человек сохраняет размеченный todo как `new_suppliers.csv`, потом import); ответ судьи — JSON `{"query_id", "labels": {key: {"label": 0|1|null, "reason"}}}`;
`... import <ответы> --model <имя>` дописывает строки `llm:<имя>` в `eval/labels/new_suppliers.csv`
в колонках заголовка существующего файла (повтор не дублирует, ручные строки не меняет, файл дописывается, не перезаписывается). Согласие с человеком и порог 20 пар / 80 % — `label_new score`.

## Шум

На десятке запросов разница в пару пунктов — шум. `make eval` считает bootstrap-интервалы по
запросам (2000 выборок, фиксированный seed). Улучшение, которое держится на одном запросе, подозрительно.

### Правило принятия изменения (#280)

Объявлено до прогона, чтобы не подбирать порог под результат: изменение поиска или ранжирования принимается, если на dev (2 000 кейсов, парный `src.eval.compare`) основная метрика `recall@10` выросла минимум на +0.01 **и** нижняя граница 95 % парного bootstrap-интервала (его считает `src.eval.compare`) разности выше 0; `winner@10` не должен упасть (точечная Δ ≥ −0.01). Падение в одном из срезов канала или `winner=new / known` — записывается в `EXPERIMENTS.md` с цифрой, а не замалчивается. Правило решает про принятие в ветку; формулу скоринга по умолчанию меняет только подтверждение человека №3. Идея правила — `alfalahnaif/RLT.Hack-RoboxTeam`, `reports/p2_003_ranking.md`.

## Чистый рефакторинг: паритет выдач (#286)

«Рефакторинг не меняет выдачу» проверяется командой, а не утверждением. `src.eval.compare` сравнивает
метрики с bootstrap-интервалом — разницу в пару кейсов он не видит; `make parity` сравнивает сами выдачи:
для каждого общего `query_id` — `per_query[].ranked` (ИНН в порядке выдачи, как их видит пользователь) побитово,
состав и порядок.

Процедура (прогон dev ≈ 500–600 с: E-002 498.7 с, H-15f 609.7 с — на пару ≈ 17–20 минут):

```bash
# 1. базовый коммит <base> (origin/main до правки), чистое дерево, sha — первые 8 символов;
#    у прогона свой ПУСТОЙ каталог индекса (иначе индекс и sidecar берутся с диска — см. ниже)
INDEX_DIR=indexes/parity-base make eval EXP=parity-base-<sha>
# 2. ветка с рефакторингом, правка закоммичена (dirty: false в результате), другой пустой каталог индекса
INDEX_DIR=indexes/parity-new make eval EXP=parity-new-<sha>
# 3. сравнение
make parity A=parity-base-<sha> B=parity-new-<sha>
```

**Что прогон выполняет заново, а что берёт с диска.** Паритет проверяет код, который работает при запросе;
готовые артефакты он не пересобирает, и тогда `PARITY: OK` ничего не говорит о коде, который их строит.

- **Индекс BM25 и sidecar `doc_codes.parquet`** читаются из `INDEX_DIR`, если там уже есть индекс с тем же ключом. Ключ — манифест
  ingest (`built_at`, `rows`), `as_of` и версия токенизатора (`src/match/index.py`: `index_key`, `get_index`); **код построения
  индекса в ключ не входит**. Прогон на новом коде при непустом каталоге берёт индекс, построенный старым, и правки `index.py`,
  `store.text_codes`, `search._doc_codes` остаются непроверенными. Поэтому у каждого прогона свой пустой `INDEX_DIR`: индекс
  строится заново. `make eval` уважает `INDEX_DIR` (`index_root()`; относительный путь — от корня репозитория); путь под
  `indexes/` уже в `.gitignore` (`indexes-parity-*` не подошёл бы). Перед повтором каталоги удалить. Общий `INDEX_DIR` у двух
  worktree — именно тот случай, который даёт ложный OK. Sidecar при недоступном на запись каталоге индекса строится в
  `<tmp>/rlt-doc-codes-<ключ>/` (docker, read-only) и оттуда же читается: если такой каталог остался с прошлого запуска — удалить.
- **Данные** `data/processed` (ingest parquet, `suppliers_<cutoff>.parquet`) и кейсы `eval/cases/dev.jsonl` берутся готовыми:
  код `src/ingest`, `src/eval/build_cases`, `src/db` (`make db-load`) при `make eval` не исполняется. Правка `src/ingest` — собрать
  ingest каждым коммитом в свой каталог и указать его: `uv run python -m src.ingest.build --out-dir data/processed-parity-<base|new>`,
  затем `DATA_PROCESSED_DIR=data/processed-parity-<base|new> INDEX_DIR=indexes/parity-<base|new> make eval EXP=…`
  (`data/*` в `.gitignore`). Без этого паритет покрывает только исполняемое при запросе; сменившийся состав кейсов даёт код 2.

- Id `parity-*` не входят в `configs/experiments.yaml`: прогон идёт на конфигурации продукта
  (`configs/search.yaml`; `make eval` пишет в лог «записи в experiments.yaml нет»). Паритет другой
  конфигурации — `uv run python -m src.eval.run --exp parity-new-<sha> --config-of H-15f` (или `--baseline`) для **обоих** прогонов.
- `eval/results/parity-*.json` в `.gitignore` — одноразовые, не коммитятся. Базовый прогон можно делать в отдельном worktree
  (`data/` вне git — указать общий каталог данных через `DATA_PROCESSED_DIR`, `INDEX_DIR` у каждого worktree свой, относительный
  путь `indexes/parity-base` уже разный); `make parity` читает только `eval/results/` своего worktree — скопировать туда
  `parity-base-<sha>.json` из worktree базового прогона.
- Вывод: `расхождений: M из N (доля %)`, разбивка «состав» (другие ИНН или другое их число) / «только порядок» (те же
  ИНН, другой порядок), первые 5 расхождений — `query_id`, ранг первого расхождения (с 1), ИНН у A и у B, у состава ещё
  «только в A / только в B»; `-n <число>` — показать больше. Конец — `PARITY: OK` или `PARITY: FAIL`.
- **Код выхода** `uv run python -m src.eval.parity A B`: `0` — все выдачи совпали; `1` — есть расхождение; `2` — сравнить
  нельзя: нет файла результата, у кейсов нет `ranked` (часть больше `RANKED_LIMIT = 5000`, как `dev_full`, или результат
  старого формата), разные наборы кейсов (та же проверка, что у `compare.paired`: `compare.require_same_cases`), `query_id`
  повторяется, кейсов нет. Невозможность сравнения — ошибка, а не «0 расхождений». Коды 0 / 1 / 2 — у `python -m src.eval.parity`; `make parity` сам выходит с
  кодом 2 при любой ошибке цели (так устроен GNU make) и печатает `make: *** … Error 1` (расхождение) или `Error 2` (сравнить нельзя) —
  различать по этой строке и по последней строке вывода.
- **Предупреждения** (не ошибки, печатаются до итога): различается `config` (перечень ключей), `part`, `store`
  (parquet / postgres), `tokenizer_version`, `vectors`, `stub`; прогон на грязном дереве (`dirty`). `config_sha256` не
  сравнивается: в него входит дерево кода метода (`METHOD_PATHS`), то есть при любом рефакторинге он различается по построению.
- **Недетерминизм.** Два прогона одного и того же коммита без правок должны давать 0 расхождений:
  `INDEX_DIR=indexes/parity-a make eval EXP=parity-a`, `INDEX_DIR=indexes/parity-b make eval EXP=parity-b` на одном дереве (два
  пустых каталога — заодно проверяется, что индекс строится одинаково) → `make parity A=parity-a B=parity-b`. «Недетерминизм прогона»
  вывод пишет только при том же коммите **и** без предупреждений о входе (config, store, part, dirty и т. д.); при том же коммите, но
  другом входе — «недетерминизм не установлен»; при разных коммитах вердикта нет, расхождение может быть самой правкой. Если расхождения
  есть и вердикт «недетерминизм прогона», это находка про поиск, а не про рефакторинг: её описывают (строка в этом разделе или в `research/ERROR_ANALYSIS.md`), а не маскируют сравнением множеств
  или усечением списков. Где искать: порядок при равенстве оценок в ретривере (`bm25s`), `ORDER BY` в `src/match/store.py`
  (сортировка текста — побайтово), итерация по `set`/`dict` до сортировки.
- Что есть на данных сейчас (`eval/results/*.json` в git, команды — после запятой): `bm25-dev-parquet` против `bm25-dev-pg`
  (один коммит `5232e4cc`, разное хранилище) — `make parity A=bm25-dev-parquet B=bm25-dev-pg`: 0 расхождений из 2 000, предупреждение

## Как это устроено в коде

- `make eval EXP=<id>` → таблица в терминал и `eval/results/<id>.json`: `exp_id`, `part`,
  `created_at`, `commit`, `dirty`, `config` (`configs/search.yaml`), `config_sha256`, `stub`,
  `n_queries`, `elapsed_s`, `metrics` (`value`, `ci95`), `slices`, `per_query` — по строке на кейс:
  метрики, `channel`, `winner_new` и `ranked` — выданные top-k ИНН по порядку (для частей до 5 000
  кейсов; `dev_full` пишется без `ranked`, иначе файл не пройдёт стража 5 МБ). Любая цифра на слайде воспроизводится этой
  командой (`pitch/facts.md`). Id `final*` зарезервирован.
- Части — `configs/split.yaml`: `cutoff`, `holdout_from`, пути к кейсам. `dev` —
  `[cutoff, holdout_from)`, для настройки; `holdout` — с `holdout_from`, **запечатан**.
  Даты — `configs/split.yaml` (cutoff 2025-07-01, holdout 2025-10-01); исключаем лоты без участников и АИС ГЗ с «ст.93»/«единственный поставщик».
- **Сборщик кейсов** (T-07, D-032): `uv run python -m src.eval.build_cases` читает
  `data/processed/{notices,participants,items}.parquet` (лоты с `publish_date ≥ cutoff`) и пишет:
  `dev` — `eval/cases/dev.jsonl`, стратифицированная выборка 2000 (канал × класс ОКПД2 лота, seed
  20261001), в git; `dev_full` — все кейсы dev, `holdout` — с `holdout_from`, оба в
  `data/processed/eval/` вне git; `real` — `eval/cases/real.jsonl`, 8 читаемых кейсов (раздел D);
  счётчики — `eval/cases/build_stats.json`. Прогон частей: `make eval EXP=<id>` (dev) или
  `uv run python -m src.eval.run --exp <id> --part dev_full|real`; holdout — только `make eval-final`.
  - Лот → `Query`: `query_id = lot-<lot_id>` (как `GET /api/lot`); `text` = `subject` (если это шаблон
    «…статьи 93» — `procedure_name`) + до 10 различных наименований позиций через «; »; `okpd2` — коды
    позиций; `customer_inn`, `budget` = НМЦК, `channel`; **`as_of = cutoff` во всех частях**.
  - Релевантные: ЭМ — все оферты, `grades`: победитель 2, остальные 1 (у 709 лотов dev победителя нет —
    все оферты 1); АИС ГЗ — победитель(и), grade 2. ИНН с неверной контрольной суммой не релевантен:
    `search()` вернуть его не может (`inn=None`). Метрики пока бинарные (`relevant_inns`), `grades` —
    для графового nDCG и среза «победитель».
  - Исключаются по порядку: нет участников; АИС ГЗ с «частью 12 статьи 93» или «единственного
    поставщика» в `subject` или `procedure_name` (прямой договор, выбора среди оферт не было; правило
    только для АИС ГЗ, в ЭМ таких лотов 0); нет участника с валидным ИНН; пустой текст.
  - Цифры (`build_stats.json`): **dev** 58 047 лотов → 51 599 кейсов (ЭМ 26 431, АИС ГЗ 25 168):
    без участников 6 189, АИС ГЗ ст.93 257, без валидного ИНН 2, пустой текст 0. **holdout**
    99 053 → 88 848 (ЭМ 49 203, АИС ГЗ 39 645): 9 671 / 529 / 5 / 0. Сверка с профилем: победитель
    без истории до cutoff — 6.65% кейсов dev (профиль — 6.75% годных лотов), все релевантные без
    истории — 5.79% (5.80%).
  - Тест на утечку — `tests/unit/test_build_cases.py` (фикстура `tests/fixtures/eval_cases/`): `as_of`
    = cutoff во всех частях, даты в окне, dev ∩ holdout = ∅, лоты до cutoff не кейсы, агрегаты
    `suppliers_<cutoff>.parquet` кончаются до cutoff.
- `Query.as_of` в кейсе — пусто или ≤ `cutoff`: пустое `src/eval/run.py` заменяет на `cutoff` (признаки только до него, D-018), позже `cutoff` — ошибка. T-07 не ставит `as_of = holdout_from`: `make eval-final` пишет маркер до прогона, и такая ошибка сожжёт sha конфигурации.
- `src/eval/split.py`: `load_cases("holdout")` вне `make eval-final` бросает `SealedError`;
  кейс dev вне своих дат — ошибка «split leak».
- `make eval-final CONFIRM=<sha256>` (`src/eval/final.py`) читает holdout, только если:
  1. `CONFIRM` равен sha256 конфигурации (`configs/search.yaml` + `configs/split.yaml` + закоммиченный код метода `src/{match,enrich,sources,ingest,eval,llm}`, `src/contracts.py`; UI и API не входят, D-015); без
     `CONFIRM` команда печатает текущий хеш;
  2. дерево чистое для `src/ configs/ pyproject.toml uv.lock`;
  3. эта конфигурация на holdout ещё не запускалась;
  4. `search()` — не `# STUB`.
  Каждый запуск — строка в `eval/final-log.md`. Запускает только `evaluator` и только по заморозке.
  **Оценивается выборка holdout** (`holdout_sample: 3000`, `holdout_seed` в `configs/split.yaml`, D-076): весь holdout — 88 848 кейсов по 0.25–0.30 с (E-002, H-15f на dev) → 6–7.5 ч одним
  запуском, а маркер «уже запускалась» пишется до чтения holdout — прерванный прогон сжигает конфигурацию без
  результата. Выборка — n кейсов с наименьшим sha256(seed:query_id), задана в хешируемом конфиге до запуска;
  3 000 кейсов ≈ 15–25 мин, 95% CI recall@10 ≈ ±0.016. **`holdout_seed` и `holdout_sample` не меняются:** другая
  выборка того же метода — повторный взгляд на holdout (новый sha гейт пропустит, поэтому seed и n видны в
  строке `eval/final-log.md`). Результат пишется построчно (`dump_record`), с полем `sample` (n, из скольких, seed).
- Тест замка — `tests/unit/test_eval_seal.py`.
- `make eval` оценивает ту же выдачу, что видит пользователь: после замены заглушки `evaluate()`

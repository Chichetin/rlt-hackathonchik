## Кто побеждает вне реестра МСП и что видят открытые наборы ФНС (#219, 02.10)

все отчитывающиеся организации, а не только МСП. **Не только МСП, но и не все: крупнейших победителей в наборах

(543 841), которых нет в реестре МСП (пул #185):

## План расширения источников (#59, 01.10)

Решение человека 01.10: берём любые источники, доступные честно, то есть без ключей и
регистраций в обход подтверждения №4, с соблюдением robots.txt (до D-085 — и без обхода капчи и WAF). Проверка
с площадки 01.10 ≈ 14:55–15:05 МСК: 1–5 запросов на хост, паузы ≥ 1 с, сырые ответы лежат в
scratchpad. **Это правило не годится для zakupki.gov.ru (`Crawl-delay: 60`).** Сколько запросов тогда
ушло на zakupki.gov.ru и с какими паузами — **не установлено**: кеш `cache/sources.sqlite` (основная копия)
пуст (0 строк), scratchpad и запись той сессии не сохранились. По тексту этого документа запросов было
не меньше трёх (главная — таймаут; поиск; РНП для 7804428656), по записи D-058 — ещё РНП с `strictEqual=true`
для ИНН с 28 записями, всё в окне около 10 минут, то есть паузы ≥ 60 с **не подтверждены и, судя по числу
запросов, соблюдены не были**. Запись трёх страниц РНП для тестов (19:41–19:43 МСК, 3 запроса) шла с паузами
82 с и 52 с; 52 с — тоже меньше 60 с. Клиент `src/sources/eis_rnp.py` держит ≥ 60 с (ниже не опускается

| В «Новые» | **та же дорога, что у веб-лида #108** (лид — первого класса ОКПД2 запроса): нет в данных организаторов, карточка ФНС в кеше, основной ОКВЭД подтверждает класс, регион — заказчика или соседний; без карточки — очередь обогащения. Объяснение `product_fit`: «Найдена в Яндекс Поиске по запросу «…», ИНН указан на сайте …; вид деятельности — по
реестру ФНС: …». Строка воронки — в `Discovery.leads` («Яндекс (запасной путь): нужен: … запросов 3, из них
платных 1; сайтов проверено 6, ИНН на сайте у 3; уже в данных …, в блок …»). **Ограничение:** в `/api/search` реестр
обычно расходует почти весь бюджет 4 с, поэтому живой Яндекс там успевает редко — блок дополняется из кеша, который
наполняют `make predict` и повторные поиски лота.

**Не сделано:** живой прогон (подвыборка, `Y-yandex-*.json`, «было → стало», ручная проверка 20 компаний) — только
человек, по его ключу и потолкам; роль по фразе сайта (`role.decide`) в карточку не подключена — роль по ОКВЭД
карточки, как у остальных «Новых»; отдельной строки плана прогона («лотов под Яндекс, запросов, ₽») в `make
predict` нет — лог пишет число платных запросов на лот.

## Сопоставление с ИНН — самое хрупкое место

Название на сайте не совпадает с названием в ЕГРЮЛ; у группы компаний несколько юрлиц. Порядок:

1. ИНН со страницы реквизитов на сайте;
2. поиск по названию и региону в реестре;
3. ручная проверка на выборке.

ИНН проверяется по контрольным цифрам (10 знаков — юрлицо, 12 — ИП; `inn_is_valid` в
`src/contracts.py`). Неразрешённая компания показывается с пометкой «ИНН не подтверждён»
(`inn=None`), а не с угаданным ИНН.

## Правила

- У каждого факта — источник, URL и дата получения (`Evidence`). В интерфейсе источник рядом с
  фактом. Факт без источника не показывается.
- LLM может **извлекать** данные из текста страницы, но не **порождать** их. ИНН, телефон, email
  или адрес, которых нет в тексте источника, — ошибка уровня блокера. Механически ловит
  `src/enrich/evidence.py` (значение буквально в тексте закешированной страницы + контрольные
  цифры ИНН); тест — `tests/unit/test_evidence.py`.
- Все ответы внешних источников кешируются на диск: `src/sources/cache.py` (SQLite, TTL,
  при падении сети — устаревший кеш). Демо работает на кеше, даже если упадёт интернет площадки.
- Уважаем robots.txt и условия использования, паузы между запросами и лимиты на домен. Обход капчи и защиты разрешён
  (D-085); агрегаторы реквизитов не берём — дублируют ФНС.
  Заблокированный на площадке IP — мёртвый модуль.
- Собираем данные о компаниях. Персональные данные физлиц, включая ИП, — только то, что публично
  в госреестрах, без лишнего сбора. Основание: сведения ЕГРЮЛ/ЕГРИП открыты и общедоступны (ст. 6
  129-ФЗ, `https://www.consultant.ru/document/cons_doc_LAW_32881/ba389bdea85fe0ff7da642f413b40570caf17412/`),
  обработка ПДн, подлежащих опубликованию по федеральному закону, допускается без согласия (п. 11
  ч. 1 ст. 6 152-ФЗ, `https://www.consultant.ru/document/cons_doc_LAW_61801/315f051396c88f1e4f827ba3f2ae313d999a1873/`;
  оба открыты 01.10). Для ИП показываем ФИО, ИНН, ОГРНИП, статус, дату регистрации, ОКВЭД,
  категорию МСП; **адрес места жительства ИП не показываем** (исключён из общедоступных сведений —
  норму **[ПРОВЕРИТЬ дословно]**, п. 1 или п. 5 ст. 6 129-ФЗ); контакты ИП не собираем. 12-значный ИНН,
  которого нет в ЕГРИП, — «физическое лицо, сведения не раскрываются», без обогащения.
- РНП: **сейчас — жёсткое исключение** (METHODOLOGY шаг 3, `src/match/filters.py`). Справка:
  требование об отсутствии в РНП заказчик **вправе** установить (ч. 1.1 ст. 31 44-ФЗ — вторичный
  источник, **[ПРОВЕРИТЬ дословно]**); ликвидация/прекращение ИП/конкурсное производство — обязательное
  требование (ч. 1 п. 3 ст. 31). Переключатель «показывать поставщиков из РНП» — **предложение**,
  ждёт ответа на Q-27 и подтверждения человека №3, без них не реализуется.
- Пакетные задачи (ночное обогащение) идемпотентны, пишут прогресс и продолжаются с места
  падения: очередь `src/worker/queue.py` + `make worker`.
- Массовый парсинг сайтов — подтверждение человека №4. Сначала подвыборка, потом весь объём.

### Прогрев top-N поставщиков (#11)

`python -m src.worker.prefetch --top N` (`src/worker/prefetch.py`), запускать при остановленном `worker`. Правило отбора, детерминированное: из `suppliers.parquet` только `inn_valid`, порядок `lots_won DESC, lots_participated DESC, last_seen DESC, inn ASC` (победы важнее участий, дальше недавность, затем ИНН). ИНН ставятся в очередь `tasks` (идемпотентно по `(enrich, inn)`), прогрев берёт только свои ключи (`claim_keys`), чужие задачи очереди не трогает. Пауза 1 с после каждого обращения в сеть, ответ из кеша паузы не требует. Капча pb.nalog.ru прогрев не останавливает, пока отвечает запасной источник (D-052): pb отключается на 15 мин, дальше реестр МСП и ГИР БО. Остановка и код выхода 1 - если ни один источник не ответил (и если готово меньше, чем запрошено); задачи остаются в очереди, повторный запуск продолжает с места остановки. Ctrl+C возвращает текущую задачу в очередь.

Прогон 01.10 (top-200, `cache/prefetch-run1.log`): 200 из 200, 20,7 ИНН/мин, 0 ошибок. pb ответил по первым 5 ИНН, затем капча; 195 ИНН через реестр МСП, у 30 из них добавлен ГИР БО. Название найдено у 187 из 200; у 13 крупных компаний только статус реестра МСП без названия (не МСП, ГИР БО их не вернул).

Ночной режим (#20, D-155): `python -m src.worker.prefetch --enqueue-only --top N` ставит ИНН в очередь Postgres в порядке активности (те же правила отбора, что у top-N: победы, участия, недавность — это те, кого пользователь увидит первыми в выдаче), `worker` их разбирает — в ночном режиме `docker compose -f docker-compose.yml -f docker-compose.night.yml up -d --build db worker` (`make up` его не включает): капча без запасных источников — сон 15 мин и продолжение, потеря БД — повтор подключения, пауза 1 с только после живого запроса. **Кеш источников — только в файловой системе Linux (правило оператора):** `api` и `worker` монтируют `./cache`; SQLite на bind-mount Windows (`/mnt/c`) при записи из контейнера и процессов Windows повредил `cache/sources.sqlite` основной копии (01.10, восстановлено 1241 из 1243 страниц). Темп к одному хосту общий только внутри процесса (`HostPacer` в `src/sources/pacing.py`; при рестарте контейнера охлаждение после капчи забывается, между контейнерами лимитера нет), поэтому ночью — один воркер. К pb.nalog.ru обращаются и другие процессы машины. Живая скорость первого замера через compose — не больше ≈ 4,7 ИНН/мин (12 карточек pb, 147 запросов реестра МСП, 29 ГИР БО за 34 мин; `scripts/cache_rate.py`; `eval/results/night-rate-v1.json`), остальные 340 − 159 done — кеш top-200; Электронный магазин в очередь не входит (D-061). РНП ЕИС воркер не спрашивает: `enrich()` читает его только из кеша (#111), РНП — отдельный проход `prefetch --rnp` по шорт-листу (Crawl-delay 60 с, не больше 1 ИНН/мин).

### Как искали и проверяли (предзащита, #122)

Для вопросов «какие источники, сколько набрали, как понимали, где искать, как проверяли». Числа — из
`eval/results/*.json`; таблица по кешу — `uv run python -m src.eval.source_table S-sources-v1`.

- **Где искали.** Не там, где поставщиков много, а в «тонких» категориях ОКПД2 (D-095): группа `XX.XX`, где
  в Электронном магазине не менее 50 лотов, у половины лотов одна оферта и меньше 25 поставщиков на 100 лотов
  (`uv run python -m src.eval.thin T-thin-v1` — 47 групп). Источник новых компаний — реестр МСП ФНС
  (rmsp.nalog.ru): СПб и ЛО, основной ОКВЭД = класс ОКПД2 группы, для товаров ещё оптовый код (таблица `WHOLESALE`,
  D-036, D-071 — наше правило, официального ключа ОКПД2 → ОКВЭД2 нет).
- **Как понимали.** Один запрос на (ОКВЭД, регион), первая страница реестра (10 строк), пауза ≥ 1 с, всё через
  `SourceCache`; отказ (403/429/капча) — остановка без обхода. Живых запросов за задачу: 40, в кеше 38 ответов,
  2 таймаута; время ответа реестра — 01.10.2026 (`dtQueryEnd`, не дата обновления реестра).
- **Как проверяли.** (1) ИНН проходит контрольные цифры; (2) запись действующая в реестре МСП (исключённые
  отсеиваются — 196 из 360 строк); (3) ИНН буквально есть в закешированной странице (Evidence,
  `src/enrich/evidence.py`); (4) компании нет в `suppliers.parquet` организаторов — иначе она «уже известна», а не
  «новая». Ограничение: статус по карточке ФНС, ГИР БО и РНП для найденных компаний не запрашивался.
- **Чего не утверждаем.** Количество — не цель: сколько найдено, показываем «было → стало» по группам
  (`T-disc-v1`), а подходят ли компании под предмет закупки, не измерено (разметка #21, судья #82).
- **Свежесть.** Таблица источников показывает `fetched_at` (мин…макс) и дату реестра по каждому источнику; пустой
  кеш источника — строка нулей с пометкой, а не число. Электронный магазин и АИС ГЗ — первоисточник данных
  организаторов, в таблице строка «сверка», а не источник новых (D-061).

Открытые данные ФНС (#59, D-130): `python -m src.sources.fns_opendata download && python -m src.sources.fns_opendata build`, факты по ИНН — `python -m src.enrich.fns_lookup <ИНН>`. Покрытие поставщиков организаторов (нужны `data/processed/suppliers.parquet` и `fns_opendata.parquet`): `uv run python -c "import duckdb; S='data/processed/suppliers.parquet'; F='data/processed/fns_opendata.parquet'; print(duckdb.sql(f\"SELECT length(inn) AS len, count(*) AS suppliers, count(*) FILTER (WHERE inn IN (SELECT inn FROM read_parquet('{F}'))) AS in_fns FROM read_parquet('{S}') WHERE inn_valid GROUP BY 1 ORDER BY 1\"))"` — 10 цифр: 20 589 / 18 423, 12 цифр (ИП): 23 585 / 0.

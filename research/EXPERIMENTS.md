# EXPERIMENTS — гипотезы и таблица экспериментов

Источник: разделы 8 и 9 `docs/source/hackathon-research-workflow.md`. Процесс — скилл `experiment`.
Любая цифра — из `make eval EXP=<id>` → `eval/results/<id>.json`; «из головы» не пишем.

## Гипотеза — пять строк

Образец (из workflow, не наш эксперимент):

```text
H-07 | Наблюдение: baseline популярности обыгрывает нас в категории канцтоваров
     | Изменение: затухание experience по давности контрактов
     | Почему поможет: активные поставщики вытеснили ушедших с рынка
     | Минимальная проверка: backtest на текущем split, 5 минут
     | Критерий успеха: MRR +0.03, ни одна категория не просела
```

## Правила

- Один эксперимент — одна концептуальная переменная. Меняешь несколько — объясни почему.
- Приоритет ≈ ожидаемый gain × вероятность успеха / стоимость. Сначала дешёвые с большим gain.
- Задача > ~5 минут compute или > ~100 внешних запросов — оцени время, сначала подвыборка.
- Отрицательный результат записывается так же, как положительный. Отвергнутые не удаляются.
- **Три эксперимента подряд без прогресса — стоп тюнингу**: error analysis на 20–30 ошибках
  (`research/ERROR_ANALYSIS.md`), потом новые гипотезы.
- Существующий код — не истина: если eval показывает, что подход хуже альтернативы, — замена через `DECISIONS.md`.
- После чек-поинта 1 большинство гипотез — из error analysis и фидбека экспертов, а не из головы.
- Разница в пару пунктов на десятке запросов — шум: смотри bootstrap-интервалы.

## Вопросы скептика (перед KEEP)

- Не утечка ли: не видит ли модель будущее или саму тестовую закупку?
- Не судит ли LLM собственную выдачу?
- Держится ли улучшение на большинстве запросов или на одном?
- Не подняли ли метрику backtest ценой блока новых поставщиков?
- Увидит ли это жюри в демо?

## Гипотезы

- H-15a (#22): инкумбент-сигнал — участие в лотах того же заказчика до as_of — поднимает recall@10 против `bm25-dev-v1` (после #15 планка — B-bm25 0.449; на срезе «знакомый заказчику» текущий метод уступает B-inc 0.096 — здесь сигнал и должен сработать). Опция `signals.incumbent` (`src/match/signals.py`), по умолчанию 0. Прогоны: `signals.incumbent` = 0.3 и 0.6, `make eval EXP=H-15a-03|H-15a-06`.
- H-15c (#15 → #22): у ИП КПП нет или стоит заглушка `000000000`, `geography` = 0, и ИП из СПб проигрывает 0.1 балла любой организации с КПП 78. Для обоих случаев регион ИП — по первым двум цифрам ИНН (78/47; это регион выдачи ИНН) с пометкой в объяснении. Из 96 потерянных ИП с geography = 0: без КПП 33, с нулевым КПП 61, другой регион 2; ИНН 78/47 у 63, из них до балла 10-го места дотягиваются 48 — верхняя оценка эффекта (`uv run python -m src.eval.lost E-002 B-bm25`, блок `geography`). Изменение расчёта компоненты — дефолт только с подтверждением человека №3.
- H-15d (#15 → #22): `experience` и `activity` насыщаются у крупных поставщиков класса и перевешивают текстовую близость. Варианты: больший вес product_fit; BM25 как тай-брейк вместо ИНН (28 из 375 потерянных выпали при равном балле, `tie_by_inn`); RRF порядка BM25 и порядка по компонентам. Планка — B-bm25 (recall@10 0.449), а не `bm25-dev-v1`.
- H-15e (#22): `experience` по группе ОКПД2 награждает любого крупного поставщика класса; опыт по лотам с похожими позициями (те, что нашёл ретривер) ближе к «поставлял именно это». Опция `options.experience_by: similar`.
- H-15f / H-15g (#22): параметры подобраны офлайн-перебором по признакам кандидатов на **всех 2 000 dev-кейсах** (скрипт перебора в репозиторий не вошёл — его промежуточные цифры здесь не приводятся; в таблице только то, что воспроизводится `make eval`). Что из перебора проверено отдельными прогонами: experience по похожим позициям — главный выигрыш (H-15e); ненулевой вес geography снижает recall даже с регионом ИП по ИНН (H-15f-geo против H-15f: −0.013 [−0.020, −0.007]). Подбор на одной половине dev с проверкой на другой не делался — честная проверка против подгонки только `make eval-final` на holdout. Конфигурации — `configs/experiments.yaml`.
- H-15b (#22): веса — product_fit 0.5 / experience 0.25 / activity 0.15 / geography 0.1 против D-004. Только правкой `weights` в конфигурации эксперимента; дефолт меняется лишь с подтверждением человека №3.
- H-104 (#104, фидбек ЧП1): веса зависят от типа закупки — для услуг география не влияет, для товаров влияет. Тип — по классу ОКПД2 запроса (`src/match/profiles.py`: товар 01–32, 35; работы/услуги 33, 36–99), профиль — `weights_by_type` поверх `weights`, по умолчанию выключен. Проверка — срез `type=goods|services` в `make eval` и `src.eval.compare`: вес географии 0.05 только у товаров (H-104b, H-104g) и у обоих типов (H-15f-geo) против 0.
- L-okved-link (#250, идея IR630 в #77): официального ключа ОКПД2 ↔ ОКВЭД нет, а ручная таблица оптовых кодов (D-036, `WHOLESALE`) — 31 строка. Наблюдение: поставщики класса — в основном торговые компании (46.x, 47.x), а не производители с ОКВЭД = классу. Изменение: связь считается по истории — основной ОКВЭД поставщиков класса в пуле МСП (#185) до `cutoff`, отбор по lift. Почему поможет: для редкого класса строки в ручной таблице нет, а история называет его торговые ОКВЭД. Минимальная проверка: холодные победители dev (нет в train, есть в пуле) — попал ли их основной ОКВЭД в отобранные, при каком размере набора кандидатов СПб+ЛО. Критерий успеха: доля выше D-036 при сопоставимом размере набора, интервал Δ не накрывает 0.

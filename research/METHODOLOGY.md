# METHODOLOGY v0 — как считается релевантность

Источник: раздел 5 `docs/source/hackathon-research-workflow.md`. Владелец — MATCH. Это же
слайд «методология» (пункт 3 условий).

Прозрачная взвешенная модель, а не чёрный ящик: жюри из госзаказа должно понимать каждую
компоненту. **Изменение формулы или состава компонент — подтверждение человека №3** (CLAUDE.md):
это слайд. Подстройка весов на backtest — эксперимент (`research/EXPERIMENTS.md`), не смена методологии.

## Шаг 1. Понимание запроса

- Нормализация текста: регистр, ё→е, единицы, числа, лемматизация.
- ОКПД2/КТРУ не указаны → код предсказывается по ближайшим позициям истории (голосование по префиксу).
- Разбор ТЗ на позиции и характеристики LLM — только если хватит времени и API разрешён
  (`[ОБНОВИТЬ 01.10]` разрешённые провайдеры; режим без LLM обязателен, `src/llm/provider.py`).

## Шаг 2. Кандидаты из двух источников

- **Из данных организаторов** — контрагенты, которые поставляли или предлагали похожие позиции.
  Лестница: BM25 по наименованиям (`bm25s`) → совпадение ОКПД2 по префиксу → гибрид с
  эмбеддингами через Reciprocal Rank Fusion. **Следующая ступень остаётся, только если
  выиграла на eval** (`make eval EXP=<id>`, research/EVAL.md). Текущая ступень —
  `retriever` в `configs/search.yaml` (сейчас `stub`).
- Кандидаты эмбеддинг-моделей для 20-минутного бенчмарка: `intfloat/multilingual-e5-small/base/large`,
  `BAAI/bge-m3`, `deepvk/USER-bge-m3`, `ai-forever/FRIDA`. Скачиваются заранее `make models`
  (Wi-Fi площадки ненадёжен), ставятся `make setup-ml`. **[ПРОВЕРИТЬ скорость на наших
  ноутбуках; для e5 нужны префиксы `query: ` и `passage: `]**.
- **Из открытых источников** — компании, которых нет в данных (research/SOURCES.md).

## Шаг 3. Жёсткие фильтры

Юрлицо действует; его нет в РНП; фильтры пользователя (только СМП, регион, только
производители). Реализация — `src/match/filters.py`; отсутствующее значение не угадываем, а
показываем «не проверено».

## Шаг 4. Скоринг по компонентам, каждая в [0, 1]

| Компонента | Что измеряет | Откуда берётся |
|---|---|---|
| `product_fit` | поставляет ли контрагент именно это | сходство запроса с позициями его истории или каталога, глубина совпадения ОКПД2 |
| `experience` | опыт в категории | число и сумма релевантных контрактов с затуханием по давности; опыт с заказчиками СПб |
| `reliability` | риск срыва | статус, возраст, РНП, доля расторжений, отчётность |
| `activity` | ответит ли на приглашение | дата последней оферты или контракта |
| `geography` | логистика | СПб и Ленинградская область |
| `price` | конкурентность цены | среднее снижение от НМЦК в истории, если такие данные есть |

`score = Σ wᵢ · componentᵢ`

Стартовые экспертные веса (D-004, `configs/search.yaml`), подстраиваются на backtest:

| product_fit | experience | reliability | activity | geography | price |
|---|---|---|---|---|---|
| 0.35 | 0.20 | 0.20 | 0.10 | 0.10 | 0.05 |

Веса видны в интерфейсе; если хватит времени — 2–3 пресета («надёжность важнее», «широкий охват»).
Какие компоненты реально вычислимы по данным — `[ОБНОВИТЬ 01.10]` после профиля (например, `price`
требует НМЦК и цены контракта).

## Шаг 5. Объяснение

Для каждой компоненты — строка на человеческом языке (`ScoreComponent.explanation`, заполнять с
самого начала) и ссылка на evidence. Пример: «12 контрактов по ОКПД2 32.50.13 за 2 года, из них
9 с заказчиками СПб (данные АИС ГЗ)».

## Ловушка инкумбентов

Модель, настроенная только на историю, ставит наверх тех, кто и так выигрывает, — это
противоречит цели найти больше поставщиков. Поэтому в выдаче два блока — «С опытом госзакупок»
(`origin=history`) и «Новые из открытых источников» (`origin=discovered`), и качество каждого
оценивается отдельно (research/EVAL.md: блок A и блок B).

## Запасной вариант

Если эмбеддинги не выиграли или не успели: BM25 + ОКПД2-префикс, компоненты
`product_fit`, `experience`, `reliability`, `activity` — уже закрывает пункт 3 условий.

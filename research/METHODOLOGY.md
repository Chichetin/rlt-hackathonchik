# METHODOLOGY v0 — как считается релевантность

Источник: раздел 5 `docs/source/hackathon-research-workflow.md`. Владелец — MATCH. Это же
слайд «методология» (пункт 3 условий).

Прозрачная взвешенная модель, а не чёрный ящик: жюри из госзаказа должно понимать каждую
компоненту. **Изменение формулы или состава компонент — подтверждение человека №3** (CLAUDE.md):
это слайд. Подстройка весов на backtest — эксперимент (`research/EXPERIMENTS.md`), не смена методологии.

## Шаг 1. Понимание запроса

- Нормализация текста: регистр, ё→е, единицы, числа, лемматизация.
- ОКПД2/КТРУ не указаны → код предсказывается по ближайшим позициям истории (голосование по префиксу).
- Разбор ТЗ на позиции и характеристики LLM — только если хватит времени и API разрешён
  (`[СПРОСИТЬ Q-13]` разрешённые провайдеры; режим без LLM обязателен, `src/llm/provider.py`).

## Шаг 2. Кандидаты из двух источников

- **Из данных организаторов** — контрагенты, которые поставляли или предлагали похожие позиции.
  Лестница: BM25 по наименованиям (`bm25s`) → совпадение ОКПД2 по префиксу → гибрид с
  эмбеддингами через Reciprocal Rank Fusion. **Следующая ступень остаётся, только если
  выиграла на eval** (`make eval EXP=<id>`, research/EVAL.md). Текущая ступень —
  `retriever` в `configs/search.yaml` (сейчас `bm25`, v1 — ниже, «Реализация v1»).
- Кандидаты эмбеддинг-моделей для 20-минутного бенчмарка: `intfloat/multilingual-e5-small/base/large`,
  `BAAI/bge-m3`, `deepvk/USER-bge-m3`, `ai-forever/FRIDA`. Скачиваются заранее `make models`
  (Wi-Fi площадки ненадёжен), ставятся `make setup-ml`. **[ПРОВЕРИТЬ скорость на наших
  ноутбуках; для e5 нужны префиксы `query: ` и `passage: `]**.
- **Из открытых источников** — компании, которых нет в данных (research/SOURCES.md).

## Шаг 3. Жёсткие фильтры

Юрлицо действует; его нет в РНП; фильтры пользователя (только СМП, регион, только
производители). Реализация — `src/match/filters.py`; отсутствующее значение не угадываем, а
показываем «не проверено».

## Шаг 4. Скоринг по компонентам, каждая в [0, 1]

| Компонента | Что измеряет | Откуда берётся |
|---|---|---|
| `product_fit` | поставляет ли контрагент именно это | сходство запроса с позициями его истории или каталога, глубина совпадения ОКПД2 |
| `experience` | опыт в категории | число и сумма релевантных контрактов с затуханием по давности; опыт с заказчиками СПб |
| `reliability` | риск срыва | статус, возраст, РНП, доля расторжений, отчётность |
| `activity` | ответит ли на приглашение | дата последней оферты или контракта |
| `geography` | логистика | СПб и Ленинградская область |
| `price` | конкурентность цены | среднее снижение от НМЦК в истории — по плану; на наших данных не вычислимо (нет цены контракта), см. ниже |

`score = Σ wᵢ · componentᵢ`

Стартовые экспертные веса (D-004, `configs/search.yaml`), подстраиваются на backtest:

| product_fit | experience | reliability | activity | geography | price |
|---|---|---|---|---|---|
| 0.35 | 0.20 | 0.20 | 0.10 | 0.10 | 0.05 |

Веса видны в интерфейсе; если хватит времени — 2–3 пресета («надёжность важнее», «широкий охват»).
Что из этой таблицы реально вычислимо на данных организаторов — раздел «Что вычислимо на наших
данных» ниже. Данные: оферты и победители с ИНН, НМЦК, ОКПД2 позиций, заказчик, канал (ЭМ / АИС ГЗ);
**нет**: названий и контактов поставщиков, цены контракта, исполнения и расторжений
(`research/DATA_DICTIONARY.md`).

## Шаг 5. Объяснение

Для каждой компоненты — строка на человеческом языке (`ScoreComponent.explanation`, заполнять с
самого начала) и ссылка на evidence. Пример: «12 контрактов по ОКПД2 32.50.13 за 2 года, из них
9 с заказчиками СПб (данные АИС ГЗ)».

## Ловушка инкумбентов

Модель, настроенная только на историю, ставит наверх тех, кто и так выигрывает, — это
противоречит цели найти больше поставщиков. Поэтому в выдаче два блока — «С опытом госзакупок»
(`origin=history`) и «Новые из открытых источников» (`origin=discovered`), и качество каждого
оценивается отдельно (research/EVAL.md: блок A и блок B).

## Реализация v1 (T-02, #9; D-029)

Код — `src/match/search.py`, индекс — `src/match/index.py`, тесты — `tests/unit/test_search.py`.

- **Токены**: регистр, ё→е, слова и числа (`\w+`), без предлогов; слово обрезается до 5 букв
  («бумага», «бумаги» → «бумаг»), кириллическая «А4» = латинская «A4». PyStemmer в lockfile нет —
  настоящий стеммер или лемматизация — эксперимент.
- **Индекс**: документ — различный текст среди `ТРУ.product_name` и `Извещения.subject` лотов,
  у которых есть участники **строго до `as_of`** (в продукте — все данные). Строится один раз и
  кешируется в `indexes/` (ключ — manifest ingest + `as_of` + версия токенизатора); заранее —
  `uv run python -m src.match.index` (продукт и cutoff split).
- **Кандидаты**: топ-500 документов BM25 → их лоты → участники этих лотов (Поставщики) → топ-200
  поставщиков по лучшему BM25 их лотов → скоринг → топ-k. Все — `origin=history`.
- **ОКПД2 запроса**: `Query.okpd2`; если пусто — голосуют позиции, которые сами совпали с запросом
  (100 лучших текстов, вес — BM25, один голос на текст): сначала группа `XX.XX`, затем код внутри неё;
  предмет лота голосует, только если не совпала ни одна позиция (D-045; в объяснении: «определён по
  похожим позициям»).

| Компонента | Значение в [0, 1] | Объяснение (пример) |
|---|---|---|
| `product_fit` | 0.6 · BM25/BM25 лучшего кандидата + 0.4 · глубина ОКПД2 (код 1.0, подкатегория XX.XX.XX 0.75, группа XX.XX 0.5, класс XX 0.25, нет 0); без ОКПД2 — только BM25 | «Похожие позиции в 4 лот(ах), лучшее совпадение «Бумага офисная А4» (лот 6); ОКПД2 запроса: совпадает код 17.12.14.110» |
| `experience` | 0.5 · min(1, ln(1+лоты)/ln 21) + 0.5 · min(1, ln(1+победы)/ln 11) — лоты и победы в группе ОКПД2 (XX.XX) запроса до `as_of`; без ОКПД2 — по лотам с похожими позициями | «4 лот(ов) по ОКПД2 17.12 за весь период данных, из них побед: 2» |
| `activity` | 0.5^(дней/90) от последнего участия до `as_of` (в продукте — до конца данных) | «Последнее участие 15.10.2025 — 0 дн. до конца данных» |
| `geography` | регион КПП = регион запроса — 1.0; соседний (78 ↔ 47) — 0.8; иначе или КПП нет (ИП) — 0 | «КПП 780101001: на налоговом учёте в Санкт-Петербурге» |
| `reliability` | качество поставщика по истории до `as_of` (раздел «reliability» ниже, #72); режим `reliability.mode`: по умолчанию `shadow` — считается и показывается, **weight 0**, в score не входит | «Побед 3 из 3 лот(ов) — 75% с поправкой на малую выборку (у похожих поставщиков 60%); повторные победы у 1 из 2 заказчик(ов) с победой; …» |
| `price` | **нет данных**: value 0, weight 0 — в score не входит (D-029) | «Нет данных: …» |

`score = Σ weight · value` по показанным компонентам; веса — `configs/search.yaml` (D-004), у
компонент без данных вес в ответе 0, поэтому score сверяется с карточкой арифметикой. Максимум
сейчас 0.75 (сумма весов посчитанных компонент); порядок выдачи тот же, что у формулы D-004 с
нулём на месте отсутствующих компонент. Константы (0.6/0.4, 20 лотов, 10 побед, 90 дней, 0.8) —
экспертные, подстраиваются только экспериментом.

К каждому кандидату добавляется факт `Evidence(source="data:items", url="data:items#<лот>")` —
лот с лучшим совпадением; ИНН — Evidence загрузчика (`data:participants`). Невалидный ИНН —
«ИНН не подтверждён». Тип (производитель/дистрибьютор), МСП, статус — только из `enrich()`:
фильтры по ним без данных отбрасывают, а не угадывают, и UI говорит, у скольких признак неизвестен;
фильтр «регион» — по реестру, иначе по префиксу КПП (D-030). Eval передаёт `as_of = cutoff` split
(`src/eval/run.py::with_cutoff`; кейс с `as_of` позже cutoff — ошибка).

### `price`: что можно вычислить честно

Не вычислимо вообще: снижение цены относительно НМЦК, демпинг, «конкурентность цены» — нужна цена
контракта или ценовое предложение, их в выгрузке нет. Вычислимо только **типичный масштаб закупок
поставщика**: в данных есть НМЦК лотов, где он участвовал или побеждал, и `Query.budget` запроса.
Сейчас `suppliers.median_start_price` (`src/ingest/build.py:184`) — медиана НМЦК по всей истории
поставщика, а не по группе ОКПД2; статистики по группе в коде нет, её пришлось бы добавить.
Для backtest НМЦК берутся строго до `as_of`, иначе утечка во времени. Это не цена и не «выгодность», а
ответ на вопрос «закупки такого размера для него обычны?». **Не реализовано — ПРЕДЛОЖЕНИЕ**
(раздел «На подтверждение человеку»). Ограничения: масштабы ЭМ (медиана НМЦК 55 000 ₽) и АИС ГЗ
(167 172 ₽) различаются (`DATA_DICTIONARY.md`); выбросы НМЦК до десятков миллиардов — нужна
устойчивая оценка (медиана или квантили).

## Жёсткие фильтры — отдельно от балла

Фильтры не меняют score, а убирают кандидата (`src/match/filters.py:30-45`, `apply_filters`): ликвидация,
банкротство, прекращение деятельности по `Counterparty.status` и `in_rnp is True` — всегда;
«только СМП», «только производители», регион — по желанию пользователя. По D-030 фильтр
пользователя оставляет только подтверждённые совпадения: неизвестный МСП / тип отбрасывается, а
UI пишет, у скольких кандидатов признак неизвестен. Регион — реестр (`Counterparty.region`), иначе
префикс КПП 78 / 47. Отсутствующий статус или РНП кандидата не отбрасывает («не проверено»).
Статус, РНП, МСП и тип поставщика приходят из `enrich()`, а не из данных организаторов.

## reliability — качество поставщика (#72, D-058)

Вопрос компоненты: не «подходит ли по товару», а «**хороший ли это поставщик**». Явной метки
качества в данных нет (исполнения, расторжений, штрафов, жалоб нет), поэтому — косвенные сигналы,
**все строго до `as_of`** (`Store.supplier_history`, один SQL для parquet и Postgres).

**Старые поставщики** (есть история в данных организаторов), `reliability = Σ wᵢ · sᵢ`:

| Сигнал | Вес | sᵢ в [0, 1] | Что значит |
|---|---|---|---|
| `win_rate` | 0.35 | (победы + 5 · p₀) / (лоты + 5), p₀ — общая доля побед кандидатов этого запроса (похожие поставщики) | конкурентоспособность; Beta-сглаживание: 1 из 1 — не 1.0 |
| `retention` | 0.25 | (заказчики с ≥ 2 победами + 3 · r₀) / (заказчики с победой + 3), r₀ — та же доля у кандидатов запроса | заказчик вернулся — лучший доступный прокси удовлетворённости |
| `breadth` | 0.20 | min(1, ln(1 + заказчики) / ln 21) | широта репутации, не «карманный» поставщик одного заказчика |
| `tenure` | 0.20 | 0.5 · min(1, мес. с первого участия / 12) + 0.5 · активные мес. / мес. с первого участия | стаж в данных и регулярность |

Объяснение в карточке — одна строка с числами (фикстура `tests/fixtures/ingest`, ИНН 7801000012,
запрос «бумага офисная», `as_of` 01.07.2025): «Побед 3 из 3 лот(ов) — 75% с поправкой на малую
выборку (у похожих поставщиков 60%); повторные победы у 1 из 2 заказчик(ов) с победой; всего
заказчиков 2; в данных с 01.2024, активен 3 из 18 мес.». Месяцы считаются по день перед `as_of`. Повторные победы — это и «доволен», и
«узкий круг» (F-04): в формуле это качество, а не причина поднимать старых над новыми — блоки
«С опытом» и «Новые» ранжируются раздельно.

**Новые поставщики** (истории нет): только реестровая часть из того, что `enrich()` положил в
`Counterparty` (`registry_reliability`): статус действующий — 1 / иначе 0 (вес 0.4), в РНП нет — 1 /
есть — 0 (0.3), возраст по году записи из подтверждённого ОГРН (цифры 2–3), min(1, лет / 5) (0.3).
Неизвестные сигналы пропускаются с перенормировкой весов; не известно ничего — **«Не проверено»**,
value не выдумывается. Подключение в блок «Новые» — `src/enrich/discover.py` (область SOURCES),
отдельной задачей; там сейчас reliability = 0 с весом 0.

**Не используется**: масштаб (НМЦК — не цена контракта), лоты ЭМ без победителя (смысл не ясен,
[ПРОВЕРИТЬ], вопрос организаторам), МСП (это не качество). Жёсткие фильтры (ликвидация, РНП) —
отдельно от балла, не тронуты.

**Переключатель** `configs/search.yaml`, `reliability.mode`: `off` — как v1 (D-029); `shadow`
(по умолчанию) — value и объяснение в карточке, weight 0, score и порядок не меняются (тест

## На подтверждение человеку (№3)

- Сейчас: `score = Σ weight · value` по 4 вычислимым компонентам, веса `configs/search.yaml`
  0.35 / 0.20 / 0.10 / 0.10 (product_fit / experience / activity / geography), максимум 0.75;
  `reliability` (0.20) и `price` (0.05) показываются с нулём и «нет данных» (D-029).
- Предложение 1: `price = max(0, 1 − |ln(budget / median_nmck)| / ln 10)`, где `median_nmck` —
  медиана НМЦК лотов поставщика (в группе ОКПД2, строго до `as_of`; такой статистики в коде пока
  нет, сейчас есть медиана по всей истории); константа ln 10 — экспериментом; это близость
  масштаба, не «снижение цены»; зачем — задействовать единственный ценовой
  сигнал в данных; измерим `make eval EXP=<id>` против B-pop / B-inc / B-bm25 (#15) и `bm25-dev-v1` на dev.
- Предложение 2 (#72, D-058): включить `reliability` в score — `reliability.mode: on`, вес 0.20 из
  D-004; формула и сигналы — раздел «reliability» выше (история до `as_of` для старых, реестровая
  часть для новых, «не проверено» без данных). Сейчас `shadow`: показывается в карточке с весом 0.
  Решение — по eval `rel-on` против `rel-off` (раздел «reliability», `research/EXPERIMENTS.md`).
- Блок «Новые из открытых источников» (#16, D-036) — экспертное правило v0, **не измерено**: та же

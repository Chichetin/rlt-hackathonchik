# METHODOLOGY v0 — как считается релевантность

Источник: раздел 5 `docs/source/hackathon-research-workflow.md`. Владелец — MATCH. Это же
слайд «методология» (пункт 3 условий).

Прозрачная взвешенная модель, а не чёрный ящик: жюри из госзаказа должно понимать каждую
компоненту. **Изменение формулы или состава компонент — подтверждение человека №3** (CLAUDE.md):
это слайд. Подстройка весов на backtest — эксперимент (`research/EXPERIMENTS.md`), не смена методологии.

## Шаг 1. Понимание запроса

- Нормализация текста: регистр, ё→е, единицы, числа, лемматизация.
- ОКПД2/КТРУ не указаны → код предсказывается по ближайшим позициям истории (голосование по префиксу).
- Разбор ТЗ на позиции и характеристики LLM — только если хватит времени и API разрешён
  (Q-13, D-133: сторонние API нельзя, локальная модель можно; режим без LLM обязателен, `src/llm/provider.py`).

## Шаг 2. Кандидаты из двух источников

- **Из данных организаторов** — контрагенты, которые поставляли или предлагали похожие позиции.
  Лестница: BM25 по наименованиям (`bm25s`) → совпадение ОКПД2 по префиксу → гибрид с
  эмбеддингами через Reciprocal Rank Fusion. **Следующая ступень остаётся, только если
  выиграла на eval** (`make eval EXP=<id>`, research/EVAL.md). Текущая ступень —
  `retriever` в `configs/search.yaml` (сейчас `bm25`, v1 — ниже, «Реализация v1»).
- Кандидаты эмбеддинг-моделей для 20-минутного бенчмарка: `intfloat/multilingual-e5-small/base/large`,
  `BAAI/bge-m3`, `deepvk/USER-bge-m3`, `ai-forever/FRIDA`. Скачиваются заранее `make models`
  (Wi-Fi площадки ненадёжен), ставятся `make setup-ml`. **[ПРОВЕРИТЬ скорость на наших
  ноутбуках; для e5 нужны префиксы `query: ` и `passage: `]**.
- **Из открытых источников** — компании, которых нет в данных (research/SOURCES.md).

## Шаг 3. Жёсткие фильтры

Юрлицо действует; его нет в РНП; фильтры пользователя (только СМП, регион, только
производители). Реализация — `src/match/filters.py`; отсутствующее значение не угадываем, а
показываем «не проверено».

## Шаг 4. Скоринг по компонентам, каждая в [0, 1]

| Компонента | Что измеряет | Откуда берётся |
|---|---|---|
| `product_fit` | поставляет ли контрагент именно это | сходство запроса с позициями его истории или каталога, глубина совпадения ОКПД2 |
| `experience` | опыт в категории | число и сумма релевантных контрактов с затуханием по давности; опыт с заказчиками СПб |
| `reliability` | риск срыва | статус, возраст, РНП, доля расторжений, отчётность |
| `activity` | ответит ли на приглашение | дата последней оферты или контракта |
| `geography` | логистика | СПб и Ленинградская область |
| `price` | конкурентность цены | среднее снижение от НМЦК в истории — по плану; на наших данных не вычислимо (нет цены контракта), см. ниже |

## Как выбраны веса (#104)

**Принцип — три шага на каждый вес.** (1) Стартовая точка — экспертный вес по смыслу компоненты (D-004):
чем прямее компонента отвечает на вопрос заказчика «поставлял ли он именно это», тем больше вес. (2) Проверка
на backtest: 2 000 dev-лотов до cutoff, кого метод ставит в топ-10 против тех, кто реально подал заявку и
выиграл (recall@10, парный bootstrap, `research/EVAL.md`), **отдельно по срезам** — товары / услуги, канал
ЭМ / АИС ГЗ, новый / знакомый заказчику. (3) Правку оставляем, если на dev она не хуже в целом и ни в одном
срезе не хуже значимо; итог проверяется вне выборки подбора (#145) и один раз на holdout (`make eval-final`).

| Вес | Было (D-004) → сейчас (D-077) | Почему такой — одной фразой | Чем проверено |
|---|---|---|---|
| `product_fit` | 0.35 → 0.762 | главный вопрос заказчика — «поставлял ли именно это»; текстовая близость позиций — самый сильный сигнал данных | B-bm25 (порядок по одному тексту) 0.449 выше v1 0.382; H-15f 0.490 (`research/EXPERIMENTS.md`) |
| `experience` | 0.20 → 0.190 | опыт по **похожим позициям**, а не по всей группе ОКПД2: «поставлял это», а не «крупный в классе» | H-15e: +0.044 [+0.033, +0.054] к v1, и «новым», и «знакомым» |
| `activity` | 0.10 → 0.048 | «ответит ли на приглашение» — слабый признак, только различает равных по предмету | насыщается у крупных поставщиков (H-15d), с большим весом вытесняет текст |
| `geography` | 0.10 → 0 (показывается) | по смыслу — логистика; на рынке СПб почти все участники из СПб и ЛО, компонента не различает кандидатов, а штрафует иногородних победителей | H-15f-geo −0.013 [−0.020, −0.007]; по срезам — ниже |
| `reliability`, `price` | 0.20, 0.05 → 0 | в выгрузке нет статусов, РНП, цены контракта — 0 и «нет данных» вместо выдуманного значения | D-029 |

**Профили по типу закупки** (фидбек ЧП1: «для услуги география не влияет, для товара влияет»). Тип — по классу
ОКПД2 запроса, явного или предсказанного (`src/match/profiles.py`): **товар** — классы 01–32 и 35 (разделы
A–D, включая электроэнергию и газ), **работы/услуги** — 33 («Услуги по ремонту и монтажу машин и оборудования»
внутри раздела C) и 36–99; смесь товаров и услуг в одном лоте или нераспознанный код — общий набор весов, и
объяснение говорит почему. Доли в данных (604 436 лотов ТРУ): товары 52.4 %, услуги 47.0 %, смешанные или без
кода 0.6 %; dev-выборка — 1 169 / 823 / 8. Профиль — правки поверх `weights` (`weights_by_type` в
`configs/search.yaml`, **по умолчанию пусто**); при включённом профиле строка «География» в карточке
заканчивается так: «профиль весов «услуга» (ОКПД2 запроса, класс 43): география не учитывается».

Гипотезу эксперта проверили в обе стороны — вес географии 0.05 (с регионом ИП по ИНН) только у одного типа
(dev 2 000, recall@10, парный bootstrap):

| Срез | География 0.05 → 0, Δ recall@10 | Команда |
|---|---|---|
| товары (1 169) | вес 0.05 хуже, чем 0: 0.435 → 0.420, −0.015 [−0.024, −0.007] | `uv run python -m src.eval.compare H-104b H-15f` |
| услуги (823) | вес 0.05 хуже, чем 0: 0.568 → 0.557, −0.011 [−0.020, −0.002] | `uv run python -m src.eval.compare H-15f-geo H-104b` |

**Вывод:** на данных СПб география снижает качество и у товаров, и у услуг, поэтому оба профиля совпадают с
D-077 (география 0, показывается в карточке), а механизм профилей остаётся выключенной опцией: он включается
одной строкой конфигурации, если на других данных (другой регион, межрегиональные поставки) срез покажет
обратное. Ограничения: при весе 0.05 проверено одно значение; на 8 реальных кейсах вес 0.05 для товаров поднял
один кейс из пяти товарных (0 → 1), интервал широкий (`eval/results/H-104b-real.json`). Решение — D-099.

## Шаг 4б. Порядок задаёт обученный ранжировщик (с 02.10, D-103, #198)

Компоненты шага 4 считаются как прежде и показываются в карточке, но **порядок в выдаче задаёт модель**:
LightGBM LambdaMART (`src/match/ranker.py`, `configs/search.yaml` → `ranker:`), обученный на истории закупок
СПб. Её входы — 44 признака кандидата: значения компонент v2, BM25, лоты и победы с похожими позициями и в
группе ОКПД2, лоты у этого заказчика, давность участия, регион, разница НМЦК и типичной цены его лотов,
профиль поставщика (#114) и канал. **Балл остаётся на шкале формулы** (Σ wᵢ · componentᵢ, D-077), но не выше,
чем у поставщика выше в списке: число не спорит с порядком, пороги релевантности, фильтр «минимальная
релевантность» и сравнение с блоком «Новые» работают как раньше; у первого балл равен сумме его критериев.
Сырой выход LambdaMART — не шкала релевантности (он ранжирует внутри запроса), на экран не идёт.

- **Без утечки.** Обучение — лоты [2025-04-01, 2025-07-01), признаки — только по истории до 2025-04-01 (индекс
  BM25 и агрегаты поставщиков на эту дату); dev [2025-07-01, 2025-10-01) при обучении не читается, ранняя
  остановка — на 15 % обучающих запросов (`src/match/ranker_train.py`).
- **Качество** (`eval/results/R-198-gbm.json`, `uv run python -m src.eval.compare R-198-gbm v2`): dev 2 000 —
  recall@10 0.491 → 0.572, Δ +0.081 [+0.069, +0.096]; MRR +0.105, nDCG@10 +0.091. Сложные срезы: «АИС ГЗ, новый
  для заказчика» (492) +0.091 [+0.061, +0.124]; сборные лоты (≥ 3 класса ОКПД2) +0.166; короткий текст (≤ 6 слов)
  +0.086; из 801 лота, где v2 не нашёл никого, ранжировщик находит участника в 21 %; там, где v2 находил,
  −0.007 [−0.017, +0.003] (шум). Где не помогает: «ЭМ, новый для заказчика» +0.015 [−0.009, +0.037] — шум.
- **Объяснение.** Вклад каждого признака в оценку модели — точный (SHAP деревьев, `pred_contrib`), не догадка.
  Карточка (`product_fit`) показывает три признака, которые подняли поставщика сильнее всего, и один, который
  тянул вниз, — со значениями (признак без данных доводом не бывает): «почему на этом месте — модель LightGBM, обученная на истории закупок (критерии —
  её входы): за — лоты у этого заказчика: 7; победы в группе ОКПД2: 12; …; против — давность последнего участия: 240 дн.».
  Интерфейс показывает это отдельным блоком «Почему на этом месте» над критериями (`src/ui/src/ranker.ts`).
- **Надёжность.** Нет файла модели, нет lightgbm или признаки модели не совпадают с кодом — порядок v2 (D-077)
  и заметка «ранжировщик недоступен — порядок по формуле v2»; поиск не падает. Лестница отката (#113) работает
  до ранжировщика: пустой запрос, нет ОКПД2, никого по тексту — как раньше.
- **Выключить:** `ranker: null` (запись `v2` в `configs/experiments.yaml`).

## Шаг 5. Объяснение

Для каждой компоненты — строка на человеческом языке (`ScoreComponent.explanation`, заполнять с
самого начала) и ссылка на evidence. Пример: «12 контрактов по ОКПД2 32.50.13 за 2 года, из них
9 с заказчиками СПб (данные АИС ГЗ)».

## Ловушка инкумбентов

Модель, настроенная только на историю, ставит наверх тех, кто и так выигрывает, — это
противоречит цели найти больше поставщиков. Поэтому в выдаче два блока — «С опытом госзакупок»
(`origin=history`) и «Новые из открытых источников» (`origin=discovered`), и качество каждого
оценивается отдельно (research/EVAL.md: блок A и блок B).

## Реализация (T-02 v1 → H-15f; D-029, D-077)

Код — `src/match/search.py`, индекс — `src/match/index.py`, тесты — `tests/unit/test_search.py`.
С D-077 (#174) дефолт — H-15f: текст важнее (`product_fit` 0.8 · BM25 + 0.2 · ОКПД2), опыт — по лотам с
похожими позициями, география показывается, но в балл не входит, равные баллы — по BM25. Механика v1
(опыт в группе ОКПД2, 0.6 / 0.4, равные — по ИНН) осталась опцией (`options` в `configs/search.yaml`) и
воспроизводится как `v1` в `configs/experiments.yaml`.

- **Токены**: регистр, ё→е, слова и числа (`\w+`), без предлогов; слово обрезается до 5 букв
  («бумага», «бумаги» → «бумаг»), кириллическая «А4» = латинская «A4». PyStemmer в lockfile нет —
  настоящий стеммер или лемматизация — эксперимент.
- **Индекс**: документ — различный текст среди `ТРУ.product_name` и `Извещения.subject` лотов,
  у которых есть участники **строго до `as_of`** (в продукте — все данные). Строится один раз и
  кешируется в `indexes/` (ключ — manifest ingest + `as_of` + версия токенизатора); заранее —
  `uv run python -m src.match.index` (продукт и cutoff split).
- **Кандидаты**: топ-500 документов BM25 → их лоты → участники этих лотов (Поставщики) → топ-200
  поставщиков по лучшему BM25 их лотов → скоринг → топ-k. Все — `origin=history`.
- **ОКПД2 запроса**: `Query.okpd2`; если пусто — голосуют позиции, которые сами совпали с запросом
  (100 лучших текстов, вес — BM25, один голос на текст): сначала группа `XX.XX`, затем код внутри неё;
  предмет лота голосует, только если не совпала ни одна позиция (D-045; в объяснении: «определён по
  похожим позициям»).

| Компонента | Значение в [0, 1] | Объяснение (пример) |
|---|---|---|
| `product_fit` | 0.8 · BM25/BM25 лучшего кандидата + 0.2 · глубина ОКПД2 (код 1.0, подкатегория XX.XX.XX 0.75, группа XX.XX 0.5, класс XX 0.25, нет 0); без ОКПД2 — только BM25 (v1: 0.6 / 0.4) | «Похожие позиции в 4 лот(ах), лучшее совпадение «Бумага офисная А4» (лот 6); ОКПД2 запроса: совпадает код 17.12.14.110» |
| `experience` | 0.5 · min(1, ln(1+лоты)/ln 21) + 0.5 · min(1, ln(1+победы)/ln 11) — лоты и победы среди лотов с похожими позициями до `as_of` (v1: в группе ОКПД2 XX.XX запроса) | «4 лот(ов) с похожими позициями за весь период данных, из них побед: 2» |
| `activity` | 0.5^(дней/90) от последнего участия до `as_of` (в продукте — до конца данных) | «Последнее участие 15.10.2025 — 0 дн. до конца данных» |
| `geography` | регион КПП = регион **заказчика** (с #218: по ИНН заказчика 78/47, иначе регион запроса — ИНН 77… у федеральных органов о месте поставки не говорит) — 1.0; соседний (78 ↔ 47) — 0.8; иначе или КПП нет (ИП) — 0. С D-077 вес 0: показывается в карточке, в балл не входит (регион КПП штрафовал ИП — `research/ERROR_ANALYSIS.md`) | «КПП 780101001: на налоговом учёте в Санкт-Петербурге» |
| `reliability`, `price` | **нет данных**: value 0, weight 0 — в score не входят (D-029) | «Нет данных: …» |

`score = Σ weight · value` по показанным компонентам; веса — `configs/search.yaml` (D-077: 0.762 / 0.190 /
0.048 / 0 — product_fit / experience / activity / geography), у компонент без данных вес в ответе 0, поэтому
score сверяется с карточкой арифметикой. Максимум 1.0 (веса нормированы); равные баллы — по BM25, затем по
ИНН. Константы (0.8/0.2, 20 лотов, 10 побед, 90 дней, 0.8) — экспертные, подстраиваются только экспериментом.

К каждому кандидату добавляется факт `Evidence(source="data:items", url="data:items#<лот>")` —
лот с лучшим совпадением; ИНН — Evidence загрузчика (`data:participants`). Невалидный ИНН —
«ИНН не подтверждён». Тип (производитель/дистрибьютор), МСП, статус — только из `enrich()`:
фильтры по ним без данных отбрасывают, а не угадывают, и UI говорит, у скольких признак неизвестен;
фильтр «регион» — по реестру, иначе по префиксу КПП (D-030). Eval передаёт `as_of = cutoff` split
(`src/eval/run.py::with_cutoff`; кейс с `as_of` позже cutoff — ошибка).

## Лестница отката (#113, D-072)

Код — `src/match/fallback.py`, тесты — `tests/unit/test_search_edge.py`. Включается **только когда
по тексту не нашлось ни одного кандидата** (опечатка, латиница, только предлоги, редкий товар):

1. **По смыслу** — векторный поиск названий (`pg_retriever`), если Postgres + pgvector отвечают;
   иначе ступень пропускается с записью в лог. Не используется, если ретривер уже `pg_hybrid`, в
   запросе нет слов, и в eval с `retriever: bm25`.
2. **По ОКПД2** (заданному в запросе) — участники лотов с этим кодом до `as_of`, чаще участвовал —
   выше.
3. **Подъём кода**: код → подкатегория XX.XX.XX → группа XX.XX → класс XX; на классе стоп.

У найденных откатом BM25-часть `product_fit` = 0 (остаётся 0.4 · глубина ОКПД2), первая фраза
объяснения говорит, как найден: «По названию не найдено; поставщик группы ОКПД2 17.12 по частоте
участия: 8 лот(ов), последний «…» (лот …)». Пустой ответ всегда с причиной — заголовок
`X-Search-Note` и лог: «в запросе нет слов для поиска; ОКПД2 не задан…», «нет истории до 01.01.2023»,

### `price`: что можно вычислить честно

Не вычислимо вообще: снижение цены относительно НМЦК, демпинг, «конкурентность цены» — нужна цена
контракта или ценовое предложение, их в выгрузке нет. Вычислимо только **типичный масштаб закупок
поставщика**: в данных есть НМЦК лотов, где он участвовал или побеждал, и `Query.budget` запроса.
Сейчас `suppliers.median_start_price` (`src/ingest/build.py:184`) — медиана НМЦК по всей истории
поставщика, а не по группе ОКПД2; статистики по группе в коде нет, её пришлось бы добавить.
Для backtest НМЦК берутся строго до `as_of`, иначе утечка во времени. Это не цена и не «выгодность», а
ответ на вопрос «закупки такого размера для него обычны?». **Не реализовано — ПРЕДЛОЖЕНИЕ**
(раздел «На подтверждение человеку»). Ограничения: масштабы ЭМ (медиана НМЦК 55 000 ₽) и АИС ГЗ
(167 172 ₽) различаются (`DATA_DICTIONARY.md`); выбросы НМЦК до десятков миллиардов — нужна
устойчивая оценка (медиана или квантили).

## Жёсткие фильтры — отдельно от балла

Фильтры не меняют score, а убирают кандидата (`src/match/filters.py:30-45`, `apply_filters`): ликвидация,
банкротство, прекращение деятельности по `Counterparty.status` и `in_rnp is True` — всегда;
«только СМП», «только производители», регион — по желанию пользователя. По D-030 фильтр
пользователя оставляет только подтверждённые совпадения: неизвестный МСП / тип отбрасывается, а
UI пишет, у скольких кандидатов признак неизвестен. Регион — реестр (`Counterparty.region`), иначе
префикс КПП 78 / 47. Отсутствующий статус или РНП кандидата не отбрасывает («не проверено»).
Статус, РНП, МСП и тип поставщика приходят из `enrich()`, а не из данных организаторов.

## Роль контрагента

Роль — производитель, дистрибьютор или дилер (`Counterparty.kind`) — определяется правилом v1 по
**основному ОКВЭД2 из источника**, без LLM (D-057, `src/enrich/role.py`). Код берётся из карточки
ФНС (pb.nalog.ru, `vyp.КодОКВЭД`), реестра МСП (`okved1`) или ГИР БО (`okved2`) — тем же путём
`enrich()`, что и остальные факты, и из строки реестра МСП в блоке «Новые». Роль — это заявленный
основной вид деятельности с основанием, а не подтверждённый тип поставщика.

| Основной ОКВЭД2 | Роль (`kind`) | Основание — текст факта в карточке |
|---|---|---|
| 10–32 | производитель (`manufacturer`) | обрабатывающее производство (раздел C, коды 10–32) |
| 33 | не определена (`unknown`) | ремонт и монтаж машин и оборудования — услуги, не производство (класс 33) |
| 45.2 | не определена (`unknown`) | техническое обслуживание и ремонт автотранспортных средств |
| 45, кроме 45.2 | дилер (`dealer`) | торговля автотранспортными средствами, мотоциклами и их деталями — перепродавец |
| 46.1x | дилер (`dealer`) | торговля оптовая за вознаграждение или на договорной основе — агент, посредник |
| 46.2–46.9 и «46» без подкласса | дистрибьютор (`distributor`) | оптовая торговля |
| 47 | дилер (`dealer`) | розничная торговля — перепродавец |
| прочие коды, в т.ч. 01–08 | не определена (`unknown`) | вне обрабатывающих производств и торговли — правило v1 роль не определяет |
| кода нет или он не разбирается | `None` | факта нет, в UI «Тип не определён» |

**Почему присвоена роль (К4).** Основание — отдельный факт с источником, url и датой:
«Роль — производитель: заявленный основной ОКВЭД 17.12 «Производство бумаги и картона» —
обрабатывающее производство (раздел C, коды 10–32)». Значение факта — строка закешированной
страницы с ключом основного ОКВЭД этого ИНН (белый список: `vyp.КодОКВЭД: 17.12`,
`search.okved2main: …`, `row.<ИНН>.okved1: …`, `row.<ИНН>.okved2: …`). `strip_unverified`
оставляет роль, только если эта строка есть на странице **целиком**, факт прошёл проверку
Evidence и правило по коду даёт ту же роль; иначе роль сбрасывается в «не определён»
(`src/enrich/evidence.py`). Строка запроса или чужая строка той же страницы реестра основанием не
считается.

**Роль в score не входит.** `product_fit`, веса и подбор топ-10 блока «Новые» (`_mix`: производители
и дистрибьюторы по очереди — по каналу поиска, а не по роли) не меняются. Роль работает только в
фильтре роли (чипы «Производители / Дистрибьюторы / Дилеры / Роль не определена», #232) и в карточке.

**Ограничения.** ОКВЭД заявляет сама компания: это вид деятельности по реестру, не подтверждение
производства. Исключения правила — класс 33 и 45.2 (ремонт — услуги, «не определена»; пример —
ООО «БРАСС», 33.12); других исключений внутри 10–32 нет (полиграфия 18 и 32.5 — производители).
Дополнительные ОКВЭД не учитываются: в реестре МСП и ГИР БО их нет. Блок «С опытом госзакупок»
получает роль только после подмешивания `enrich()` в выдачу (#38). **Точность правила не измерена —
разметки ролей нет; на слайде точность не заявляется до разметки.**
Проверка: `uv run pytest tests/unit/test_role.py`.

  выдачи тот же (география уже 0), но в карточке появится строка с типом закупки и профилем. До решения
  `weights_by_type: {}`. Раздел «Как выбраны веса» выше.
- Не меняется без подтверждения №3: формула, веса, состав компонент и константы выше. Нормировка весов к 1
  введена вместе с H-15f (D-077); перенормировка «на лету» по доступным компонентам по-прежнему отклонена (D-029).

## Релевантность новых поставщиков (#77, D-096)

**Проблема v0.** В блоке «Новые» `product_fit` = 1.0 (основной ОКВЭД совпал с классом ОКПД2) / 0.6 (опт по
таблице): внутри группы у всех один балл, топ-10 — первые строки реестра. ОКВЭД заявляет сама компания, и код
класса широк (`22.19` — и перчатки, и шланги). Цель — ОКВЭД остаётся грубым фильтром кандидатов, ранжирует то,
что компания реально продаёт.

**Инкремент 1 — `product_fit_new` без новых внешних источников** (`src/match/new_fit.py`, `configs/discover.yaml`):

| Компонента | Сигнал #77 | Как считается | Опора |
|---|---|---|---|
| `okved_match` | 5, 8 | база v0 (класс 1.0 / опт 0.6) × глубина: основной ОКВЭД глубже класса совпал с полным ОКПД2 запроса (`21.20.2` ↔ `21.20.23.110`) — 1.0; ОКВЭД только класса — 0.85; другая подгруппа класса — 0.6; опт 46.* не сравнивается | Evidence «Основной ОКВЭД» со страницы реестра МСП |
| `text_match` | 6, 8 | основы слов (5 букв) запроса и **профиля полного ОКПД2** (частые слова наименований позиций ТРУ с этим кодом до `as_of`; код укорачивается до подгруппы / группы / подкласса, но не до класса) найдены в названии (1.0; «мебел» ловится и в «БЮРОМЕБЕЛЬ») или в наименовании ОКВЭД (0.5); слово профиля — ×0.5; `min(1, сумма / 2)` | Evidence «Наименование» и «Основной ОКВЭД», значение буквально есть на закешированной странице (`value_in_page`) |

| `llm_check` | 9 | не считается; его доля распределена, в объяснении — «LLM-проверка не выполнялась» | — |

`product_fit_new = (3/7 · okved_match + 4/7 · text_match) × (1 − 0.5 · [есть минус-слово])` — доли 0.3 / 0.4 / 0.3
предложения #77 без LLM. У каждой компоненты — строка объяснения и список Evidence, на которые она опирается; факты
не порождаются, только читаются из ответа реестра.

**Режим.** `new_fit.mode: shadow` (по умолчанию): значение считается и пишется в `Discovery.fit_new` и лог, выдача
и балл — как в v0 (`tests/unit/test_new_fit.py::test_shadow_leaves_the_block_unchanged`). `on` — `product_fit`
блока «Новые» = `product_fit_new`, объяснение v0 дополняется формулой — **только для эксперимента**; включение по
умолчанию — изменение методологии скоринга, подтверждение человека №3 после precision@10 на разметке (#21).

**Константы — ручная эвристика.** Значения глубины (1.0 / 0.85 / 0.6), вклады слова (1.0 / 0.5 / ×0.5), насыщение 2.0, штраф минус-слов 0.5 и сама таблица минус-слов выбраны вручную по просмотру 11 закешированных запросов; они не подобраны по данным и не проверены на разметке (`configs/discover.yaml`, `src/match/new_fit.py`). Поэтому режим по умолчанию — shadow, а `on` пишет предупреждение в лог. Размер профиля кода ограничен потолком `profile_max_names` (2000 наименований): при его достижении в объяснении «≥ 2000», точного числа позиций нет. Без `notices.parquet` профиль строится без среза `as_of` и пишет предупреждение. Первое построение профиля нового кода — 0.17–0.53 с (замер 01.10, 6 кодов; reviewer — 0.62–0.66 с), повторное — меньше 1 мс (`research/EXPERIMENTS.md`, N-new-fit).

**Профиль кода без данных организаторов.** Профиль ОКПД2 читается из `items.parquet` / `notices.parquet`
напрямую, не через `Store` (ревью #220, №4; после хакатона — через `Store`, пока в нём нет подходящего метода:
`text_codes` отдаёт все тексты, не позиции одного кода). Нет `items.parquet` (`make up` без parquet) или мало
позиций — профиль не строится, `Discovery.profile_gap` и текст компоненты `text_match` говорят «профиль ОКПД2 не
посчитан: <причина>», в лог — warning; остальное считается по словам запроса и ОКВЭД, то есть не «0», а «нет
сигнала профиля» (`tests/unit/test_new_fit.py::test_without_parquet_the_profile_is_not_computed_and_says_why`).

**Что не измерено и чего нет.** Метрики нет: ручной разметки блока ещё нет. Сравнение off / on на 11 запросах
разметки (`uv run python -m src.eval.new_fit_compare prepare --offline`, `research/EXPERIMENTS.md` N-new-fit):
среднее пересечение top-10 — 8.8, состав изменился в 3 запросах, порядок — в 7. Сигнал 5 «нужный ОКВЭД затерян
среди дополнительных» не измерим: дополнительных ОКВЭД нет ни в одном закешированном ответе rmsp, pb.nalog и ГИР БО
(поиск реестра идёт по основному ОКВЭД). Текст у кандидата короткий (название + ОКВЭД), и наименование ОКВЭД у всех
строк одного кода одинаково — внутри одного кода различает только название.

**Попутно — «код ОКПД2 не бьётся с текстом»** (плохой случай эксперта, #113): пустое пересечение слов запроса с
профилем полного ОКПД2 — кандидат в признак (облучатели бактерицидные с кодом `32.50.50.190`, профиль кода —
«одноразовый, стерильный, медицинский, хирургический»). Сейчас только печатается в сравнении, на выдачу не влияет.

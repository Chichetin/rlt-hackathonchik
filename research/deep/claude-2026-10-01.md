## 2. Критика наших решений

1. **История для holdout заморожена на `cutoff` 2025-07-01** (`Query.as_of = cutoff`, D-018,
   `src/contracts.py:68`). На holdout (окт–дек) это выбрасывает три месяца истории и занижает
   метрику относительно продукта, который обновляется ежедневно, — особенно на поставщиках, впервые
   появившихся летом (582–1 314 новых в месяц, PROBLEM.md). Стандарт: признаки для holdout — до
   `holdout_from` (train+dev), веса — замороженные с dev. Поправить до первого `eval-final`. [ВЫВОД]
2. **Ловушка инкумбента — риск методологии, а не только eval.** 57.85% побед 2025 года — у
   поставщика, уже выигрывавшего у этого заказчика. Backtest «угадай участника» вознаграждает
   компоненту «работал с вами» сильнее всех, а продукт обязан расширять конкуренцию. OCP прямо
   называет «high share of buyer's contracts» (R040) и «single bid» (R018) red flags [ДОК, OCP 2024].
   Признак — метка «уже работал с вами / новый для вас», инкумбент — baseline. Главная цифра —
   срез «новый для заказчика» и метрики расширения. Изменение — подтверждение №3. [ВЫВОД]
3. **`reliability` (вес 0.20 в METHODOLOGY.md) не вычислима из данных организаторов** (нет
   исполнения и расторжений) и отсутствует в T-02 и в списке принятых компонент — документ и код
   расходятся. Сделать её жёстким фильтром + мягкими флагами из реестров, а не взвешенной компонентой
   на пустых данных. [ВЫВОД]
4. **`price` при одной НМЦК — это масштаб, а не цена.** Переименовать в `scale_fit`
   («работает с закупками такого размера»: лог-расстояние от НМЦК запроса до медианы НМЦК лотов
   поставщика, клип по p99 канала) или убрать; оставлять только при приросте вне интервала. Есть ли
   цена контракта в реестре контрактов ЭМ — `UNKNOWN` [П]: если есть, это настоящая `price`. [ВЫВОД]
5. **Единица запроса.** Backtest берёт весь лот (`subject` + все позиции), а пользователь вводит
   короткую строку — нужен второй режим «короткий запрос». Многопозиционные лоты (max 7 000 позиций):
   искать по каждой позиции и агрегировать на поставщика через max/top-3, а не сумму (сумма —
   скрытая популярность); объяснение «совпало 3 из 4 позиций». Индекс — по уникальным
   `product_name`. [ВЫВОД]
6. **Метрики.** АИС ГЗ: один релевантный → Recall@10 = HitRate@10, так и называть. ЭМ: основной
   срез — ≥ 2 оферт, nDCG@10 с градациями. Bootstrap по лотам занижает интервалы (лоты одного
   заказчика коррелированы) → кластерный bootstrap по `customer_inn`. Добавить Recall@200 кандидатов
   (где теряем: в поиске или в весах) и macro-срез по топ-классам ОКПД2. В АИС ГЗ отсутствие в
   ground truth ≠ нерелевантность — метрики там нижняя граница. [ВЫВОД]
7. **Каналы.** Трактовка верна. Одна формула, отчёт раздельно (раздельные веса удваивают риск
   переобучения на dev). Использовать асимметрию: оферта в ЭМ без победы = заявленная способность
   поставить товар — лучший сигнал для `activity`; популярность побед (АИС ГЗ) и участий (ЭМ)
   считать раздельно. Пользовательский сценарий — ЭМ, значит ЭМ — первая цифра. [ВЫВОД]
8. **`geography` по первым цифрам ИНН** — регион налоговой, выдавшей ИНН, не место деятельности.
   В объяснении «ИНН выдан в СПб»; для найденных — адрес ЕГРЮЛ с URL (у ИП адрес не показываем). [ВЫВОД]
9. **ИП = 53.4% уникальных ИНН.** 12-значный ИНН ≠ ИП (может быть физлицо/самозанятый): нет в
   ЕГРИП → «Физическое лицо, сведения не раскрываются», без обогащения. ИП ранжировать наравне с
   ЮЛ — иначе ответ на «только крупные» слабеет. [ВЫВОД, правовая часть — блок 2]
10. **D-001 (доля холодных победителей dev, найденных discovery) — лучшая объективная цифра блока
    «Новые»**, но с оговорками утечки: канал А (контракты ЭМ 2026) для dev — будущее, фильтр дат
    сдвигать на окно dev; реестр МСП — снимок 10.09.2026, а не на дату лота (мягкая утечка — писать
    явно). [ВЫВОД]

## 4. Методология

Источник: исследователь блока 3; критика его же раздела 1 сведена в разделе 2 выше.

### 4.1 Схема

1. **Кандидаты** (из истории): BM25 (`bm25s`, русский стеммер PyStemmer) по уникальным
   `product_name` для каждой позиции запроса → поставщики этих позиций; плюс поставщики с совпадением
   ОКПД2 на уровне группы (4 знака); объединение, top-200. Опционально — RRF с эмбеддингами.
2. **Жёсткие фильтры**: статус «действует» (внешний источник; нет данных — «не проверено», не
   отбрасывать), пользовательские: регион, СМП (по реестру МСП, не по `is_smp` — в ЭМ поле всегда
   false, PROBLEM.md).
3. **Скоринг** `score = Σ wᵢ·cᵢ`, каждая `cᵢ ∈ [0,1]`, веса видны в UI.
4. **Метки, не влияющие на ранг**: «уже работал с вами» / «новый для вас», ИП/ЮЛ, «ИНН подтверждён».

### 4.2 Компоненты → поля

| Компонента | Формула (v0) | Поля | Объяснение (пример формата) |
|---|---|---|---|
| `product_fit` | среднее по позициям запроса `q` от `max` нормированного BM25 (или косинуса) по позициям поставщика; × бонус глубины ОКПД2 (совпали 2/4/6/9 знаков → 0.25/0.5/0.75/1, берём max(text, okpd)) | ТРУ: `product_name`, `okpd2_code`; Поставщики: `lot_id`→`supplier_inn` | «совпало 3 из 4 позиций; ОКПД2 до 9 знаков; пример: лот … от …» |
| `experience` | `log(1+Σ exp(−Δt/365))` по релевантным лотам (ОКПД2 ≥ 4 знаков или text ≥ порога), нормировка по кандидатам; оферты и победы раздельно | Поставщики: `is_winner`; Извещения: `publish_date`, `is_eshop_or_aisgz` | «N оферт, M побед за 2 года в группе ОКПД2 …» |
| `activity` | `exp(−дней_с_последнего_участия/90)` | Извещения: `publish_date` | «последняя оферта — …» |
| `geography` | 1 — ИНН региона 78; 0.7 — 47; 0.3 — прочие (у найденных — по адресу ЕГРЮЛ) | `supplier_inn` (первые 2 цифры) | «ИНН выдан в СПб» |
| `scale_fit` (вместо `price`) | `1 − min(1, |log НМЦК_q − медиана log НМЦК_поставщика| / 2)` по клипнутым значениям | Извещения: `start_price` | «обычно лоты 50–300 тыс. ₽, запрос 120 тыс. ₽» |

Нормировки и пороги — стартовые, `HYPOTHESIS`; подстраиваются на dev. Признак «работал с заказчиком»
(`customer_inn`) в формулу **не входит** (см. 1.1) — решение для подтверждения №3.

### 4.3 Веса

Стартовые — экспертные, затем покоординатный перебор 2–3 весов на dev; финальный слайд —
**ablation-таблица** «без компоненты X → метрика» с интервалами: она доказывает, что каждая компонента
зарабатывает своё место, и это понятнее жюри, чем подобранные веса. **[ВЫВОД]**

### 4.4 Запасной вариант

`product_fit` (BM25 + префикс ОКПД2) × `activity`, сортировка; число релевантных лотов за 12 месяцев —
второй ключ. Две компоненты, одна строка объяснения каждая, считается за минуты. Это уже закрывает
пункт 3 при условии, что обгоняет популярность в классе ОКПД2 на dev. **[ВЫВОД]**

### 4.5 Эмбеддинги — когда и какие

- BEIR: «BM25 is a robust baseline» вне домена обучения моделей — **[ДОК]**
  https://arxiv.org/abs/2104.08663 (проверено 2026-10-01). Ни одна задача ruMTEB не похожа на

### 4.6 Что измерить первым (по порядку, ~1.5 ч)

1. На dev, 1 000 лотов/канал: популярность в классе ОКПД2, инкумбент (заказчик × ОКПД2), BM25 —
   HitRate/Recall@10, MRR, nDCG@10; срез «победитель новый для заказчика».
2. Recall@200 кандидатов (BM25 ∪ ОКПД2) — потолок.
3. Режим «короткий запрос» (`subject` / одна позиция) против «весь лот».
4. Ablation компонент; затем эмбеддинг-реранкер mE5-small vs bge-m3 на 200 лотах.

## 5. Протокол оценки

### 5.1 Что поменять в backtest

| Изменение | Зачем |
|---|---|
| Кластерный bootstrap по заказчику | честные интервалы |
| История для holdout — до `holdout_from` (с dev) | паритет с продуктом |
| Два режима запроса: весь лот / короткий текст | совпадение со сценарием UI |
| Срезы: новый для заказчика; ≥ 2 оферт (ЭМ); топ-классы ОКПД2; без холодного старта | показать, где прирост |
| Метрики «расширения»: доля новых для заказчика в top-10, доля топ-100 поставщиков в top-10 | ответ на «только крупные и привычные» |
| Recall@200 кандидатов | диагностика |
| Инкумбент — baseline-планка, не компонента | см. 1.1 |

Литература подтверждает, что простые baselines надо принимать всерьёз: из 18 нейросетевых
рекомендательных методов воспроизвелись 7, и 6 из них часто обгоняются простыми эвристиками
(nearest-neighbor) — **[ДОК]** https://arxiv.org/abs/1907.06902 (проверено 2026-10-01).

### 5.2 Как оценивать «Новых»

1. **Автоматический прокси без разметки** (`HYPOTHESIS`, проверить выполнимость): в dev 6.75% лотов
   с холодным победителем. Если discovery по ОКПД2→ОКВЭД+регион возвращает список ИНН, мерить
   **долю холодных победителей dev, попавших в список discovery** (и их ранг). Это единственная
   цифра «Новых», не зависящая от разметчика. Holdout не трогать.
2. **Pooled-разметка вслепую**: на 10–15 реальных запросов пул = top-10 «Новых» + top-5 «С опытом»,
   перемешано, источник скрыт от разметчика. Шкала 2/1/0 («поставляет именно это» / «профильная
   отрасль» / «нет»), для 2 — обязательный URL-доказательство. Метрика — P@10 по «Новым» (label ≥ 1 и
   = 2 раздельно), плюс сравнение блоков на общем пуле. **[ВЫВОД]**
3. **Объём**: 12 запросов × 15 = 180 суждений; при 20–40 с на суждение — 1–2 часа одного человека
   (оценка, `HYPOTHESIS`). Для P@10 по 120 меткам «Новых» биномиальная полуширина 95% при p≈0.5 —
   около ±9 п.п. (1.96·√(0.25/120)); с учётом корреляции внутри запроса — шире, считать bootstrap
   по запросам. **[ВЫВОД]**
4. **LLM-судья**: проверять **Cohen's kappa**, а не долю совпадений (ориентир «~80% согласия» в
   EVAL.md при перекосе классов может соответствовать слабой kappa). На пересечении 40–60 суждений:
   kappa(человек₁, человек₂) и kappa(LLM, человек); LLM допускается, если его kappa не ниже
   межчеловеческой. **[ВЫВОД]**
   Ориентир из литературы: GPT-4o (UMBRELA) против асессоров TREC DL — binary kappa 0.42–0.50,
   graded 0.31–0.37, но Kendall τ ранжирования систем 0.87–0.94 — **[ДОК]**
   https://arxiv.org/html/2406.06519 (проверено 2026-10-01). Значит, LLM-судья пригоден для
   **сравнения вариантов** между собой, но абсолютный P@10 на слайде — только по человеческой разметке.
   **[ВЫВОД]** Риски циркулярности (система с LLM, оцениваемая LLM) — **[ДОК]**
   https://arxiv.org/abs/2412.17156 (проверено 2026-10-01); Thomas et al. (Bing): LLM-метки на уровне
   сторонних асессоров, но чувствительны даже к перефразировке промпта — **[ДОК]**
   https://arxiv.org/abs/2309.10621 (проверено 2026-10-01).
5. Модель-судья ≠ модель, участвующая в извлечении/ранжировании (уже в EVAL.md — подтверждается
   2412.17156).

### 5.3 Объяснимость для жюри

- Карточка: полоска каждой компоненты с весом + одна строка текста + **ссылка на конкретные лоты
  истории** (дата, заказчик, позиция; для АИС ГЗ — ссылка в ЕИС по `reqnum`, если трактовка Q-12
  верна) + у каждого внешнего факта URL и дата. **[ВЫВОД]**
- Метки «уже работал с вами» / «новый для вас» — прямой ответ на R040 OCP. **[ВЫВОД]**
- Слайд методологии: формула, таблица «компонента → поле данных», ablation, сравнение с baselines,
  срез «новые для заказчика». Прозрачная формула лучше модели-«чёрного ящика»: и потому, что простые
  методы часто не хуже (1907.06902), и потому, что жюри — владелец системы. **[ВЫВОД]**

## 6. Вопросы жюри и организаторам

### 6.1. 15 вопросов жюри с короткими ответами

1. **«Не нарушает ли сервис равный доступ (ст. 8 44-ФЗ)? Вы же подсказываете конкретных
   поставщиков».**
   Нет. Закупка в ЭМ остаётся публичной, оферту может подать любой аккредитованный поставщик.
   Сервис только **добавляет** адресатов уведомления или запроса КП и никого не исключает. Выбор
   за заказчиком: в закупке у единственного поставщика заказчик «самостоятелен в выборе» (FAQ
   Комитета). Мы расширяем круг участников, а не сужаем его.
2. **«Не рекомендуете ли вы только крупных и привычных?»**
   Мы это измеряем. Выдача разделена на два блока, «Знакомые» и «Новые»; в метриках есть срез
   «победитель новый для заказчика». Фактор «уже работал с этим заказчиком» не главный. Показываем
   долю рекомендаций, которая приходится на топ-поставщиков. В данных 1 506 поставщиков (3.41%)
   дают 71% участий, и мы не хотим эту концентрацию усиливать.
3. **«Как вы обращаетесь с персональными данными ИП? Их больше половины».**
   Показываем только открытые сведения ЕГРИП (129-ФЗ, ст. 6): ФИО, ОГРНИП, статус, ОКВЭД, у каждого
   факта ссылка на реестр и дата. Адрес и личные контакты ИП не показываем. ИНН во внешние
   сервисы и LLM не передаём.
4. **«Насколько свежие данные?»**
   История — выгрузка организаторов за 2024–2025 годы. Сведения о компаниях берутся из реестров
   ФНС в момент запроса и кешируются с TTL. В карточке у каждого факта дата получения. Если факт
   старше TTL, видна пометка. В продакшене история обновлялась бы ежедневной выгрузкой из АИС ГЗ.
5. **«Как это встроить в АИС ГЗ?»**
   Через REST API и кнопку «Подобрать адресатов» в форме «Запрос коммерческих предложений» ЭМ:
   заказчик уже выбирает там организации текстовым поиском, мы подставляем готовый список по тем
   же ОКПД2. Минимальный вариант — ссылка из карточки закупки, доступ к закрытым данным не нужен.
6. **«Почему мы должны верить рекомендации?»**
   У каждого поставщика есть разложение балла по компонентам (соответствие предмету, опыт,
   активность, география) с объяснением в одну строку и ссылкой на факты. Качество проверено
   backtest'ом на реальных закупках СПб: Recall@10 и MRR раздельно по ЭМ и АИС ГЗ, в сравнении
   с простыми baselines. Цифры только из `eval/results`.
7. **«Откуда новые поставщики, которых нет в нашей системе?»**
   Из открытых госреестров (ЕГРЮЛ/ЕГРИП, реестр МСП, ГИР БО) и реестра контрактов ЭМ. У каждой
   компании есть URL-источник и дата. Ограничение такое: если компания не зарегистрирована в ЭМ,
   через штатный запрос КП её не выбрать, и сервис предлагает пригласить её зарегистрироваться.
8. **«Если сервис ошибся и посоветовал недобросовестного поставщика?»**
   Сервис не назначает. Статус юрлица (ликвидация, недостоверность) виден в карточке, если он
   получен из реестра; если проверки не было, так и написано: «не проверено». Проверку РНП
   заказчик делает как обычно. `UNKNOWN`: есть ли у нас автоматическая проверка РНП к демо.
9. **«Не порождает ли LLM несуществующие компании и контакты?»**
   Продукт работает без LLM. Если LLM используется, она только извлекает факты из текста
   закешированной страницы. Значение (ИНН, телефон) показывается, только если оно буквально есть
   на странице, а ИНН проходит контрольные цифры. Это проверяет тест.
10. **«Как сервис помогает с обоснованием НМЦК?»**
    Показывает, у кого запросить КП по предмету закупки: столько адресатов, сколько нужно по
    методическим рекомендациям (приказ МЭР № 567, они рекомендательные), включая новых, а не
    только привычных. Цену мы не считаем: цен контрактов в данных нет.
11. **«А национальный режим, СМП?»**
    Признак СМП проверяется по реестру МСП ФНС, фильтр включает сам пользователь. Для нацрежима
    (ПП 1875) нужен реестр российской промпродукции в ГИСП, автоматически он нам недоступен. Это
    честно помечено «проверьте в ГИСП». Ограничений за заказчика сервис не вводит.
12. **«Как масштабируется на всю АИС ГЗ и другие регионы?»**
    Индекс поиска строится из истории позиций и ОКПД2 за минуты на CPU (цифру — из нашего прогона).
    Обогащение — фоновая очередь с кешем. Для другого региона нужна только его история закупок.
    В ЭМ уже есть котировочные сессии Москвы и Ленобласти, так что межрегиональный сценарий
    органичен.
13. **«Чем вы лучше Контур.Закупок и других агрегаторов?»**
    Они помогают поставщику найти закупку. Мы помогаем заказчику СПб найти поставщика, внутри его
    процесса (ЭМ, запрос КП), с объяснением и источником каждого факта.
14. **«Что если поставщик не хочет получать запросы?»**
    Уважаем его выбор. Штатный механизм ЭМ скрывает поставщика, снявшего признак «получать
    запросы», и мы рекомендуем внутри этого механизма. «Новым» из реестров только предлагаем
    зарегистрироваться, массовых рассылок не делаем.
15. **«Почему у части поставщиков нет названия?»**
    В данных организаторов есть только ИНН. Название берём из ЕГРЮЛ/ЕГРИП или реестра контрактов
    ЭМ с источником. Если не подтвердили, пишем «не подтверждено» и не угадываем.

## 7. Выводы по блокам с источниками

### 7.1. Блок 1 — Discovery

#### Главное

1. **Реестр МСП (rmsp.nalog.ru) умеет искать по ОКВЭД + региону без капчи, с пагинацией и выгрузкой в Excel** — это рабочий канал discovery «по профилю», проверено живым запросом.

3. **Официального переходного ключа ОКПД2 → ОКВЭД2 нет** (у Минэкономразвития есть ключи для других пар); связь берём из общей структуры классификаторов: первые 4 знака ОКПД2 = класс ОКВЭД2 вида деятельности, который производит этот продукт.
4. **FTP ЕИС закрыт с 01.01.2025**, а сервис выгрузки требует ЕСИА и обоснования цели. `spending.gov.ru` возвращает 410 Gone. Реестр Минпромторга (ПП 719) ведёт на ГИСП, а ГИСП отвечает 403. Для СПб лучший источник контрактов — реестр контрактов ЭМ (`estore.gz-spb.ru`).

### 7.2. Блок 2 — Обогащение и фильтры по ИНН

#### 1.1. Какие сведения об ИП публичны и что можно показывать

1. **[ДОК]** 129-ФЗ, ст. 6, п. 1: сведения и документы госреестров (ЕГРЮЛ, ЕГРИП) «являются открытыми и
   общедоступными». Исключения: реквизиты документа, удостоверяющего личность (номер, дата выдачи, орган),
   **сведения о месте жительства ИП** и сведения ограниченного доступа. П. 2: место жительства ИП выдаётся
   только по запросу, который физлицо подаёт лично с документом, удостоверяющим личность, а госорганам — в
   случаях, предусмотренных законом. Есть и норма о размещении сведений в электронной форме на сайте
   регистрирующего органа в открытом доступе.
   Источник: https://www.klerk.ru/cdoc/view/federalnyj-zakon-ot-08082001-no-129-fz-o-gosudarstvennoj-registracii-uridiceskih-lic-i-individualnyh-predprinimatelej/stata-6-predostavlenie-soderzasihsa-v-gosudarstvennyh-reestrah-svedenij-i-dokumentov/
   (ред. 31.07.2025, проверено 2026-10-01). Тот же смысл — в разъяснении ФНС:
   https://www.nalog.gov.ru/rn57/news/tax_doc_news/6101866/ (в выдаче поиска, не открыт).
   Оговорка: страница отдала пересказ статьи, а не дословный текст. Перед слайдом сверить с
   consultant.ru или pravo.gov.ru — [ПЛОЩАДКА].
2. **[ДОК]** 152-ФЗ, ч. 1 ст. 6, п. 11: обработка допускается без согласия, если «осуществляется обработка
   персональных данных, подлежащих опубликованию или обязательному раскрытию в соответствии с федеральным
   законом». Запасное основание — п. 7 (законные интересы оператора или третьих лиц, «общественно значимые
   цели» при условии, что права субъекта не нарушаются).
   Источник: https://www.consultant.ru/document/cons_doc_LAW_61801/315f051396c88f1e4f827ba3f2ae313d999a1873/
   (ред. от 26.07.2026, проверено 2026-10-01).
3. **[ВЫВОД]** Сочетание (1) и (2): сведения ЕГРИП, которые ст. 6 129-ФЗ делает общедоступными, можно
   обрабатывать и показывать без согласия ИП. Это ФИО, ИНН, ОГРНИП, даты регистрации и прекращения, статус,
   ОКВЭД, сведения о лицензиях. Цель обработки должна совпадать с целью раскрытия, то есть с проверкой
   контрагента. **Адрес места жительства ИП показывать нельзя**: закон прямо исключает его из
   общедоступных. Регион ИП (субъект РФ из ИНН, из реестра МСП или из карточки ПБ) — сведения о месте
   нахождения бизнеса, их показ допустим. `HYPOTHESIS`: проверить, что pb.nalog.ru сам показывает регион ИП
   [ПЛОЩАДКА].
4. **[ВЫВОД]** Контакты ИП (телефон, email) — персональные данные физлица, и ст. 6 129-ФЗ их не раскрывает.
   В карточке ИП их **не показываем и не храним**, даже если нашли на стороннем агрегаторе. Если ИП сам
   опубликовал контакты на своём сайте, в карточке достаточно ссылки на сайт, без копии контакта.
   `HYPOTHESIS`: показ контакта с собственного сайта ИП юридически допустим; без юриста не рискуем.
5. **[ВЫВОД, важно для 53.4% 12-значных ИНН]** 12-значный ИНН ещё не означает ИП: участником закупки может
   быть физлицо без регистрации ИП, включая плательщика НПД («самозанятого»). Если ИНН не найден в ЕГРИП,
   карточка — «Физическое лицо (не зарегистрировано как ИП) — сведения не раскрываются». Никакого
   обогащения, только история участий из данных организаторов. Существование официальной проверки статуса
   НПД по ИНН — `UNKNOWN`: я не проверял, на эту проверку не рассчитываем.

**Как показывать ИП в выдаче** [ВЫВОД]:
- Название — как в ЕГРИП: «ИП Фамилия Имя Отчество». Рядом ИНН и ОГРНИП, у каждого поля — `Evidence`
  (URL карточки egrul/pb и `fetched_at`).
- Поля: статус (действует / прекратил деятельность с даты), дата регистрации (возраст), основной ОКВЭД,
  категория МСП, регион. Адреса нет. Контактов нет.
- Подпись в карточке: «Сведения из ЕГРИП, общедоступны по ст. 6 129-ФЗ; адрес места жительства ИП не
  раскрывается по закону».
- ИП ранжируются наравне с ЮЛ. Штрафовать за форму «ИП» нельзя: это 53.4% поставщиков, и аргумент «не
  рекомендуете только крупных» на защите сильнее, если ИП в выдаче на равных.
- Хранение: кеш с TTL, только перечисленные поля, без сырых PDF-выписок ИП на диске дольше демо.
  `HYPOTHESIS` — минимизация по ст. 5 152-ФЗ; текст ст. 5 я не открывал.

#### 1.2. Жёсткие фильтры: что требует закон

6. **[ДОК-втор.]** 44-ФЗ, ст. 31, ч. 1, п. 3 — **обязательное** требование к участнику: юрлицо не
   ликвидируется; нет решения арбитражного суда о признании участника (ЮЛ **или ИП**) банкротом и об
   открытии конкурсного производства. Ч. 1.1 — отсутствие в РНП (включая учредителей и руководителя)
   заказчик **вправе** установить, но не обязан. Сведения исключаются из РНП через 2 года.
   Источники (в выдаче поиска, не открыты): https://www.zakonrf.info/doc-32672656/gl3-pf1-st31/ ,
   https://base.garant.ru/58079582/ , https://www.socialkirov.ru/social/root/AnotherInfo/GovPurchases/44fz/reestr.htm
   Применяется ли ст. 31 к ЭМ (закупки по п. 4, 5 ч. 1 ст. 93) и в каком объёме — `UNKNOWN`, спросить
   организаторов.
7. **[ВЫВОД]** Отсюда — разные типы фильтров:
   - **Жёсткое исключение по закону**: ЮЛ ликвидировано или в стадии ликвидации; ИП прекратил деятельность;
     банкротство с конкурсным производством.
   - **РНП — фильтр по умолчанию «вкл.»** с видимым переключателем и плашкой «в РНП до <дата>,
     основание — закупка №…». Исключать молча нельзя: по ч. 1.1 это право заказчика, а не обязанность, и
     жюри из Комитета это знает.
   - **Мягкие флаги без исключения** (штраф в `reliability` и плашка): «недостоверность сведений»,
     дисквалифицированный руководитель, задолженность, переданная ФССП, отчётность не сдаётся больше года.
8. **[ДОК-втор.]** Недостоверность: 129-ФЗ, ст. 11, п. 6 — регистрирующий орган вносит запись о
   недостоверности, если ЮЛ за 30 дней не подтвердило сведения. Запись касается только адреса,
   учредителя и руководителя. Если запись висит больше 6 месяцев, ФНС вправе исключить ЮЛ из ЕГРЮЛ.
   Видно в выписке ЕГРЮЛ и в pb.nalog.ru. Источники (не открыты): https://www.consultant.ru/law/podborki/129_fz_nedostovernost/ ,
   https://focus.kontur.ru/site/news/174 . **[ВЫВОД]**: для ЮЛ это сильный сигнал риска «фирма вот-вот
   исчезнет». Ставим мягкий флаг; исключение не нужно — закон такого требования не содержит.
9. **[ВЫВОД]** Банкротство ИП: по 127-ФЗ (ст. 216 по памяти — `HYPOTHESIS`, текст не открыт) после
   признания банкротом ИП утрачивает регистрацию, и статус в ЕГРИП становится «прекращена». Тогда
   отдельный запрос к ЕФРСБ для ИП в MVP не нужен: хватает статуса ЕГРИП. Для ЮЛ стадия банкротства
   может отражаться в статусе ЕГРЮЛ — `HYPOTHESIS`, проверить по выписке на площадке.

### 7.3. Блок 3 — Методология и оценка

#### Подробная критика (исходный текст исследователя)

#### 1.1 Ловушка инкумбента — главный риск методологии, а не только eval

- В 2025 году 57.85% побед — у поставщика, уже выигрывавшего у этого заказчика (PROBLEM.md). Любой
  backtest «угадай, кто участвовал» будет вознаграждать компоненту «работал с этим заказчиком» сильнее
  всех остальных. **[ВЫВОД]**
- Но цель продукта — расширить конкуренцию. Open Contracting Partnership в руководстве по red flags
  (2024) прямо относит к индикаторам риска **R018 «Single bid received»** и **R040 «High share of
  buyer's contracts»** («A supplier wins a high share of contracts in a particular market from the same
  buyer»; «the ultimate goal of institutionalized corruption is to award contracts repeatedly to the
  same company») — **[ДОК]** https://www.open-contracting.org/wp-content/uploads/2024/12/OCP2024-RedFlagProcurement-1.pdf
  (проверено 2026-10-01, текст извлечён из PDF).
- Следствие: признак «уже работал с вами» **не должен поднимать ранг** в основной формуле — иначе жюри
  из Комитета увидит сервис, который усиливает R040. Показывать его как метку («уже работал с вами» /
  «новый для вас»), а инкумбент-модель держать как **baseline-планку**. Это изменение состава
  компонент → подтверждение человека №3. **[ВЫВОД]**
- Честный способ показать прирост: не «обогнали инкумбента по Recall@10» (скорее всего не обгоним —
  `HYPOTHESIS`, проверить на dev), а (а) срез «победитель новый для заказчика», где инкумбент по
  построению не может поставить победителя из своей истории; (б) Recall по **неинкумбентным**
  релевантным; (в) доля «новых для заказчика» в top-10 при сопоставимом Recall. **[ВЫВОД]**

#### 1.2 Split

- Статичный `cutoff` 2025-07-01 для всего dev — корректно и просто, утечки нет. **[ВЫВОД]**
- Риск 1: при оценке holdout история должна пересчитываться на `holdout_from` (2025-10-01) и включать
  dev, иначе holdout оценивается на истории полугодовой давности и Recall занижен относительно
  продукта, который обновляется ежедневно. Проверить в коде `make eval-final`. **[НА ПЛОЩАДКЕ]**
- Риск 2: в статичном протоколе лоты сентября не видят историю июля–августа — это консервативно для
  всех методов одинаково, но завышает долю «холодного старта» (6.75% dev) по сравнению с продуктом.
  Отчитаться как ограничение; rolling-протокол (история до даты лота − 1 день) — только как
  вторичный, и с дедупликацией повторных публикаций одной и той же закупки (иначе повторное
  размещение несостоявшейся закупки даёт тривиальное «угадывание»). **[ВЫВОД]**
- Риск 3: bootstrap по лотам при выборке 1 000 лотов на канал занижает интервалы — лоты одного
  заказчика коррелированы. Делать **кластерный bootstrap по `customer_inn`** (ресемплинг заказчиков).
  **[ВЫВОД]**
- Стратификация: крупные классы ОКПД2 (32 — 11.58% лотов, PROBLEM.md) будут доминировать. Добавить
  macro-среднее по топ-10 классам или хотя бы срез по классам. **[ВЫВОД]**

#### 1.3 Метрики

- АИС ГЗ: один релевантный → Recall@10 = HitRate@10; называть так на слайде, чтобы не путать. **[ВЫВОД]**
- ЭМ: 41.47% лотов с одной офертой → в них Recall@10 тоже HitRate. Основной ЭМ-срез — «≥ 2 оферт»
  (dev 17 054), там же nDCG@10 с градациями 2/1. **[ВЫВОД]**
- Нет метрик, отвечающих на вопрос жюри «не рекомендуете ли только крупных и привычных»:
  добавить **долю «новых для заказчика» в top-10** и **долю рекомендаций из топ-100 поставщиков**
  (сравнить с их 28.16% участий, PROBLEM.md). **[ВЫВОД]**
- Добавить **Recall@200 этапа кандидатов** — потолок для скоринга; иначе непонятно, где теряется
  качество: в поиске или в весах. **[ВЫВОД]**

#### 1.4 Единица поиска

- Запрос в backtest = `subject` + все позиции лота, а в продукте пользователь вводит короткую строку.
  Это рассогласование протокола и сценария. Нужен второй режим запроса: **только `subject` или одна
  позиция**. **[ВЫВОД]**
- 59.3% лотов — одна позиция, но max 7 000 (PROBLEM.md): склейка всех позиций в один BM25-запрос
  размывает многопозиционные лоты. Лучше: поиск **по каждой позиции** → агрегация на поставщика
  (доля позиций лота, по которым поставщик найден, × сила совпадения). Это же даёт объяснение
  «совпало 3 из 4 позиций». **[ВЫВОД]**
- Агрегация позиций в поставщика через **сумму** BM25 даёт преимущество тем, у кого больше строк в
  истории, — скрытая популярность. Брать max/среднее top-3 по позиции, объём учитывать отдельно в
  `experience`. **[ВЫВОД]**
- Индекс — по **уникальным** строкам `product_name` (с частотой на поставщика), а не по 2.97 млн строк
  ТРУ: меньше памяти и быстрее эмбеддинги. Сколько уникальных — `UNKNOWN`, посчитать. **[НА ПЛОЩАДКЕ]**

#### 1.5 Компоненты

- **Расхождение документов**: в METHODOLOGY.md шесть компонент с `reliability` = 0.20, в списке
  «принятых решений» — пять без `reliability`. Из данных организаторов надёжность не вычисляется
  (нет исполнения и расторжений). `reliability` в v0 — **жёсткий фильтр** по внешнему статусу
  (действует / ликвидация), а не взвешенная компонента с весом 0.20 на пустых данных. **[ВЫВОД]**
- **`price` переименовать или убрать.** Конкурентность цены без цены контракта не измерить. Что
  вычислимо: **соответствие масштаба** — попадает ли НМЦК запроса в диапазон НМЦК лотов, где
  поставщик участвовал/побеждал (лог-шкала, клип по p99 канала из-за выбросов до 30.4 млрд ₽,
  PROBLEM.md). Называть `scale_fit` («работает с закупками такого размера»), вес малый, оставлять
  только если ablation на dev показал прирост вне доверительного интервала. **[ВЫВОД]**
  Есть ли цена контракта в реестре контрактов ЭМ (`estore.gz-spb.ru/contracts/catalog`) — `UNKNOWN`,
  **[НА ПЛОЩАДКЕ]**; если есть — это настоящая `price` (снижение от НМЦК) для поставщиков ЭМ.
- **`geography` по ИНН** — это регион налоговой, присвоившей ИНН, а не место деятельности; у ИП —
  тем более. В объяснении писать «ИНН выдан в СПб», для найденных в открытых источниках — адрес из
  ЕГРЮЛ с URL. **[ВЫВОД]**
- **`experience` и `activity`** вычислимы прямо из Поставщиков+Извещений; разделить «подавал оферты
  в ЭМ» и «побеждал», это разные факты для объяснения. **[ВЫВОД]**

#### 1.6 Трактовка каналов

- Трактовка верна по профилю (ЭМ — все оферты, АИС ГЗ — 83.60% лотов с 1 поставщиком). **[ВЫВОД]**
- Не обучать раздельно: при ручной формуле с 4–5 весами раздельная подстройка удваивает риск
  переобучения на dev. Одна формула, **отчёт раздельно**; отдельные веса для канала — только если
  выигрыш вне интервала. **[ВЫВОД]**
- Использовать асимметрию: **оферта в ЭМ = заявленная способность** поставить товар, даже без
  победы. Это сигнал кандидата и для запросов АИС ГЗ; «популярность» в АИС ГЗ — это популярность
  побед, в ЭМ — участия, считать их раздельно. **[ВЫВОД]**
- Приоритет: пользовательский сценарий — приглашение в ЭМ (рабочая гипотеза), значит основная
  метрика на слайде — ЭМ (≥ 2 оферт), АИС ГЗ — вторая. **[ВЫВОД]**

### 7.4. Блок 4 — Право, встраивание, защита

#### Главная находка: штатный «Запрос КП» в ЭМ

**В Электронном магазине уже есть штатная функция «Запрос коммерческих предложений», и в ней заказчик
сам выбирает организации-адресаты.** [ДОК] Руководство заказчика ЭМ, раздел «Создание запроса
коммерческих предложений» (https://manuals.gz-spb.ru/estore/ru/lkz/lkz-2/lkz-9/lkz-11/lkz-13,
проверено 2026-10-01; WebFetch не принимает сертификат сайта, страница прочитана через `curl -k`):

- Права на запрос есть только у пользователя с ролью «Добавление запросов предложений».
- Позиции запроса: «Код ОКПД2/ККН» (выбор из справочника), «Код КТРУ» (подставляется, если есть),
  ед. измерения, характеристики.
- Цитата: «Для внесения сведений об организации или нескольких организациях, в адрес которых
  направляется запрос коммерческого предложения, в поле „Организация“ воспользуйтесь текстовым поиском».
- Цитата: «У поставщиков предусмотрена возможность получения запросов, в случае, если в личном
  кабинете установлен соответствующий признак. Поставщик не будет размещен в списке организаций …
  если признак поставщиком был снят».
- Ответы приходят во «Входящие уведомления»; в реестре ответов видны «Наименование поставщика»,
  «ИНН поставщика», дата (https://manuals.gz-spb.ru/estore/ru/lkz/lkz-2/lkz-9/lkz-11/lkz-12,
  проверено 2026-10-01).

Что из этого следует [ВЫВОД]:

1. **Встраивание.** Наш сервис может **подставлять готовый список адресатов в поле «Организация»**
   штатного запроса КП, по тем же ОКПД2 и ККН, что заказчик уже ввёл. Такую интеграцию легко
   объяснить жюри из ИМЦ: новую процедуру она не вводит, а дополняет существующую форму. Это наш
   основной сценарий встраивания (см. ниже, форма C).
2. **Ограничение.** Через эту функцию можно выбрать только тех, кто зарегистрирован в ЭМ и не снял
   признак «получать запросы». Поставщику, найденному в открытых источниках, нужен другой канал:
   пригласить его зарегистрироваться в ЭМ или написать по публичным контактам с его сайта. Блок
   «Новые» в UI так и подписываем: «нет в ЭМ — пригласить зарегистрироваться».
3. **Правовой тезис.** Если заказчику разрешено направлять запрос КП выбранным организациям, то
   и подсказка, кого выбрать, не меняет правового положения. Решение принимает заказчик.

Там же в руководстве [ДОК, оглавление https://manuals.gz-spb.ru/estore/ru/npo, проверено 2026-10-01]:

- **«Оценка участника закупки (поставщика) по исполнению контракта».** После исполнения или
  расторжения контракта заказчик получает «Опрос по работе поставщиков»
  (https://manuals.gz-spb.ru/estore/ru/lkz/lkz-4/lkz-10). Это готовый сигнал надёжности внутри АИС
  ГЗ. Публичен ли он и есть ли в данных организаторов — `UNKNOWN`, вопрос организаторам.
- «Работа с публичными офертами» и «Акцепт публичных оферт»: поставщик заранее публикует строки
  оферт. Цитата: если оферт нет «и отсутствуют публичные оферты, то закупка автоматически перейдёт
  в статус „Закупка не состоялась“» (https://manuals.gz-spb.ru/estore/ru/lkz/lkz-3/lkz-7/lkz-11).
- «Закупки других регионов»: реестры котировочных сессий заказчиков Москвы и Ленинградской
  области. Значит, ЭМ уже интегрирован с внешними площадками [ВЫВОД].
- «Журналы событий»: журналы по всем действиям со статусом контракта и актов. Для нас это шаблон
  аудита: каждая рекомендация логируется так же [ВЫВОД].

#### 1.1. Конкуренция (ст. 8 44-ФЗ) и приглашение поставщиков в закупку малого объёма

- [ДОК] Ст. 8 44-ФЗ. Ч. 1: контрактная система направлена на создание равных условий для
  конкуренции, любое заинтересованное лицо может стать поставщиком. Ч. 2 запрещает заказчикам
  «совершение любых действий, которые противоречат требованиям настоящего Федерального закона, в
  том числе приводят к ограничению конкуренции, в частности к необоснованному ограничению числа
  участников закупок». Источник — https://base.garant.ru/70353464/31de5683116b8d79b08fa2d768e33df6/
  (пересказ поисковой выдачи от 2026-10-01; дословный текст на consultant.ru не открывали — сверить).
- [ДОК] Электронный магазин — закупки у единственного поставщика по п. 4 и 5 ч. 1 ст. 93.
  Комитет по госзаказу СПб в FAQ пишет: заказчик «при осуществлении закупки у единственного
  поставщика … самостоятелен в выборе юридического лица (индивидуального предпринимателя)» и не
  обязан выбирать по минимальной цене. Если выбрана оферта с неминимальной ценой, нужно письменное
  обоснование, его учитывают контрольные органы
  (https://www.gov.spb.ru/gov/otrasl/kgz/obrasheniya-grazhdan/faq/4052/, проверено 2026-10-01).
- [ДОК] Лимиты ст. 93 44-ФЗ в ред. от 04.08.2026 (https://www.consultant.ru/document/cons_doc_LAW_144624/ab3273e757a9e718cbb3741596bc36eb8138e4f6/,
  проверено 2026-10-01):
  - п. 4 ч. 1 — до 600 тыс. ₽ за закупку; годовой объём не более 2 млн ₽ или 10% СГОЗ, но не более
    50 млн ₽;
  - п. 5 ч. 1 — до 600 тыс. ₽ (учреждения культуры и др.); годовой объём не более 5 млн ₽ или 50%
    СГОЗ, но не более 30 млн ₽;
  - ч. 12 — электронная закупка на электронной площадке до 5 млн ₽: оператор направляет заказчику
    не более пяти заявок с наименьшими ценами, выбор по наименьшей цене. Это **другой режим**, не
    ЭМ СПб.
  - На странице есть пометка о редакции, не вступившей в силу с 01.10.2026. По вторичному источнику
    (https://moscow.fz44.org/goszakupki-news/izmeneniya-v-goszakupkah-s-1-oktyabrya-2026/,
    проверено 2026-10-01) это 279-ФЗ от 04.08.2026: годовые ограничения п. 4 не применяются к
    закупкам для сельских населённых пунктов. **[ПЛОЩАДКА]** Для СПб это почти не важно, но на
    слайд лимиты ставить только с датой редакции.
- [ВЫВОД] Рекомендация конкуренцию не ограничивает. Закупка в ЭМ публикуется открыто (данные о
  закупках и офертах публичны на estore.gz-spb.ru), оферту подаёт любой аккредитованный поставщик.
  Сервис **добавляет** известных заказчику участников и никого не исключает из числа возможных.
  Ограничить конкуренцию может только фильтр, который убирает поставщиков из закупки, но наш
  фильтр действует лишь на подсказку.
- `HYPOTHESIS`: возможна претензия по ст. 17 135-ФЗ «О защите конкуренции» (координация,
  преимущественные условия), если сервис систематически советует одних и тех же. Текст ст. 17 не
  проверяли. Как защищаемся: блок «Новые», показатель концентрации (доля рекомендаций у топ-N
  поставщиков), «инкумбент» не главный сигнал, ранжирование прозрачно.
- **Формулировки для слайда и UI** [ВЫВОД]:
  - «Сервис расширяет круг участников, а не сужает его: закупка остаётся открытой для всех».
  - «Рекомендация — подсказка, кого уведомить или у кого запросить КП. Решение и ответственность
    остаются за заказчиком».
  - «Мы не скрываем поставщиков и не меняем порядок оферт в ЭМ».
  - «Каждая рекомендация объяснена: видно, почему поставщик в списке, и источник каждого факта».
  - Не писать: «лучший поставщик», «рекомендуем заключить контракт», «надёжный»/«ненадёжный» без
    названия источника.

#### 1.2. КП для обоснования НМЦК (ст. 22 44-ФЗ): порядок на 2026 год

- [ДОК] Ч. 5 ст. 22 (ред. от 04.08.2026): для метода сопоставимых рыночных цен можно использовать

- [ДОК] Ч. 20 ст. 22: методические рекомендации по методам определения НМЦК «устанавливаются
  федеральным органом исполнительной власти по регулированию контрактной системы в сфере
  закупок» (там же).
- [ДОК] **В тексте ст. 22 нет числа «не менее пяти»** (там же, поиск по странице). «Пять
  поставщиков» берётся из Методических рекомендаций, утверждённых приказом Минэкономразвития от

  № 567 — не менее пяти запросов», а не «по закону».
- [ДОК] Приказ № 567 по-прежнему действует: Контур.Норматив, статус «Действует»
  (https://normativ.kontur.ru/document?moduleId=1&documentId=220720, по выдаче поиска от
  2026-10-01). Письмо Минфина от 06.10.2025 № 24-06-09/96564
  (https://zakupki-inform.ru/44-fz/pisma-i-raz-yasneniya-po-44-fz/pismo-minfina-rossii-ot-06-10-2025-24-06-09-96564.html,
  проверено 2026-10-01) указывает, что рекомендации «носят исключительно рекомендательный характер
  и не являются обязательными», а субъект РФ вправе установить собственные дополнительные. Проект
  замены приказа № 567 Минфин публиковал в 2020 году (https://nposys.ru/obnovlenie-metodicheskih-rekomendacij-opredeleniya-nmck/).
  Принят ли он — `UNKNOWN`, в 2025–2026 годах замены не нашли.
- [ВЫВОД] Сценарий «у кого запросить КП» законен и полезен. Число адресатов задаёт рекомендация
  (5+), а не закон. Есть штатный инструмент ЭМ (см. «Главная находка»). Свои региональные
  рекомендации СПб по НМЦК — `UNKNOWN` **[ПЛОЩАДКА]**, вопрос организаторам.
- `HYPOTHESIS`: наш блок «Новые» можно продать как «больше независимых источников ценовой
  информации», но без цен контрактов цифру экономии мы не покажем.

#### 1.4. Персональные данные ИП (53.4% ИНН в данных — ИП)

  места жительства регулируется отдельно — п. 5 ст. 6, дословно не сверяли

- [ДОК] Руководства пользователя: ЭМ, «Портал АИС ГЗ 44-ФЗ», «Портал АИС ГЗ 223-ФЗ»

  (https://www.crpp.ru/proizvodstvennaya_kooperatsiya/zakupki___zaprosyi/ais_gz_elektronnyiy_magazin,
  проверено 2026-10-01). Источник вторичный.

  **[ПЛОЩАДКА]** Спросить ИМЦ.
- [ВЫВОД] Формы встраивания, по возрастанию стоимости для ИМЦ:
  - **A. Отдельный веб-сервис со ссылкой из карточки закупки.** Deep link
    `/?q=<наименование>&okpd2=<код>&customer=<ИНН заказчика>`, без доступа к закрытым данным АИС
    ГЗ. Работает уже сегодня.

    «встраивание» как цель.
  - **D. Пакетная ночная выгрузка** (CSV/parquet) рекомендаций по опубликованным закупкам — для
    аналитики Комитета: где мало оферт и кого можно было бы уведомить.

  Без LLM работают все четыре формы. Данные поставщиков берём только из открытых реестров с
  кешем, у каждого факта — evidence.

#### 1.6. Аналоги в РФ (один абзац, без маркетинга)

[ВЫВОД; сегодня проверены только описания из выдачи поиска, функции сервисов не проверяли.]
Коммерческие агрегаторы тендеров (Контур.Закупки, Тендерплан, РосТендер, СТАР, Гарант «Мастер
закупок» и др., https://rostender.info/extsearch, https://star-pro.ru/poisk-tenderov-zakupok,
https://goszakaz.garant.ru/) сделаны прежде всего **для поставщика**: найти закупку по ОКПД2,
ключевым словам, региону, посмотреть конкурентов и заказчиков. Сервисы СПС (КонсультантПлюс «ОКПД 2.
Поиск особенностей закупок», https://www.consultant.ru/news/278/) подбирают **код и правовые
особенности**, а не контрагента. В ЕИС есть механизм «запрос цен» (ч. 5 ст. 22): заказчик
публикует запрос и ждёт откликов, но поставщиков сам не подбирает. В ЭМ СПб есть ручной выбор
адресатов запроса КП текстовым поиском. B2B-маркетплейсы (СберB2B и т. п.) показывают каталог тех,
кто сам разместился. Чего мы не нашли ни у кого из перечисленных (`UNKNOWN`, не исчерпывающий
обзор): подбора **для заказчика СПб** по предмету его закупки с разделением на «знакомые по
истории ЭМ/АИС ГЗ» и «новые из открытых реестров», с объяснением каждой позиции и источником
каждого факта. Функции платных сервисов не проверяли: на защите не говорить «аналогов нет», а
говорить «аналоги работают на поставщика; мы работаем на заказчика внутри его системы».
